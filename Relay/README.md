# Relay

Passes Monster Girl Quest! Online's frames between games. The games never connect to each other directly: many home connections cannot be reached from outside (DS-Lite, CGNAT, no IPv6, no forwarded port), but every one can connect out, so every game connects out to the relay.

The relay never sees what is played: the games encrypt every frame with a key derived from the join code or the world's token, which the relay never gets. For worlds it keeps the **world directory**, which everyone can read, but for hidden worlds, which only their players and whoever names their id see listed: each world's name, seats and creator, its description, the mods it needs and what tells its creator's game data from another's, the names of its players and who is online. It never learns a world's password or token: it keeps the token locked with the password, and checks a game that enters against a hash. A world may keep a **starting save**, which the games encrypt with a key from the token before it arrives, so the relay only keeps its bytes. The one thing of a world it reads is its **chat**: the games mirror every line of the world's chat to it in plain text, so the relay's admins can read the chat and say something in it from outside the game; the map, party and whisper chats stay between their players.

## Protocol (v1)

A **world room** seats up to 32 games that play in the same world.

### Versions

Every game from 0.6.0 names its features in the header `X-MGQ-Features` on its directory requests and world rooms, and newer ones name their version in `X-MGQ-Version` on these, such as `0.6.5` (`0.0.0-dev` for a development build). The World Admin tool names `admin` in `X-MGQ-Features` and `0.0.0-dev` in `X-MGQ-Version`. Before routing a request, the relay turns a game too old for it away:
- the world directory's routes (the Raid World admin routes included), the trades, the bug reports, a Raid World's story and boss routes, the story mapping games read (`GET /v1/story-mapping`), the world rooms and the PvP rooms older games ask for (`/v1/room/<room id>`) need `X-MGQ-Features`, so games before 0.6.0 and builds of the World Admin tool before it named `admin` are refused;
- every one of these routes holds the version named in `X-MGQ-Version` against the lowest release an admin set (see Release control), else the setting `MIN_VERSION` (`0.7.1` unless set). A request that names an older version, none or one that is no version is refused. Only the development stamp `0.0.0-dev` (with or without `+<commit>`) always passes, so the World Admin tool does too; another suffixed version such as `0.7.0-beta` counts by its numbers;
- every route of the retired mod catalog (`/v1/mods` and below) is refused whatever the headers name, since the website's catalog took its place.

A refused world room gets HTTP 400 with the text `Update MGQ Online to play online.` and the code `update` in `X-MGQ-Refusal`: released games from 0.5.1 to 0.6.4 take a 400 with a code they do not know as final and show their own "The relay turned the request down. Update the mod.", while they would try a 426 again and again; newer ones show the text. Any other refused request gets HTTP 426 with the text as `error`.

### Release control

Which release the games should run and the lowest one the relay serves, kept in the relay's database, so they outlast a restart and need no change of its settings. The relay's admins set both (see Relay admin); the gate holds every game to the lowest at once. Once the update watch (see Update notice) reads a latest release newer than the current one and newer than the latest it had read when the current one was set, the relay clears the current release back to null, so the games follow GitHub's latest again, keeps the lowest one and logs it: a rollback to an older release lasts until the next release is out.

| Request | What it does |
|---|---|
| `GET /v1/release` | Hands out `current` (the release the games should run, such as `0.6.8`, null while unset), `min` (the lowest release the relay serves: the one an admin set, else `MIN_VERSION`) and `repo` (the repository the games update from, `Pauliinchen/MGQ-Online`). Open to every game whatever its version and headers. Only the Node relay answers it. |

### World directory

Plain HTTP with JSON bodies of up to 256 KB in general, and 413 beyond the size a route takes, on every route of the relay; a few routes take other sizes: a trade's commit, cancel and done 72 KB, and a boss report and an admin's request to a Raid World 4 KB. A world's id is 32 lowercase hexadecimal characters, the start of a hash of its token. A request names its player by the key in the header `X-MGQ-Player`, never from a POST's JSON body, and a world's auth key by the header `X-MGQ-Auth`; a key in the address counts for nothing, since addresses end up in logs. Where a route below names `player`, it means that key. A refusal's body holds `error` and, where the games tell reasons apart, `code`: `removed`, `members` (the world has as many players as it may, 200), `pending`, `rate` or `storage`. A route that does not exist is answered with 404.

| Request | What it does |
|---|---|
| `GET /v1/worlds?ids=<id>,<id>` | Lists every public world, and the hidden ones the player of the key in `X-MGQ-Player` joined or `ids` names (up to 50 ids, which the worlds' creators hand out; without a key and `ids`, public ones only), or every world for an admin. Answers `worlds`, each with the listed fields below, and `admin`, true for an admin. A game gets each world without its `mods`, `modHashes` and `settings`, which may be long, and with `modsCount` instead; it reads them for the world it opens from `GET /v1/worlds/<id>`. The website and the World Admin tool (naming `web` or `admin` in `X-MGQ-Features`) get every world with them. |
| `GET /v1/worlds/<id>` | Hands out one world as `world`, with every listed field below, its `mods`, `modHashes`, `modVersions` and `settings` included, and `admin`, true for an admin. Naming its id is enough, as it is for a hidden world in the list; 404 for a world the directory lacks. |
| `POST /v1/worlds` | Makes a world from the fields sent on create below. 201, or 409 when the id is taken, 429 past 20 worlds per creator, a limit admins do not have, 503 past 2000 worlds in all, and 429 with `code` `rate` past 5 worlds at once and 10 an hour from one address, counting only requests no other refusal turned away. A world whose starting save has not come 10 minutes after it was made is deleted. |
| `GET /v1/worlds/<id>/lock` | Hands out the world's `lock` (`salt`, `iterations`, `box`), which only the password opens, with its `name`, `seats`, `start` and `choose`, so a hidden world is entered by its id. |
| `POST /v1/worlds/<id>/edit` | Changes whichever of `seats`, `description`, `mods` (400 past 16000 characters), `settings` (400 past 64000 characters), `otherModsOff` (400 for anything but `true` or `false`) a Raid World's `difficulty` and `squad` (400 for a Classic world) and a Classic world's `raidBosses` (400 for anything but `true` or `false`, and for a Raid World) the body names, if `player` is the creator's or an admin's key, and replaces `data`, the creator's game data, and `modHashes`, if it is the creator's or an admin's. An admin's edit also changes whichever of these it names: `name` (as at create; 400 for a name that is empty once tidied), `featured`, `hidden` and `strict` (400 for anything but `true` or `false`), `creator` (the id of a player of the world whom the creator did not remove, who becomes its creator under the name the world knows them by; 400 for anyone else) and `lock` (`salt`, `iterations`, `box` as at create, a new password; 400 for one that is not as at create) with `open` (`true` when the new password is empty, since the games enter an open world with the empty password; 400 for `open` without a `lock`). An edit by anyone else leaves these fields as they are, as it always did, so released games that send them change nothing. Everything else of a world stays as it was made. Running games learn of none of these admin fields: no frame carries them, and a game reads the world's name and seats from the list as it enters the world, the creator's powers in the game too; players who entered the world before keep its token, so a new password only asks those who enter it for the first time. A new `difficulty`, `squad` or `raidBosses` goes to every game in the world room as a text frame, and so does an edit that changes whether the world turns other mods off or its mods (see world rooms below); an edit that sends the values the world has already tells nothing. |
| `POST /v1/worlds/<id>/delete` | Deletes the world, if `player` is the creator's or an admin's key, and closes its world room. |
| `POST /v1/worlds/<id>/ban` | Removes the player whose id is `target` and keeps them out, if `player` is the creator's key. A world keeps at most 500 removed players (429 beyond). |
| `POST /v1/worlds/<id>/start` | Keeps the world's starting save, the body as bytes (at most 8 MB), if the key in `X-MGQ-Player` is the creator's and the world was made with `start: true`. Only once: 409 afterwards. 413 past 8 MB, 507 with `code` `storage` once all starting saves together would pass 1 GB, and 429 with `code` `rate` past 5 uploads at once and 10 an hour from one address. |
| `GET /v1/worlds/<id>/start` | Hands out the starting save as bytes, to a game the world room would let in, with the player's key in `X-MGQ-Player` and the auth key in `X-MGQ-Auth`. 404 when the world has none. |
| `GET /v1/worlds/<id>/chat?after=<n>` | Hands out the world's chat as the relay saw it, if `player` is the creator's or an admin's key: `lines`, oldest first, each with `n` (its number, counting up), `at`, `player` (the sender's id), `name`, `text` and `admin` (true for a line said over this route). With `after`, only the lines numbered beyond it. The relay keeps the last 200 lines of each world, 200 characters each at most; the games mirror every line of the world's chat into it (see world rooms below), the map, party and whisper chats stay between their players. |
| `POST /v1/worlds/<id>/chat` | Says a line in the world's chat as an admin: `text` (1 to 200 characters) and `name` (the name the line carries, up to 32 characters; `Admin` when left out), if `player` is an admin's key (403 for everyone else, the creator included, who talks through the game). The line goes into the chat and to every game in the world room as a text frame. Answers the `line` as kept. |

| `online`, `created`, `active` | | yes | How many players are in the world now, when it was made, when someone was last in it. |
| `members` | | yes | Every player who joined: `id`, `name`, `online`, `seen` (when last in the world). |

A player's key never appears in the list: everyone sees the player's id, the first 32 characters of the SHA-256 of `mgqmp player <key>`. Names are at most 32 characters, on one line.

**Admins** look after the directory: they see every world, hidden ones too, may delete any, and make the featured worlds. They cannot open a world's lock or enter it without its password. The relay reads their player ids from the setting `ADMINS`, separated by commas or spaces; without it there are none. The relay reads it from the environment variable of the same name. An admin's id is made from the key in their game's `Patch\Multiplayer\Player.ini`, as above.

### Relay admin

The relay's own routes for its admins (the `ADMINS` setting), such as the website's dashboard. Each takes an admin's key in `X-MGQ-Player`, and a POST a JSON body of up to 4 KB; 403 for everyone else. They need no `X-MGQ-Features`.

| Request | What it does |
|---|---|
| `GET /v1/admin/stats` | Hands out what the relay carries now: `startedAt` (ISO time), `uptimeSeconds`, `memory` (`rss`, `heapTotal`, `heapUsed`, `external`, in bytes), `worlds` (each world room open: `id`, `name`, `type`, `seats`, `players`), `players` (`worlds` and `total` connections), `versions` (the world rooms' games by the version they named in `X-MGQ-Version`, `unknown` for none, such as `{"0.6.7.7": 3}`), `battles` (`tracked`, the server battles the relay keeps, and `served`, those with a connection to the battle server) and `battleServer`, the battle server's answer to `{"op":"ping"}` as it sent it (`ok`, `boot_seconds`, `battles`, `busy`, `mode`, `pid`; in fork mode `battles` and `busy` are the child's own), null without a battle server or when it does not answer within 2 seconds. |
| `GET /v1/admin/release` | Hands out the release control as `GET /v1/release` does, with `envMin` (what `MIN_VERSION` sets), `updatedAt` (when an admin last set it, in milliseconds since 1970, null before) and `updatedBy` (that admin's player id). Only the Node relay answers it. |
| `POST /v1/admin/release` | Sets `current`, `min` or both, each a version of 1 to 4 whole numbers separated by dots, or null to clear it back to its default (none for `current`, `MIN_VERSION` for `min`); one left out stays as it is (400 for a body naming neither, or a value that is no such version). A lowest release above the current one, `MIN_VERSION` counting while no `min` is set, is refused with 400 and `code` `min_above_current`. Answers as `GET /v1/admin/release`. The gate holds every request after it to the new lowest release; games already in a room stay. The relay logs each change with what it replaced. Only the Node relay answers it. |
| `POST /v1/admin/announce` | Says `text` (1 to 120 characters once control characters are taken out, the most released games show of a chat line; 400 otherwise) in the chat of every world with players online, as the update notice is said: an admin's line named `MGQ Online` that every game in those world rooms hears as `chat MGQ Online` + tab + the line and the world's admins see in its chat. Games from 0.6.5 on show it red as `// <line> //` in every chat tab, older ones as `[Admin] MGQ Online: <line>`. Answers `text` as said and `worlds`, in how many it was said. The relay logs each line. Only the Node relay answers it. |

### Story mapping

One story mapping every Raid World shares, which the relay's admins keep by hand in the website's World Admin (story plan phase 1): which switches and variables the world's story shares and by which rule (`keys`), the events whose self switches go against the rule (`events`), the index of the map events whose self switches are shared because they read or write a shared key, which the battle server derives from the rows and the game's events, and beside them the catch-up's tables, kept and served alike (see below). A key without a row is each player's own, so an empty mapping leaves the whole story personal. Only the Node relay keeps it, in the SQLite tables `story_meta`, `story_history`, `story_index` and one `story_<table>` per table. The admin routes take an admin's key as the relay's admin routes do; edits take bodies of up to 1,000,000 characters.

| Request | What it does |
|---|---|
| `GET /v1/admin/story` | Sums the mapping up: `rev` (raised by every batch and every index kept), `rowsRev` (the last batch that changed rows), `tables` (each table's rows counted) and `index` (`built`, the `rowsRev` it was built from, `stale` once rows changed since, `events` and `commons` counted, `author`, the admin's player id or `battle server`, `time`; null before the first). |
| `GET /v1/admin/story/<table>` | Hands out `rev`, `table` and `rows`, each `{id, row, note, author, time, rev}` (the admin's player id, milliseconds since 1970, the revision of its last change), in the order games read them. 404 for no such table. |
| `GET /v1/admin/story/<table>/<id>/history` | Hands out the row's last 20 changes, newest first, also of a row removed since: each `{rev, op, before, after, note, author, time}`, `before` and `after` the whole rows (null for an add or a remove). |
| `POST /v1/admin/story/edit` | Applies `edits` (1 to 2000) whole or not at all, as one new revision: each `{table, op, ...}`, `op` `add` with `row`, `change` with `id` and the whole `row`, `remove` with `id`; `note` (at most 500 characters) sets the row's note, left out it keeps the note it had. A row of `keys` or `events` is named by its `key`, which a change keeps. `rev`, the revision the admin read, refuses the batch once the mapping moved on; left out, nothing is checked. Answers `rev` and `changed` (each `{table, id, op}`; a change that leaves a row and its note as they were is none, and a batch of only those raises nothing). Refused with `error`, `code` and `edit` (the index of the edit refused): 400 `edits` (not a list of edits, an unknown `op`, an add with an `id`, a change or remove without one), `table` (no such table), `field` (a field missing, unknown or not as it should be), `kind` (a kind that does not fit a switch or a variable), `option` (an option the kind does not take, or one it needs left out), `twice` (one row named twice), `key` (a change of a row's key); 409 `exists` (an add of a key the table holds), `missing` (a change or remove of a row it lacks), `rev` (with the current `rev`). The relay logs each batch. |
| `GET /v1/admin/story/names` | Hands out `rowsRev` and `names`: `built`, `stale`, `names` (`switches`, `variables` and `maps`, each id to the game's name, the empty ones left out; `events`, each `"<map>.<event>"` to its name; `companions`, how many entries the game's actor list holds, which is how many affection variables it keeps), `author`, `time`; null before an index with names. The website's World Admin can show the keys with them in place of a names file. |
| `GET /v1/story-mapping` | For games, open to all; a game asks for it on entering a Raid World and again on a push of a newer revision: `rev`, `tables` (each table's rows as `row` alone, without ids and notes, in story order) and `index` (`built`, `stale`, `events`, `commons`; null before the first). `?known=<rev>` answers `{rev, same: true}` alone while the mapping is at that revision. |

**The derived index** is built by the battle server, which holds the game's `Data/`, over the relay's connection to it (`BATTLE_SERVER`; without one nothing derives it): after every batch that changed rows, and half a minute after a start when the index is missing or stale, the relay sends `{"op":"story_index","rowsRev":N,"keys":[{key, kind}],"events":[{key, share}]}` and keeps the answer `{"ok":true,"built":N,"events":[[map, event]],"commons":[id],"names":{...}}` (waiting up to 2 minutes for one line of at most 64 MB) with `author` `battle server`; `{"ok":false,"error":...}` and no answer keep nothing and are logged. One runs at a time; a batch meanwhile, or rows that changed while the server derived (409 `rev`), make it run once more. `events` are the map events whose self switches are shared because an event reads or writes a key of kind `shared`, `one_way` or `count`, `commons` the common events that do (their self switches are those of the event calling them), both with the `events` rows for a whole event, map or common event (letter `*`) applied; a row for one letter is the reader's to apply.

**`keys`** rows: `key` (`s<id>` or `v<id>`, ids 1 to 99999), `kind` and the options its kind takes:

| Kind | Fits | What it means | Options |
|---|---|---|---|
| `personal` | switches, variables | each player's own, as a key without a row; a row only carries an option or a reviewed decision | `defeatWrite` |
| `shared` | switches, variables | the world's story shares it | `defeatWrite`, `wholeWorld`; variables also `routeReturnClears`, `defeatReturns`, `battleScene`, `localSteps` |

Options, each left out when off: `defeatWrite: true` (the post-defeat processing writes it, and a frozen fight's undo leaves it as the defeat set it); `wholeWorld: true` (the whole world keeps it, players behind included, as the companions' affection, see Story tracks); `routeReturnClears: true` (the route return, common event 154, clears it, so a one-way key may go down then); `defeatReturns` (`{"<step>": <value>}`: steps a story event sets before a battle it cannot lose, which the world keeps as the value its defeat sets); `battleScene` (`{steps, start, mainStep, troops}`: steps a story event sets before raid boss battles of its own, which the world keeps as `start` while variable 1001 is at `mainStep` and no fight of the troops is frozen or over); `localSteps` (`{steps, sharedAs, places}`: steps that stay each player's own while they stand in one of the `places`, each `{map, fromX}`, and that the world keeps as `sharedAs`); `counts` (`{from, to}`: the switches counted, at most 1000).

**`events`** rows: `key`, the self switches of a map event (`ss<map>.<event>.<letter>`, `*` for every event or every letter: `ss231.*.*` for every self switch of map 231, `ss0.*.F` for the found items' self switches on map 0, which has no events) or those a common event writes (`ce<id>.<letter>`); `share` (`shared` or `personal`, against what the derived index says); `chest: true` for a chest's self switches, with `share` `personal` only, which the relay keeps for the player alone (the `chest` kind of Story tracks); the reviewed seed holds such a row only for the chests whose event the derived index would otherwise share, while every other chest's self switches stay in the player's own save; `wholeWorld: true` with `share` `shared` only, for self switches the whole world keeps, players behind included (the found items' `ss0.*.F`, so a key item or a job or race item any player found reaches every player of the world). A relay seeded before 2026-11-01 keeps its `ss0.*.F` row without the option until an admin changes it.

A file holds either `rows` (each as an admin would add it) and `source` (where they came from), or the list of edits an admin would send to `POST /v1/admin/story/edit`, each an `add` of the file's table. At every start the Node relay fills each table that holds no rows yet from its seed file, all in one revision with the author `seed` and no history, and leaves every table with rows as the admins keep it; a table it filled or found with rows once is never seeded again (the mapping's meta names it in `seeded`), so a table the admins emptied stays empty; a seed file of another shape or a seed row the table refuses stops the relay, and a relay installed without the folder seeds nothing and logs so. The seeding leaves an edit's `note` out, which an admin who applies a file through the route keeps; the route takes at most 2,000 edits at a time, so the larger files go in slices. The mapping's own `keys` and `events` are seeded the same way, from their reviewed rows.

**Join and removal indexes as ords.** The `index` of `joins` and `removals` once named a command's place in the list of the copy of the game the rows were read from (the TEST install, a common event's place in its data file), which a translation moves. The seed holds ords since 2026-10-28; a relay seeded before keeps the places until one reviewed batch rewrites them, once: an admin saves `GET /v1/admin/story/joins` (and `.../removals`) as a file, runs `dotnet run --project MGQOnline.Data.Generator -- ordinals package/Multiplayer/Data/events.db "<the TEST install>" <saved file> <batch.json>` in the repository, reviews the batch (each edit a `change` of a row whose index moves, at the listing's `rev`; the command names every row whose command it did not find and leaves it out) and sends it to `POST /v1/admin/story/edit`. Run on a table already rewritten, it would read the ords as places, so it runs once. The games compare an `index` only with another of the same list, a removal against a join of the same companion, which the rewrite keeps in their order.

### Story tracks

A Raid World's story as the relay's own, key by key (story plan phase 2), on **tracks**: the world's track `world`, which every player who keeps up with the world plays, and a track of their own, `t<n>`, for each player behind the world. Games send the keys their own events write as requests; the relay applies them by the story mapping (see Story mapping) in the order they arrive, pushes what changed to every game on the track, and answers each request it did not keep as written with its own value. Only the Node relay keeps tracks, in the SQLite tables `track_meta` (each world's summary), `track_keys` (one row per key of a track), `track_players` (each player's track, last place, chest flags, last batch and cursor per track), `track_runs` (one row per run entry of a track) and `track_checkpoints`; telling locks and levels live in memory, so a restart ends them. The game plays its story on them (story plan phase 3b); the keyed story (see World story) keeps a world's shared companions and the admins' pins, released games play it, and a world's tracks start from it.

Every game plays it over its world room in a Raid World, both ways as text frames `track <JSON>`, each one JSON object whose `t` names it. The world room's limits hold for them (512 KB a message, 60 a second). A game in a Classic world is closed for such a frame as for any other text.

**Keys and values.** A key is `s<id>` (switch), `v<id>` (variable), `ss<map>.<event>.<letter>` (self switch; map 0 for the Makina's found marks) or `f<troop>` (a frozen raid boss fight), ids without leading zeros. Values travel and are kept as text, never as numbers: a switch or self switch `1` or `0`; a variable as `story_state.rbx` `encode_value` writes it (`n<whole number>` of any length, compared exactly; `f<decimal>`, `s<base64>`, `T`, `F`), at most 4096 characters; a frozen fight as `world_freeze.rbx` writes it, `0` once it ended, at most 65,536. A key nobody wrote is `0` or `n0`.

**What a request does**, by the key's kind at the relay's current mapping revision (each answer names it in `mapping`):

| Kind | Kept | A request |
|---|---|---|
| no row, `personal` | nowhere | answered `personal` without a value: the game keeps its own |
| `scene` | nowhere | answered `scene` without a value |
| `chest` | with the player | kept for the player alone, never pushed |
| `shared` | on the player's track | goes in |
| `one_way` | on the player's track | goes in, but a whole number below the kept one is answered `one_way` with the kept value, unless the row has `routeReturnClears` and the write comes from `ce:154` (the route return) |
| `count` | on the player's track | answered `count` with the count: after every batch the relay counts the switches of `counts` that are on in the track |
| `f<troop>` | on the world's track | goes in for the whole world, also from a player behind; once `0` it is answered `ended` with `0` |

- **`wholeWorld`**: the key is kept on the world's track for every player, players behind included, so a player behind writes it to the world's track and reads it from there (the companions' affection, `one_way`, is the highest any player of the world reached). The found items' marks, `ss0.*.F`, and the marks of the key items events used up, every other self switch of map 0 (`ss0.*.*`), are always the whole world's, whatever their `events` row says (`FOUND_MARKS` of `core/story_tracks.js`, and the game's `StoryMapping`), so a relay whose seeded row predates the option needs no edit.
- **Steps the world never shares**, in this order: `localSteps` (a step of `steps` is kept as `sharedAs`), `battleScene` (a step of `steps` while the track's 1001 is at `mainStep` and no `f<troop>` of `troops` is on the world's track is kept as `start`), `defeatReturns` (a step named is kept as its value). Answered `step` with the value kept: the writing game keeps its own value until its event ended, as it takes pushes only once it is free (open question B2). `defeatWrite` changes nothing on the relay.
- **Self switches** by the most fitting `events` row: the key's own, its event's (`ss<map>.<event>.*`), the common event's that wrote it when the site is `ce:<id>` (`ce<id>.<letter>`, then `ce<id>.*`), its map's letter's (`ss<map>.*.<letter>`), its map's (`ss<map>.*.*`); without a row `shared` when the derived index names the event, else personal. A `chest` row makes it a chest flag.
- **Pins**: a key an admin pinned (the Raid World admin's pins, kept with the keyed story) is answered `pinned` with the pinned value on the world's track; a player behind writes it on their own track. A change of the pins sets every kept pinned key of the world's track and pushes it. An admin's keys and route lock act on the world's track alone as well (see the admin routes under Raid bosses), never on the tracks of players behind.
- **Routes** (the world's track): a route variable (1141, 1142, 1143) above 0 is answered `route` while 1001 is below 40 or another route is under way; with no route locked, the first such write locks its route, or is answered `finished` or `closed` as the route frame is; while one is locked, another route's variable and the clear switch (7096, 7097, 7039) of a route the world did not finish are answered `route`. The lock ends with the batch after which the locked route is finished and none is under way, once the route was under way or was finished in that batch.
- **The hold for players behind** (a track of their own): a write of 1001, 1141, 1142 or 1143 that would move the track out of its part is answered `held` with the track's value; everything else goes in, so only what moves their story past the end of their part waits for their level gate.

**Frames a game sends:**

| `t` | Fields | Answer |
|---|---|---|
| `sync` | `level` (`{best, cap}`: the highest base level among the player's characters not on a visit and the highest level the game lets that character reach, `null` without a cap; 1 to 99,999; left out while the game does not know it yet, as after a save loads, which keeps the gates shut until a `level` frame names it), `cursors` (`{<track>: n}`, the cursor of the game's saved log on each track of the world it took entries of), `seed` (the game's story: each key the mapping keeps or a chest flag to its value; at most 40,000 keys) when the relay asks or with `fresh: true` (a new game or a story from elsewhere, which places the player anew) | `state`, or `need` (`{what: "seed"}`) for a player the relay does not know yet |
| `write` | `seq` (whole number above the player's last batch), `track` (the one the game plays on), `writes` (1 to 4000, each `[key, value, site]`; site `map:<map>:<event>:<page>` with pages from 1, `ce:<id>`, or `game` / `game:<what>` for a write outside events, such as `game:affection`), `run` (a run entry, see Run entries; then `writes` may be empty or left out) | `answer`, then a `push` per track it changed, then `run` when the track kept the entry |
| `runs` | `track` (the one the game plays on), `after` (an entry's number) | `runs` |
| `took` | `track`, `n` (the number of the entry the game took) | none |
| `level` | `best`, `cap` | `state` with `why` `moved` when the gate opened |
| `tell` | `telling` (the game's id, 1 to 32 of `A-Za-z0-9_-`), `map`, `event` (the site that started it) | `telling` to the other games on the track, then `tell` |
| `told` | `telling` | `told` to every game on the track |
| `watch` | `teller` (seat), `telling` | `watch` |
| `route` | `route` (`ad`, `mr`, `chaos`) | `route`, and a `push` with the world's summary when it locked |

**Frames the relay sends:**

- `state`: the whole track, which the game lays over its story's kept keys: `why` (`started`: the seed started the world's story; `sync`; `behind`; `moved`), `track`, `rev`, `part`, `gate` (the level gate of the track's part, `null` on the world's track), `move` when the player moved on (`{from, to, gate, by}`, `to` a part or `world`, `by` `level` or `cap`), `world` (the world's summary: `rev`, `part`, `route`, `done`, `open` (the routes a `route` frame is granted, which the Great Decision offers), `checkpoints` and `start`, the story markers v1001, v1141, v1142 and v1143 where the world's run entries begin: where its story started, or where it stood when the relay first kept run entries), `mapping`, `seq` (the last batch taken), `keys` (each key the track keeps; on a track of one's own with the world's `wholeWorld` keys and frozen fights), `chests` (the player's chest flags), `tellings` (`[{telling, teller, map, event}]` on the track), `cursor` (the player's cursor on the track), `last` (the number of the track's last run entry, 0 for none) and `log` (the world's keys where its run entries begin that differ from `keys`, a key the start lacks at its value nobody wrote: `0` or `n0`); followed by `runs` after the cursor when `last` is past it.
- `answer`: `seq`, `revs` (`{"world": <rev>, "<own track>": <rev>}`, the revisions after the batch), `mapping` and `keys`: each key of the batch not kept as written, `{code, value}` (no `value` for `personal` and `scene`), a key written twice answering for its last write; with a run entry `run` (`{id, n}`, `n` the number the track kept it under, `null` when it kept none). Or a whole batch refused with `code` alone, nothing applied: `sync` (sync first), `seen` (with `revs`: the relay took this `seq` already, as after a reconnect), `track` (with `track`, the one the player is on: sync anew), `bad` (with `error` and the write's `index`).
- `push`: `track`, `rev`, `prev` (the revision before), `keys` (what changed, with the values kept), and `world` (the summary) when it changed. A game on the world's track hears every revision, its own writes' too, so a gap means it missed one and syncs anew. A player behind hears every revision of their own track, and of the world's only those that change `wholeWorld` keys, frozen fights or the summary.
- `run` (`track`, `run`: an entry the track kept, with its number `n`) to every synced game on the track, the writer's too; `runs` (`track`, `runs`: up to 16 entries after the number asked for, oldest first; `more`: whether later ones follow).
- `telling` (`telling`, `teller` seat, `map`, `event`, `track`), `told` (`telling`, `teller`, `map`, `track`, `rev`: the track's revision as the telling ended, the one of the teller's last write; `why`: `ended`, `left` or `moved`), `tell` (`telling`, `granted`, `track`; refused with `code` `taken` and the holder's `teller`, `holding` and `event`, `many` past 4 locks of one player, `sync` or `bad`), `watch` (`teller`, `telling`, `watching`), `route` (`route`, `granted`, `code` when refused: `route`, `finished`, `closed`, `track` for a player behind, `sync`, `bad`), `mapping` (`rev`, after an admin changed the story mapping: read it anew), `need`, `error` (`code` `bad`, `error`).

**Order.** A world's frames run one at a time, in the order they arrive; a batch's writes in their order, each by the track as the writes before it left it; each batch is one revision of each track it changed. The writer's `answer` comes before the batch's pushes, pushes come in revision order, and the other games on a track hear `telling` before the teller hears its grant, so they know the teller before its first page.

**Placing players.** The world's track starts with the world's keyed story, or without one with the first `sync`'s seed (the keys the mapping keeps). A player the relay does not know, or one syncing `fresh`, is placed by their seed: a story in an earlier part than the world's (another part, and earlier in the story's order of today's keyed story) gets a track of its own at that part's checkpoint, or the seed's kept keys when the world keeps none of that part; any other plays the world's track, the seed's values dropped. The chest flags come from the seed. A player known on the world's track who left in a part the world has left since is behind at that part's checkpoint on their next `sync`. While a batch moves the world's track out of a part, every synced game on it, but the writer's and those that `watch` the writer's telling, whose level does not open that part's gate falls behind to a track at its checkpoint (`state` with `why` `behind`).

**Moving on.** A part's gate is its `gate` in the `parts` table; it opens when `best` reaches it, or when `cap` is below it and `best` reaches `cap` (another mod's level cap, `by` `cap`). On every `sync` and `level`, while the gate of a track's part is open, the player moves on: to the next of the parts the world played (1, 2, 3, the routes it finished, the route under way) that has a checkpoint, the routes skipped, as a new track at that checkpoint; or, at the world's part or with none left, to the world's track, which ends their own. A track does not end because the world came back to its part. Without `parts` rows nobody falls behind; a part without a row has no gate. A part's checkpoint is kept the first time the world's track leaves it: the world as it stood when the writer's telling on the world's track started, else before the batch.

**Run entries.** A run is one start of an event that changed shared keys and gives ("Issue 73 chest effects.md", "Streams, logs and catch-up"); its game sends the run's entry with the batch after the run's last writes: `id` (1 to 80 of `A-Za-z0-9_:.-`), `site` (as a write's), `keys` (the keys of its step, 1 to 4000), `place` (the story markers v1001, v1141, v1142 and v1143 at its start, `null` for none), `opener` (the opener's name, `null` for none) and `wire` (the packed replay the receivers' games play, base64), at most 32,768 characters of JSON. The player's track keeps the entry, numbered after its last one, only when a key of its step was last changed on that track by this player's own write, which the entry then uses up: so a write the track refused, or the second of two players who opened the same thing, makes none. A track keeps every entry for good; a track of one's own drops them with its keys. Each player has a **cursor** on the world's track and on their own, the number of the last entry their game took: each `sync` sets it to the one its `cursors` names, the cursor of the game's saved log, or 0 for a track it names none of, and only their own `took` moves it on. A player moving onto the world's track from their own walks it on from their cursor there, so the world's runs they never played come too; their game's log claims what they played (see "Issue 73 chest effects.md", rule 2). A world whose story never ran on tracks starts its world's track from its keyed story, with no entries before. The world keeps its keys where its entries begin as the checkpoint `log`: the first seed's, or the world's as it stood when the relay first kept run entries.

**Telling locks**, one per map and track: the first game to `tell` on a map tells there for its track; another game on that track and map is refused `taken`, a game on another track is not. A `tell` with the same `telling` on another map moves the lock there (its viewers and start go along); another telling of the same game on the same map replaces its earlier one, which ends. A lock ends with `told`, with the teller's game leaving the world room (`left`) and with the teller's track changing (`moved`). `watch` notes a viewer of a telling on the viewer's own track.

### Mod catalog

Retired with 0.7: every route of `/v1/mods` answers HTTP 426 with `Update MGQ Online to play online.`, whoever asks. A world's mods come from the website's catalog (`/api/mods`) through the Mod Framework, and the games, the battle server and the website's admin pages work with it there. The tables `mods` and `mod_files` stay in the database untouched, so a rollback finds them.

### Update notice

Every five minutes the relay reads where `https://github.com/Pauliinchen/MGQ-Online/releases/latest` leads (`RELEASE_REPO` names another repository), which needs no GitHub API. The first release it ever reads is only kept; each newer one is said once, as `MGQ Online <version> is out. Restart the game and pick Multiplayer to update.`, in the chat of every world with players online, as an admin's line named `MGQ Online` that the world's admins see in its chat too. Games from 0.6.5 on show it red as `// <line> //` in every chat tab; older ones as `[Admin] MGQ Online: <line>`.

### Trades

Two players of a world swap items through their games, and the relay referees the swap, so a disconnect or crash never copies or loses anything. Each game commits a hash of the offers both games agreed on; the relay marks the trade committed once both hashes match, in one write, and only then do the games apply it. The offers travel sealed with a key from the world's token, so the relay keeps their bytes only, for a game that crashed before it applied the trade to fetch again. A trade's id is 32 lowercase hexadecimal characters, which the games make.

| Request | What it does |
|---|---|
| `POST /v1/trades/<id>/commit` | Commits one side: `player` (the key), `world`, `partner` (the other player's id), `hash` (SHA-256 of the offers, hexadecimal) and `sealed` (the sealed offers in base64, at most 64 KB; 413 beyond). Both players must be players of the world, whom the directory lists as members and the creator has not removed (403 otherwise; the creator always is one). The first commit makes the trade `pending`; the partner's commit with the same hash makes it `committed`, a different hash `cancelled` with `reason` `differ`. The same commit again changes nothing; other offers from a player who committed already, or a commit naming another world or partner than the trade's, get 409. A player may open at most 20 trades that are pending or committed and not yet done, and at most 100 a day that end cancelled (429). Answers `state` and, when cancelled, `reason`. |
| `POST /v1/trades/<id>/cancel` | Cancels a pending trade with `reason` `cancelled`, if `player` is the key of one of its two players. A committed trade stays committed. Answers `state` and `reason` as above. |
| `GET /v1/trades/<id>` | Answers `state` and `reason` to one of the trade's two players, 404 to anyone else. A trade still pending 2 minutes after its first commit is cancelled with `reason` `expired`. |
| `GET /v1/trades?world=<id>` | Lists the world's committed trades the player has not marked done: `trades`, each `id`, `hash` and `sealed`, the offers as the player's own game sealed them. |
| `POST /v1/trades/<id>/done` | Marks a committed trade done for `player`, whose game applied and saved it (409 for a trade not committed). The trade is deleted once both players marked it done. |

Committed trades nobody finished are dropped after 30 days, cancelled ones after a day. The relay keeps each player's sealed offers beside the trade, not in it, and drops them as soon as the trade is cancelled.

### Bug reports

A player reports a bug from the game. The relay commits the report as a folder of plain files, `reports/<id>/` with `report.md` as its index, in one commit to the branch `REPORT_FILES_BRANCH` (default `main`) of the private `REPORT_FILES_REPO` (default `Pauliinchen/MGQ-Online-Bug-Reports`), so a report reads in the browser or after a `git pull`. Then it opens a public issue in `REPORT_ISSUES_REPO` (default `Pauliinchen/MGQ-Online`) with the player's title and text and a few public facts, linking `report.md` and the screenshot, which only the developer can open. It takes reports only with two GitHub tokens: `GITHUB_ISSUES_TOKEN`, which may write issues in the issues repository, and `GITHUB_BUG_FILES_TOKEN`, which may write contents in the files repository alone, so no token of the relay can change the public repository the mod updates from. The relay keeps nothing of a report; it unpacks the text files and passes the screenshot's base64 to GitHub as sent. It handles one report at a time and reads a report's body for at most 60 seconds.

| Request | What it does |
|---|---|
| `POST /v1/reports` | Takes a report from the player whose key is in `X-MGQ-Player`. The body, at most 15 MB: one line of JSON, a line break, then the base64 of each file in the order the JSON lists them, with nothing between them. The JSON (at most 16 KB): `title` (1 to 100 characters on one line), `text` (1 to 4000 characters), `version` (1 to 32 letters, digits, `.`, `+` or `-`), `facts` (at most 12 `[label, value]` pairs on one line each, the label 1 to 32 characters, the value up to 120) and `files`, 1 to 32, each with `name`, `length` (the characters of its base64, a multiple of 4; together they add up to the rest of the body) and `gzip` (`true` or `false`, false unless given). A name is up to 120 characters, a file or a folder and a file, each starting with a letter or digit, then letters, digits, spaces and `._()+-`, and no two alike whatever their case. `report.md` is required; `screenshot.png` is the one binary file, never gzipped, at most 4 MB of base64; every other file ends in `.md`, `.log` or `.txt` and is text, unpacked from gzip when flagged and read as UTF-8, at most 8 MB each and 24 MB together unpacked. Answers 201 with `issue` (its number), `url` and `id` (the report's, `<UTC day>-<8 hexadecimal characters>`); 400 for a body that breaks a rule, a gzip stream that does not unpack or a body still arriving after 60 seconds, 401 with `code` `player` without a player key, 413 for a body or file over its limit, 429 with `code` `rate` past 3 reports of a player at once and one more every 144 minutes, or 6 of an address at once and one more every 10 minutes; the relay answers 401, 429 and both 503s before it reads the body, which it then reads to its end and drops, 503 with `code` `off` without both tokens, 503 with `code` `busy` while the relay handles another report, and 502 with `code` `github` when GitHub refused or could not be reached, whose status the relay logs per step. |

The commit goes through GitHub's Git Data API: the relay first checks that every text file unpacks within its limits, so a refused report leaves nothing on GitHub, then uploads the screenshot and every text file over 64 KB as a blob of its own, also the small ones once the inline texts would pass 1 MB together; the other text files go inline in a tree on the branch's head, the commit `report <id>: <title>`, then the branch moved to it; when another report moved the branch meanwhile, the relay commits again on the new head with the blobs it uploaded, 3 tries in all. The issue is titled `[In-game] <title>` and labelled `in-game report` (left off when GitHub refuses the label); every `@` in the title, text and facts gets a zero-width space after it, so a report mentions nobody.

### World story

A Raid World plays one story, which the relay keeps beside the world room: the counters it reads to tell which story is further (`p` for variable 1001, `r1141`, `r1142`, `r1143`, the finished routes, the story teleport's endpoint, the shared companions) and the story key by key, each switch, variable and self switch older games wrote over HTTP, which the relay keeps as world data: the world's story tracks start from it (see Story tracks), which play the story now. Games read its revision and shared companions and add companions here, and write none of the story. A story an older relay kept sealed counts as one nobody wrote key by key. Classic worlds keep none (404, code `classic`). The routes take the player's key and the auth key in the headers, as the world room does, and answer the world's players only. Why the story works this way is in [docs/DEVELOPER.md](../docs/DEVELOPER.md#world-story-on-the-relay).

| Request | What it does |
|---|---|
| `GET /v1/worlds/<id>/story` | Hands out `rev`, the story's revision, which every change counts up, and `comps`, the shared companions. |
| `POST /v1/worlds/<id>/story/companions` | Adds actor ids to the shared companions, which only grow. |

### Raid bosses

A Raid World's story bosses each have a pool whose HP the whole world shares, kept beside the story in the world room's own object. A pool keeps the share of the boss's raid max HP left, 0 to 1, with the max the first report named, since each game's difficulty and mods set the boss's max HP in its own game. It fills up again by 3% of its max a minute, also while battles fight it, and costs no writes for it: every read computes the share left now from the last report. The host of every battle fighting the boss reports what its players took off since its last report as each action ends, at most every two seconds, at each command phase and at the battle's end; the report that empties the pool defeats the boss for the world until an admin resets it. The routes take the player's key and the auth key in the headers, as the story's do, and answer the world's players only; Classic worlds keep none (404, code `classic`). A key may hold spaces and `#` (a boss of several enemies has a pool per enemy, such as `Metatronne and Sandalphone#1`) and is percent-encoded in the address, up to 72 characters; a world keeps at most 500 pools. The routes below are the contract; why the pools work this way is in [docs/DEVELOPER.md](../docs/DEVELOPER.md#raid-bosses).

| Request | What it does |
|---|---|
| `GET /v1/worlds/<id>/bosses` | Hands out every pool a report touched (`bosses`, each with `key`, `left`, `max`, `defeated`, `at` and `by`) and `regenPerMinute`. `left` is the share left now; `by` names the player whose report emptied the pool. |
| `GET /v1/worlds/<id>/bosses/<key>` | Hands out one pool; a pool never reported is full, with `max` null. |
| `POST /v1/worlds/<id>/bosses/<key>/report` | Counts what a battle took off since its last report, in a body of at most 4 KB: `battle` (its id, 1 to 64 letters, digits, `_` or `-`), `seq` (the report's number, rising within the battle), `delta` (the share of the max HP lost since the battle's last report, -1 to 1, negative for healing), `max` (the reporting game's raid max HP, which only the first report of a pool sets, at most 1e18) and `killed` (the boss died in the reporting game, which empties the pool). A `seq` the battle reported already counts nothing (`repeat`), so a report sent again counts once, unless 32 newer battles reported on the pool since. A report on a defeated boss, or one that takes nothing off, changes nothing. Answers `boss`, the pool, and `repeat`. 400 for a body that is not as it should be, an old `dealt` body too; 413 with `code` `full` past 500 pools; 429 with `code` `rate` past 30 reports at once, then two a second, per player. |

**Admins** (the `ADMINS` setting) look after a Raid World from outside the game. Each route takes an admin's key in `X-MGQ-Player`; 403 for everyone else, the creator included, 404 with `code` `classic` for a Classic world.

| Request | What it does |
|---|---|
| `GET /v1/worlds/<id>/raid` | Hands out the world's track as `story`, which starts from the keyed story an older game wrote when no game played the world on tracks yet: `tracks` true, `rev` and `wrev` the track's revision, the counters read from its keys, `part`, `route` (the route lock), `done`, `checkpoints` and `at` (when the track last changed) from its summary, `comps`, `end` and `caps` from the keyed story, and with `?keys=1` `keyed` true and the track's `keys` as lists (`s`, `sf`, `v`, `ss`, `ssf`, `a`, `f`; `f`, the frozen raid boss fights, holds one key per troop, separated by semicolons, and `<troop>|0` once a fight ended). With the story come `pins` (`keys`, each pinned key to its value as an admin names it, such as `{"s12": true, "v1201": 5}`, and `rules`, the ranges an older relay pinned at off, such as `v1201-1218`), every pool with `hp` (the HP left now), `reports` and `byPlayer` (the id of the player whose report emptied it) besides what the players see, and `regenPerMinute`. |
| `POST /v1/worlds/<id>/raid/bosses/<key>/reset` | Deletes a pool, so it is full again and its defeat taken back; the next report sets its max again. |
| `POST /v1/worlds/<id>/raid/keys` | Sets keys of the world's track by id: `s` (switch ids to `true` or `false`), `v` (variable ids to a whole number, a decimal, a text, `true` or `false`, kept as the games write them) and `ss` (`"<map>.<event>.<letter>"` to `true` or `false`), 1 to 2000 keys in all, the body up to 128 KB. The keys that change go on the world's track as a revision every game on it hears as a `push` (see Story tracks): counts, the part, the route lock and the checkpoints follow as for a write, players on it whose level does not open the gate of a part it leaves fall behind, and the tracks of players behind stay as they are. Answers the world's track as the admin view shows it with `set`, the lists of the keys that changed; only keys the story mapping keeps on tracks go in: 409 with `code` `mapping` and `keys` for keys each player keeps, scenes, chest flags and counts, 409 with `code` `pinned` and `keys` for keys pinned at other values, and 400 for a body that is not as it should be or a self switch named with leading zeros. The relay logs every change as `world <id>: admin <id> set keys of rev <n>: <lists>`. |
| `POST /v1/worlds/<id>/raid/pins` | Pins keys at values: `keys`, each key as the story names it (`s<id>`, `v<id>`, `ss<map>.<event>.<letter>`) to its value as for `.../raid/keys`, 1 to 2000 at once, at most 5000 pinned in all (413). The keyed story keeps the pins, and the world's track takes their values as a revision every game on it hears; a key pinned again takes its new value. No later write changes a pinned key, and `.../raid/keys` refuses another value for it with 409 `pinned`. Answers the world's track as the admin view shows it, with `set` and `pins`. Only keys the story mapping keeps on tracks are pinned, counts among them: 409 with `code` `mapping` and `keys` for keys each player keeps, scenes and chest flags, and 400 for a self switch named with leading zeros; a refused request pins nothing. Logged as `admin <id> pinned <keys>`. |
| `POST /v1/worlds/<id>/raid/pins/clear` | Takes pins off: `keys`, the pinned keys, or rules an older relay kept, each named as the admin view shows them. The keys keep their values until a write changes them. Answers `cleared` (what it took off) and `pins`; 409 with `code` `none` for a world without a story. Logged. |
| `POST /v1/worlds/<id>/raid/bosses/kill` | Defeats bosses for the world at once, such as every enemy of a troop: `keys` (1 to 500 pool keys as the games name them, not percent-encoded) and `max` (the raid max HP by key, more than 0 and at most 1e18), which a pool no game reported yet needs, since no game named its max; 400 naming those keys when `max` lacks them, and nothing changes. Each pool named is emptied with `by` `Admin` and `byPlayer` the admin's id, as a game's killing report would; a pool defeated already stays as it was. Answers `bosses`, every pool named as the admin view below shows it. Every game in the world room hears a `boss` frame for each pool it defeated, and so does every server battle of the world; a game then wins that boss's battle at once and the world overview shows it beaten. 413 with `code` `full` when the new pools would pass 500. |
| `POST /v1/worlds/<id>/raid/route/clear` | Takes back the route locked at the Great Decision on the world's track, so the next player who chooses sets it again, which every game on it hears as a `push` with the world's summary, and answers the world's track as the admin view shows it with `cleared` (false when no route was locked). Refused with 409 and `code` `started` while the world's track is on the locked route, since another route locked then would turn away every write of both routes. |

### Server battles

A co-op battle of two or more players goes to the relay's battle server (see [BattleServer/README.md](../BattleServer/README.md)), which hosts it with the game's own battle code; every player plays it back over a channel of the battle's own, which carries that battle's messages in plain text, so the server reads that battle alone and the world room stays end to end encrypted. The relay's battle server is named by `BATTLE_SERVER` (`host:port`); without one every request answers 503 with `code` `no_server`, and the starter's game hosts the battle as before. The routes take the player's key and the auth key in the headers, as the world room does.

| Request | What it does |
|---|---|
| `POST /v1/worlds/<id>/battles` | Starts a battle on the battle server: `battle` (its id, 1 to 32 of `0-9a-z`), `seats` (the world seats of its players, 1 to 16, each seated in the world room now, the starter among them) and `setup` (what the server needs, in base64, at most 1,000,000 characters). Answers 201 with `battle` and `seat` (250, the server's seat on the channel) once the server took it; 503 with the server's refusal (`setup`, `scripts`, `data`, `mods`, `busy`, `timeout` after 5 s), `no_server` from a relay without a battle server or one that cannot reach it, 409 `seats` for a seat nobody sits on, 403 for a starter who is no player of it, 429 `rate` past 10 battles at once and one more every 6 s per player, 503 `full` past 16 battles of a world. |
| `wss://<relay>/v1/worlds/<id>/battles/<battle id>` | A player's channel of the battle, for its players and those the server took in later: told `seat <world seat>`, then every binary message from the server with the server's seat (250) in front; a player sends binary messages to seat 250 alone (any other closes the channel with 4000). `ping` is answered with `pong`. Before the end the relay sends `closed <why>` (`ended`, `server`, `arrive` when no player came within 60 s, `expired` after 2 hours, `deleted`) and closes the channel. A request for a battle that ended within the last 60 s gets 404 with how it ended in `X-MGQ-Refusal`. |

Between the relay and the battle server one TCP connection per battle carries JSON lines: the relay's `serve`, `in`/`out` as players come and go, `message` (a player's message in base64), `boss` (a Raid World's boss pool) and `close`; the server's `serving` or `refused`, `send` (to a seat, -1 for every player), `boss_report` (what the battle did to a boss pool, which the relay counts as the starter's report and answers with the pool, and passes every other change of the world's pools on), `admit` (seats the battle takes in late, whose players may come onto the channel then) and `end`.

### Raid designs (Node only)

The Raid Designer and its `raid-designer` CLI keep one shared Raid design on the relay, split into entities (`rules`, `catalog`, `tier:<n>`, `boss:<32 hex>`, `skillDefault:<skill>`, `customSkill:<32 hex>`, `map:<n>`, `tileset:<n>`, `state:<n>`, `bossFight:<troop>`). The relay stores each entity's body as it comes and never reads it; the contract, with every body and exchange, is `docs/SERVER_FORMAT.md` in the MGQ-Online-Raid-Designer repository, and `core/fixtures/designs/` holds a copy of its fixtures, which the tests replay.

- **Designers:** a designer names its key in `X-MGQ-Designer` (32 lowercase hex characters), its version in `X-MGQ-Designer-Version` (`0.0.0-dev` for a development build) and its design format in `X-MGQ-Design-Format`. Its id is the first 32 hex characters of the SHA-256 of `mgqmp designer <key>`, never a player id. The relay serves the designers its `designers` table lists; `DESIGNER_ADMINS` (designer ids, separated by commas) adds the designer admins the table lacks on every start, under the start of their id until they rename themselves; a listed designer keeps its row, so a demoted admin stays demoted.
- **Gate:** an unlisted key gets 403 `not_designer`; a version below `DESIGNER_MIN_VERSION` (every version unless set) or a design format below the relay's lowest gets 426 `update` with `minimum` and `minFormat`, except on `me`, `release` and `release/file`, which a listed designer of any version reaches, so an outdated designer can always update itself; a designer who is no admin gets 403 `admin_only` on an admin route (builds, publish, rollback, format); a relay admin passes on the designer list and on `format` only; a development build writes (push, builds, publish, rollback, format) only as a designer admin, or as anyone with `DESIGNER_ALLOW_DEV=1` on a local test relay (403 `dev_build` otherwise). The game gate of Versions does not apply to these routes.
- **Push rule:** a push is all or nothing. A change whose stored rev differs from its `baseRev` (0 for an entity that must not exist yet) comes back in a 409 `conflict` with the stored entity; a lower schema than stored gets 409 `schema`; more than 20 deletes need `confirmDeletes` from a designer admin (409 `deletes`). A delete keeps a tombstone; a delete of what is missing or deleted changes nothing. Every entity of a push gets the push's `seq` as its rev, and each entity keeps its last 50 revisions. A push from a released designer raises the design format and the lowest format to its `designFormat` when that is the next format and its `X-MGQ-Design-Format` names it too; any other push is taken without raising them. Pushes are limited to 30 at once and then one every 2 seconds per designer (429 `rate`), a push to 2 MiB and 200 changes, one body to 256 KiB (413 `too_big`).

| Request | What it does |
|---|---|
| `GET /v1/designs/me` | Any key: its `id`, and for a listed designer `name`, `designer`, `admin`, `seq`, `designFormat`, `minFormat` and `minVersion`. |
| `PUT /v1/designs/me` | Renames a listed designer: `{name}`. |
| `GET /v1/designs/entities?since=<seq>&after=<id>&limit=500` | The entities changed after `seq`, sorted by id, a page of up to 500, with `next` (the id to pass as `after`) while more follow; `since=0` leaves tombstones out. |
| `POST /v1/designs/push` | `{designFormat, message, confirmDeletes?, changes: [{id, kind, schema, baseRev, body}]}`, `body` null to delete; answers `{seq, accepted: [{id, rev}]}`. |
| `GET /v1/designs/entities/<id>/history?limit=50` | An entity's revisions, newest first. |
| `GET /v1/designs/designers` | The designers with `online` and what each edits, for designers and relay admins. |
| `PUT /v1/designs/designers/<id>` | Adds a designer or changes its `name` and `admin`, for designer admins and relay admins (an `X-MGQ-Player` key whose id is in `ADMINS`); a relay admin may do nothing else here. |
| `DELETE /v1/designs/designers/<id>` | Removes a designer, for the same; its sockets close with 4403. |
| `POST /v1/designs/builds` | `{seq}`, the current seq: starts a build, for designer admins; answers 202 `{build: {id, seq, status: "queued"}}`, 409 `moved` with the current `seq` for another seq, 503 `compiler` with a `message` while the relay cannot build. |
| `GET /v1/designs/builds` | `{live, previous, builds}`: the live and the previous build's ids (null for none) and the newest 20 builds with the live and the previous one, newest first, each `{id, seq, status, format, marshalSha, runtimeSha, snapshotSha, report, by, at}`. |
| `GET /v1/designs/builds/<id>` | The same with that build alone in `builds`; 404 `none` for a build the relay does not hold. |
| `GET /v1/designs/builds/<id>/snapshot` | The build's snapshot, gzipped (`application/gzip`), to tell what changed since; 404 `none` without one. |

A designer sends `{"op": "editing", "entity", "path"}` (nulls for nothing), told on at most once a second; what it edits is forgotten after 60 seconds without another, and once its last socket closes. The relay pings every 30 seconds and closes a socket that did not answer the last ping; a frame over 4 KB closes the socket. A designer pulls `since=<last seq>` on every connect, so a missed frame never matters.
- **Releases:** with `DESIGNER_GITHUB_TOKEN`, `DESIGNER_RELEASE_PUBKEY` and `DESIGN_DATA_DIR` set, the relay reads the latest release of `DESIGNER_REPO` at start and every 10 minutes with the token, which never leaves the server, downloads `RaidDesigner-<v>-win-x64.exe`, `RaidDesigner-<v>.manifest.json` and its `.sig`, checks the manifest's ECDSA P-256 signature and the exe's SHA-256 against it, and keeps the exe in `DESIGN_DATA_DIR/releases`; a new one goes out to the designers online as the socket's `release` frame. The designer checks everything again. It logs a warning from 30 days before `DESIGNER_GITHUB_TOKEN_EXPIRES`.
- **Builds:** with `DESIGN_COMPILER`, `DESIGN_GAME_DATA` and `DESIGN_DATA_DIR` set, a build keeps the snapshot of the design at its seq (every entity but the tombstones, sorted by id, canonical JSON) in `DESIGN_DATA_DIR/work/<build id>`, then waits on a queue that compiles one build at a time, outside the lock pushes take, so designers push on while it compiles. It runs `DESIGN_COMPILER compile --snapshot … --game DESIGN_GAME_DATA --out … --seq <seq> [--previous <the live build's runtime.json>] --json` for at most 180 seconds. Before the first compile, and again whenever the binary changed, it runs `--version` and `preflight` (once for builds that start together) and refuses with 503 `compiler` while the compiler's design format is below the lowest format or the game data is missing. Exit 0: the relay checks every file against the SHA-256 the report names, keeps them gzipped as blobs and the build `ok`; exit 2: `refused` with the compiler's report; anything else, a timeout, a file unlike its report or a result the relay could not keep: `failed`, with `failure` in the report. Statuses: `queued`, `compiling`, `ok`, `refused`, `failed`; a restart fails the builds it cut off. Builds are limited to 3 at once and then one every 5 minutes, publishing and rolling back together to 3 at once and then one a minute, per designer (429 `rate`); a request refused as invalid (400) counts against neither. The ten-minute sweep keeps the newest 20 builds, the live and the previous one, and drops the blobs no build names.
- **World notice:** while `DESIGN_WORLD_NOTICE=1`, a publish also sends every world room the text `raid_design <marshal sha256> <runtime sha256>` and ends the pool of each boss key its `catalogDiff` names as removed or renamed (by the old key) in every Raid World, telling their games as an admin's reset does; a rollback sends the text alone. These notices go out one after another in the order the builds went live, also when publishes race. It stays off (the default) until a released game reads compiled format 3.

| Request (games and the battle server) | What it does |
|---|---|
| `GET /v1/raid-design` | With `X-MGQ-Features` and `X-MGQ-Design-Reader: <the highest compiled format the game reads>`: `{buildId, format, seq, marshal: {sha256, size}, runtime: {sha256, size}, at}` of the live build, or of the previous one when the game cannot read the live one's format; 404 `none` when it reads neither. `size` counts the bytes before gzip, `at` is when the build was made. |
| `GET /v1/raid-design/<sha256>` | A live or earlier build's `RaidDesign.rvdata2` or `runtime.json`, gzipped as kept (`application/gzip`, no `Content-Encoding`), with `Cache-Control: public, max-age=31536000, immutable` and `ETag: "<sha256>"` (304 for a matching `If-None-Match`); the reader gunzips it and checks its SHA-256. 20 at once and then one every 30 seconds per address (429 `rate`), requests from this machine, such as the battle server's, not counted; 404 `none` for any other hash. |

### World rooms

- **Connect:** `wss://<relay>/v1/world/<world id>?name=<name>`, with the player's key in the header `X-MGQ-Player` and the auth key in the header `X-MGQ-Auth`; keys in the address count for nothing. The relay lets the game in only if the world is in the directory, the SHA-256 of the auth key is the world's `authHash`, and the creator has not removed the player: otherwise HTTP 404, 401 or 403 before the WebSocket opens, HTTP 409 while the creator is still uploading the starting save. A game without `X-MGQ-Features`, or too old by its version, gets HTTP 400 with the code `update` before any of these checks, see Versions. Any other 400, a 403 or a 409 names why in the response header `X-MGQ-Refusal`, with the codes of the directory. Entering world rooms is limited per address, 30 at once and one more every 2 seconds (HTTP 429). When a player enters a world room again, the relay closes the player's earlier connection with 4009 and the reason `replaced`. The world's seats come from the directory; once every one is taken, the next game gets HTTP 409. After every change the room tells the directory who is in it.
- **Seats:** a game takes the lowest free seat, from 0. It is told `seat <own> <others…>`, the seats already taken in ascending order, such as `seat 2 0 1`. The others are told `in <seat>`, and `out <seat>` once it leaves.
- **Messages:** a game sends a binary message as its target seat, or 255 for everyone, followed by the payload. The relay passes it on with the sender's seat in place of the target, so the receiver knows who sent it. A message for a free seat is dropped.
- **Chat:** the games send each other their lines encrypted, as any message. The relay keeps a plain copy of the global chat for the admins:
  - After every global line, a game sends the text `chat <line>`. The relay keeps it in the world's chat (`GET /v1/worlds/<id>/chat`) with the sender's player id and name, and passes it to nobody.
  - Each connection may send 2 chat lines a second, after a burst of 10. The relay drops a line beyond that and answers the text `slow chat`; games that don't know it ignore it. A `chat` text without a line is ignored.
  - When an admin says something (`POST /v1/worlds/<id>/chat`), the relay sends the text `chat <name>` + tab + `<line>` to every game in the room; games that don't know the frame ignore it.
- **Story:** after the shared companions change the relay sends every game in the room the text `story <rev>`, which the games fetch; games that don't know a frame ignore it.
- **Bosses:** after every change of a Raid World's boss pool (a report that changed it, an admin's reset of a pool there was, an admin's kill) the relay sends the text `boss <left> <max> <defeated> <key>` to every game in the room: the share of the max HP left now with up to 6 decimals (at least `0.000001` while the boss stands), the raid max HP as a whole number, `1` when the boss is defeated, else `0`, and the key last, since it may hold spaces and `#`, such as `boss 0.25 5000000 0 Metatronne and Sandalphone#1`; a reset sends a share of 1. Games that don't know it ignore it.
- **Difficulty:** after an edit that changes a Raid World's `difficulty`, the relay sends the text `difficulty <n>` to every game in the room; games that don't know it ignore it.
- **Squad:** after an edit that changes a Raid World's `squad`, the relay sends the text `squad <luka> <formation> <front> <raidFront>` to every game in the room, `luka` 1 when Luka may be replaced, else 0, such as `squad 1 6 2 1`; games that don't know it ignore it.
- **Raid bosses:** after an edit that changes a Classic world's `raidBosses` (a world without it counts as `false`), the relay sends the text `raid_bosses <0|1>` to every game in the room, 1 when the world fights raid bosses; games that don't know it ignore it.
- **Mods rule:** after an edit that changes `otherModsOff` or `mods` (compared as kept, a world without `otherModsOff` by its type), the relay sends the text `mods_rule <0|1>` + tab + `<the world's mods>` to every game in the room, 1 when the world turns other mods off; the mods never hold a tab or a line break. A game that now runs mods the world turns off leaves the world.
- **Mod settings:** every game takes the world's mod settings from the relay: right after its `seat` text it is told `mod_settings ` + tab + `<the world's settings>`, and after an edit that changes `settings` (compared as kept) every game in the room is told `mod_settings <creator|admin>` + tab + `<the settings>`, naming whether the world's creator or an admin changed them. Empty settings leave every player their own; the settings never hold a tab or a line break.
- **Limits:** each connection lasts at most a day on its own; the game then connects again. On Node a connection whose player is in a battle on the battle server is never closed for its age.

### Both

- The text `ping` is answered with `pong`, for keeping an idle connection open; any other text than `ping`, a world room's `chat` and, from a game playing a Raid World on tracks, `track` (see Story tracks) closes the connection. A `ping` and a `chat` text count against the message limits.
- At most 512 KB per message and 60 messages per second over time (bursts of 240), per connection.
- **Close codes:** 1012 the Node relay stops (reason `service restart`), 4000 bad request, 4002 message too large, 4003 too many messages, 4007 the world is full, 4008 the connection lasted too long, 4009 the creator removed the player, or the player entered from elsewhere (reason `replaced`), 4010 the world was deleted.

## Tests

You need Node.js 24 or later, since the SQLite stores and their tests use `node:sqlite`.

```powershell
cd Relay
npm install
npm test
```

Two tests need more than Node and skip without it:
- `node/backup.test.js` runs `ops/backup-relay.sh` with `sh` and the `sqlite3` program; `SQLITE3` names it when it is not on the PATH.
- `node/design_cli.test.js` imports a format 1 design with a real `raid-designer` binary, pushes it to a local relay, builds it through the same binary and publishes it: `RAID_DESIGNER_CLI` names the binary, `RAID_DESIGNER_GAME` the game folder it compiles against (only read) and `RAID_DESIGNER_FIXTURE` the design file, such as the Raid Designer's `RaidDesigner.Tests/Fixtures/Format1/test-install-2026-10-17.json`.

## Moving to a rented server

1. On the server, install Node.js 24 or later (the SQLite database needs `node:sqlite`) and [Caddy](https://caddyserver.com), and point a domain at the server.
2. Copy `core/` (with `core/story_ids.json`, which `core/story.js` and `core/story_tracks.js` need beside them), `node/`, `seed/`, `package.json` and `package-lock.json`, then run `npm install --omit=dev`.
3. Start `node node/server.js` as a systemd service, with these environment variables:
   - `MGQ_RELAY_DB=/var/lib/mgq-relay/relay.sqlite`: the SQLite database the worlds, their starting saves, the trades, the Raid Worlds' stories, their story tracks and their boss pools, the release control, the story mapping and the Raid designs are kept in, made on the first start (with its `-wal` and `-shm` files beside it, and `relay.design-seq`, the highest Raid design seq it handed out, which tells it a restored backup apart). Without it everything stays in memory and is gone with the process. Back the file up with `sqlite3 relay.sqlite ".backup copy.sqlite"`, never by copying it while the relay runs; `ops/backup-relay.sh` with its systemd timer does so every night and keeps 14 copies, see [ops/DEPLOY_DESIGNS.md](ops/DEPLOY_DESIGNS.md).
   - `ADMINS`: the admins' player ids, as above.
   - `GITHUB_ISSUES_TOKEN` and `GITHUB_BUG_FILES_TOKEN`, and `REPORT_ISSUES_REPO`, `REPORT_FILES_REPO` and `REPORT_FILES_BRANCH` unless the defaults fit: where the bug reports go, see above. Without both tokens the relay takes no reports.
   - `MIN_VERSION`: the lowest version a game may name while no admin set one, `0.7.1` unless set, see Versions and Release control.
   - `HOST` and `PORT`: where it listens, `127.0.0.1:8080` unless set.
   - `DESIGNER_ADMINS`, `DESIGNER_MIN_VERSION` and `DESIGNER_ALLOW_DEV`: the designer admins' designer ids, the lowest Raid Designer version served and whether development builds push as anyone (`1` only on a local test relay), see Raid designs. The design tables live in the same database, which the relay brings up to its newest step (`PRAGMA user_version`) as it starts.
   - `DESIGN_DATA_DIR`: the folder the designer releases (`releases/`) and the builds being compiled (`work/`) are kept in, such as `/var/lib/mgq-relay/designs`.
   - `DESIGNER_REPO`, `DESIGNER_GITHUB_TOKEN`, `DESIGNER_GITHUB_TOKEN_EXPIRES` and `DESIGNER_RELEASE_PUBKEY`: the designer's private repository (`Pauliinchen/MGQ-Online-Raid-Designer` unless set), a fine-grained token with Contents: read on that repository only, its expiry date (such as `2027-10-01`) and the PEM of the release key (line breaks may be written `\n`); without the token, the key or `DESIGN_DATA_DIR` the relay serves no designer releases.
   - `DESIGN_COMPILER` and `DESIGN_GAME_DATA`: the Raid Designer's self-contained linux-x64 CLI, such as `/opt/mgq-designer/current/raid-designer`, and the game folder it compiles against, `/opt/mgq-battle/game`; without either, or without `DESIGN_DATA_DIR`, builds answer 503 `compiler`.
   - `DESIGN_WORLD_NOTICE`: `1` makes a publish tell the world rooms and end the pools of removed and renamed bosses, see Raid designs; off unless set, until a released game reads compiled format 3.
   - `BATTLE_SERVER`: the battle server's `host:port`, such as `127.0.0.1:8095`, which hosts the co-op battles; without it the starters host them, see Server battles. Run the battle server beside the relay as root (its sandbox needs it) with a game folder holding the game's `Data`, MGQ Online and the Mod Framework, which downloads the worlds' mods from the website, see [BattleServer/README.md](../BattleServer/README.md).
4. The relay writes one line per request to stdout (`<time> <method> <path> <status> <ms> <address>`, the path without its query, so no key ever appears) and every error it catches to stderr, with its stack. Under systemd both go to the journal (`journalctl -u <service>`); the service file's `StandardOutput=append:/var/log/mgq-relay/relay.log` keeps them in a file instead. The rooms and the WebSockets live in memory, so a restart ends every connection; the games connect again on their own. On SIGTERM or SIGINT the relay ends the server battles, closes every WebSocket with 1012, waits up to 2 seconds and logs its start time and uptime; a second signal ends it at once. It logs every world connection and battle channel it closes, with the code.
5. On its own the relay closes rooms and connections whose time is up every minute, checks the mod's own releases every five minutes, and every ten minutes sweeps out worlds whose starting save never came, trades kept long enough and Raid design builds past the newest 20 with the blobs no build names, so the database does not grow with what nobody asks for again.
6. Have Caddy fetch the certificate and pass WebSockets on, with a `Caddyfile` like the one below. The relay counts its rate limits by the address Caddy appends to `X-Forwarded-For` last, for requests from this machine only.

   ```
   relay.example.org {
       reverse_proxy 127.0.0.1:8080
   }
   ```

7. Run one process. The rate limits per address are counted in memory, so several processes behind one proxy would each let an address have the full allowance, and the rooms are in memory too, so two games of one room must reach the same process. One Node process carries the relay's load with room to spare.
8. To move a relay to another server, stop it, copy its newest backup (`ops/backup-relay.sh`, see step 3) to the new server as its `MGQ_RELAY_DB` and start the relay there. A join code and a world code name their relay by id, so the id stays when its address changes.
