# Relay

Passes Monster Girl Quest! Online's frames between games. The games never connect to each other directly: many home connections cannot be reached from outside (DS-Lite, CGNAT, no IPv6, no forwarded port), but every one can connect out, so every game connects out to the relay.

The relay never sees what is played: the games encrypt every frame with a key derived from the join code or the world's token, which the relay never gets. For PvP battles it sees a room id, message sizes and timing, and stores nothing. For worlds it keeps the **world directory**, which everyone can read, but for hidden worlds, which only their players and whoever names their id see listed: each world's name, seats and creator, its description, the mods it needs and what tells its creator's game data from another's, the names of its players and who is online. It never learns a world's password or token: it keeps the token locked with the password, and checks a game that enters against a hash. A world may keep a **starting save**, which the games encrypt with a key from the token before it arrives, so the relay only keeps its bytes. The one thing of a world it reads is its **chat**: the games mirror every line of the world's chat to it in plain text, so the relay's admins can read the chat and say something in it from outside the game; the map, party and whisper chats stay between their players.

## Protocol (v1)

A **room** pairs two games for a PvP battle. A **world room** seats up to 32 games that play in the same world.

### Versions

Every game from 0.6.0 names its features in the header `X-MGQ-Features` on its directory and mod catalog requests and world rooms, and newer ones name their version in `X-MGQ-Version` on these and on PvP rooms, such as `0.6.5` (`0.0.0-dev` for a development build). The World Admin tool names `admin` in `X-MGQ-Features` and `0.0.0-dev` in `X-MGQ-Version`. Before routing a request, the relay turns a game too old for it away:
- the world directory's and the mod catalog's routes (the Raid World admin routes included), the trades, the bug reports, a Raid World's story and boss routes and the world rooms need `X-MGQ-Features`, so games before 0.6.0 and builds of the World Admin tool before it named `admin` are refused;
- every one of these routes and the PvP rooms hold the version named in `X-MGQ-Version` against the lowest release an admin set (see Release control), else the setting `MIN_VERSION` (`0.6.0` unless set). An older version or one that is no version is refused. A request that names none counts as `0.6.4`, the last release that names none, so released games pass while `MIN_VERSION` is at most `0.6.4` and are refused once it is higher. Only the development stamp `0.0.0-dev` (with or without `+<commit>`) always passes, so the World Admin tool does too; another suffixed version such as `0.7.0-beta` counts by its numbers;
- a PvP room never needs `X-MGQ-Features`, since released games open PvP rooms without any header.

A refused world room gets HTTP 400 with the text `Update MGQ Online to play online.` and the code `update` in `X-MGQ-Refusal`: released games from 0.5.1 to 0.6.4 take a 400 with a code they do not know as final and show their own "The relay turned the request down. Update the mod.", while they would try a 426 again and again; newer ones show the text. A refused PvP room gets HTTP 426 with the same text in `X-MGQ-Refusal`; released games tell any refused PvP room as a relay out of reach, newer ones show the text. Any other refused request gets HTTP 426 with the text as `error` once its body is read and dropped, up to 16 MB or 60 seconds.

### Release control

Which release the games should run and the lowest one the relay serves, kept in the relay's database, so they outlast a restart and need no change of its settings. The relay's admins set both (see Relay admin); the gate holds every game to the lowest at once. Once the update watch (see Mod catalog) reads a latest release newer than the current one and newer than the latest it had read when the current one was set, the relay clears the current release back to null, so the games follow GitHub's latest again, keeps the lowest one and logs it: a rollback to an older release lasts until the next release is out.

| Request | What it does |
|---|---|
| `GET /v1/release` | Hands out `current` (the release the games should run, such as `0.6.8`, null while unset), `min` (the lowest release the relay serves: the one an admin set, else `MIN_VERSION`) and `repo` (the repository the games update from, `Pauliinchen/MGQ-Online`). Open to every game whatever its version and headers. Only the Node relay answers it. |

### Rooms

- **Connect:** `wss://<relay>/v1/room/<room id>?role=host` or `?role=guest`. The room id is 32 lowercase hexadecimal characters, the start of a hash of the join code's token.
- **Pairing:** one host and one guest per room. Another peer of a taken role is refused with HTTP 409 before its WebSocket opens.
- **Messages:** binary messages go to the other peer unchanged. Once both are in, the relay sends each the text `paired`.
- **Limits:** a peer waits alone at most 30 minutes, a room lasts at most 2 hours. A peer the relay closes leaves the room at once, which ends it for the other peer too.

### World directory

Plain HTTP with JSON bodies of up to 256 KB in general, and 413 beyond the size a route takes, on every route of the relay; a few routes take other sizes: a story write up to 300,000 bytes, the mod catalog's routes 8 KB (a mod's options 64 KB), a trade's commit, cancel and done 72 KB, and a boss report and an admin's request to a Raid World 4 KB. A world's id is 32 lowercase hexadecimal characters, the start of a hash of its token. A request names its player by the key in the header `X-MGQ-Player`, which wins over the `player` of its body or address, and a world's auth key by the header `X-MGQ-Auth`, which wins over the `auth` of its address; released games send both in the address, which is kept for them, and a key in an address ends up in logs. A refusal's body holds `error` and, where the games tell reasons apart, `code`: `removed`, `members` (the world has as many players as it may, 200), `pending`, `rate`, `storage` or `raid_unsupported` (a Raid World, which the game does not name in `X-MGQ-Features`). A route that does not exist is answered with 404.

| Request | What it does |
|---|---|
| `GET /v1/worlds?player=<key>&ids=<id>,<id>` | Lists every public world, and the hidden ones the player of `player` joined or `ids` names (up to 50 ids, which the worlds' creators hand out; without `player` and `ids`, public ones only), or every world for an admin. Answers `worlds`, each with the listed fields below, and `admin`, true for an admin. A game naming `0.6.8` or newer, or `0.0.0-dev`, in `X-MGQ-Version` gets each world without its `mods`, `modHashes` and `settings`, which may be long, and with `modsCount` instead; it reads them for the world it opens from `GET /v1/worlds/<id>`. Older games, a game naming no version, and the website and the World Admin tool (naming `web` or `admin` in `X-MGQ-Features`) get every world with them, as before. |
| `GET /v1/worlds/<id>?player=<key>` | Hands out one world as `world`, with every listed field below, its `mods`, `modHashes` and `settings` included, and `admin`, true for an admin. Naming its id is enough, as it is for a hidden world in the list; 404 for a world the directory lacks. |
| `POST /v1/worlds` | Makes a world from the fields sent on create below. 201, or 409 when the id is taken, 429 past 20 worlds per creator, a limit admins do not have, 503 past 2000 worlds in all, and 429 with `code` `rate` past 5 worlds at once and 10 an hour from one address, counting only requests no other refusal turned away. A world whose starting save has not come 10 minutes after it was made is deleted. |
| `GET /v1/worlds/<id>/lock` | Hands out the world's `lock` (`salt`, `iterations`, `box`), which only the password opens, with its `name`, `seats`, `start` and `choose`, so a hidden world is entered by its id. |
| `POST /v1/worlds/<id>/edit` | Changes whichever of `seats`, `description`, `mods` (400 past 16000 characters), `settings` (400 past 64000 characters), `otherModsOff` (400 for anything but `true` or `false`) a Raid World's `difficulty` and `squad` (400 for a Classic world) and a Classic world's `raidBosses` (400 for anything but `true` or `false`, and for a Raid World) the body names, if `player` is the creator's or an admin's key, and replaces `data`, the creator's game data, and `modHashes`, if it is the creator's or an admin's. An admin's edit also changes whichever of these it names: `name` (as at create; 400 for a name that is empty once tidied), `featured`, `hidden` and `strict` (400 for anything but `true` or `false`), `creator` (the id of a player of the world whom the creator did not remove, who becomes its creator under the name the world knows them by; 400 for anyone else) and `lock` (`salt`, `iterations`, `box` as at create, a new password; 400 for one that is not as at create) with `open` (`true` when the new password is empty, since the games enter an open world with the empty password; 400 for `open` without a `lock`). An edit by anyone else leaves these fields as they are, as it always did, so released games that send them change nothing. Everything else of a world stays as it was made. Running games learn of none of these admin fields: no frame carries them, and a game reads the world's name and seats from the list as it enters the world, the creator's powers in the game too; players who entered the world before keep its token, so a new password only asks those who enter it for the first time. A new `difficulty`, `squad` or `raidBosses` goes to every game in the world room as a text frame, and so does an edit that changes whether the world turns other mods off or its mods (see world rooms below); an edit that sends the values the world has already tells nothing. |
| `POST /v1/worlds/<id>/delete` | Deletes the world, if `player` is the creator's or an admin's key, and closes its world room. |
| `POST /v1/worlds/<id>/ban` | Removes the player whose id is `target` and keeps them out, if `player` is the creator's key. A world keeps at most 500 removed players (429 beyond). |
| `POST /v1/worlds/<id>/start?player=<key>` | Keeps the world's starting save, the body as bytes (at most 8 MB), if `player` is the creator's key and the world was made with `start: true`. Only once: 409 afterwards. 413 past 8 MB, 507 with `code` `storage` once all starting saves together would pass 1 GB, and 429 with `code` `rate` past 5 uploads at once and 10 an hour from one address. |
| `GET /v1/worlds/<id>/start` | Hands out the starting save as bytes, to a game the world room would let in, with the player's key in `X-MGQ-Player` and the auth key in `X-MGQ-Auth` (released games send `?player=<key>&auth=<auth key>` instead). 404 when the world has none. On Cloudflare it is one of the downloads the relay sends only a few of at once (see below). |
| `GET /v1/worlds/<id>/chat?after=<n>` | Hands out the world's chat as the relay saw it, if `player` is the creator's or an admin's key: `lines`, oldest first, each with `n` (its number, counting up), `at`, `player` (the sender's id), `name`, `text` and `admin` (true for a line said over this route). With `after`, only the lines numbered beyond it. The relay keeps the last 200 lines of each world, 200 characters each at most; the games mirror every line of the world's chat into it (see world rooms below), the map, party and whisper chats stay between their players. |
| `POST /v1/worlds/<id>/chat` | Says a line in the world's chat as an admin: `text` (1 to 200 characters) and `name` (the name the line carries, up to 32 characters; `Admin` when left out), if `player` is an admin's key (403 for everyone else, the creator included, who talks through the game). The line goes into the chat and to every game in the world room as a text frame. Answers the `line` as kept. |

**Admins** look after the directory: they see every world, hidden ones too, may delete any, and make the featured worlds. They cannot open a world's lock or enter it without its password. The relay reads their player ids from the setting `ADMINS`, separated by commas or spaces; without it there are none. On Cloudflare it is a secret, kept out of the repository: `npx wrangler secret put ADMINS --config cloudflare/wrangler.toml` sets it and deploys it at once. The Node server reads it from the environment variable of the same name. An admin's id is made from the key in their game's `Patch\Multiplayer\Player.ini`, as above.

### Relay admin

The relay's own routes for its admins (the `ADMINS` setting), such as the website's dashboard. Each takes an admin's key in `X-MGQ-Player`, or as `player` in the address (GET) or the JSON body (POST, up to 4 KB); 403 for everyone else. They need no `X-MGQ-Features`.

| Request | What it does |
|---|---|
| `GET /v1/admin/stats` | Hands out what the relay carries now: `startedAt` (ISO time), `uptimeSeconds`, `memory` (`rss`, `heapTotal`, `heapUsed`, `external`, in bytes), `worlds` (each world room open: `id`, `name`, `type`, `seats`, `players`), `rooms` (PvP rooms open), `players` (`worlds`, `rooms` and `total` connections), `versions` (the world rooms' games by the version they named in `X-MGQ-Version`, `unknown` for none, such as `{"0.6.7.7": 3}`), `battles` (`tracked`, the server battles the relay keeps, and `served`, those with a connection to the battle server) and `battleServer`, the battle server's answer to `{"op":"ping"}` as it sent it (`ok`, `boot_seconds`, `battles`, `busy`, `mode`, `pid`; in fork mode `battles` and `busy` are the child's own), null without a battle server or when it does not answer within 2 seconds. Only the Node relay answers it; Cloudflare's answers what it answers for any other address. |
| `GET /v1/admin/release` | Hands out the release control as `GET /v1/release` does, with `envMin` (what `MIN_VERSION` sets), `updatedAt` (when an admin last set it, in milliseconds since 1970, null before) and `updatedBy` (that admin's player id). Only the Node relay answers it. |
| `POST /v1/admin/release` | Sets `current`, `min` or both, each a version of 1 to 4 whole numbers separated by dots, or null to clear it back to its default (none for `current`, `MIN_VERSION` for `min`); one left out stays as it is (400 for a body naming neither, or a value that is no such version). A lowest release above the current one, `MIN_VERSION` counting while no `min` is set, is refused with 400 and `code` `min_above_current`. Answers as `GET /v1/admin/release`. The gate holds every request after it to the new lowest release; games already in a room stay. The relay logs each change with what it replaced. Only the Node relay answers it. |
| `POST /v1/admin/announce` | Says `text` (1 to 120 characters once control characters are taken out, the most released games show of a chat line; 400 otherwise) in the chat of every world with players online, as the update notice is said: an admin's line named `MGQ Online` that every game in those world rooms hears as `chat MGQ Online` + tab + the line and the world's admins see in its chat. Games from 0.6.5 on show it red as `// <line> //` in every chat tab, older ones as `[Admin] MGQ Online: <line>`. Answers `text` as said and `worlds`, in how many it was said. The relay logs each line. Only the Node relay answers it. |

### Mod catalog

The mods a world may require and games may download. Only admins add them: a single script or a zip laid out as in the game's `Patch` folder, by a link to a release on `https://github.com/Pauliinchen/`, the same for every version, or a mod of several files that an admin uploads. The relay keeps a link mod's hashes and version only, never the file, and checks every link for a new release: on Node half a minute after a start and then every five minutes, downloading a file only when the link leads to a release it has not read yet; on Cloudflare every half hour by a cron trigger. Adding or changing a link always reads its file. A link such as `.../releases/latest/download/Mod.rb` (or `Mod.zip`) must lead to `.../releases/download/<tag>/Mod.rb`, whose tag (without `v`) is the version, and that file may only come from GitHub's file hosts, a script at most 2 MB, a zip at most 16 MB with at most 100 files of 64 MB in all, each a path inside `Patch` (plain or deflated; backslashes are read as slashes, and a `Patch` folder at the top of the zip as `Patch` itself). A script's hash is the SHA-256 of its bytes without carriage returns; any other file's of its bytes. The catalog also tells which mods are **personal**: the games keep them on in a world that turns other mods off (`otherModsOff`), whether the world names them or not. An admin marks any mod personal, or adds one by its name alone, with nothing to download.

**Update notice.** Every five minutes (a second cron trigger on Cloudflare, a timer on Node) the relay reads where `https://github.com/Pauliinchen/MGQ-Online/releases/latest` leads (`RELEASE_REPO` names another repository), which needs no GitHub API. The first release it ever reads is only kept; each newer one is said once, as `MGQ Online <version> is out. Restart the game and pick Multiplayer to update.`, in the chat of every world with players online, as an admin's line named `MGQ Online` that the world's admins see in its chat too. Games from 0.6.5 on show it red as `// <line> //` in every chat tab; older ones as `[Admin] MGQ Online: <line>`.

| Request | What it does |
|---|---|
| `GET /v1/mods?player=<key>` | Lists the mods: `mods`, each with `key` (the name in lower case without `.rb`, spaces, underscores and hyphens), `name`, `kind` (`link`, `upload` or `name`), `personal` (true for a mod the games keep on in worlds that turn other mods off), `version`, `files` (each file's hash by its name, for an upload by its path inside `Patch`), `versions` (up to 20 earlier `version` and `files`, newest first) and `fileUrl` (a link mod's release file), `archive` (true when that file is a zip, whose files go to their paths inside `Patch`), `options` (the Mod Config options an admin's game sent, see below) and `optionsVersion` (the version they came from, empty before any arrived); for an admin also `link`, `size`, `checked` and `error` (why the last check failed, the last good version kept); `admin`; and `personal`, every mod marked personal as `key` and `name`, by name, whether checked or not, name entries included. A link never read successfully (no version, no files) and a `name` entry, which has nothing to download, are listed in `mods` for admins only. In every `<key>` below the key is percent-encoded, and a JSON body longer than its route takes (8 KB, the options 64 KB) is answered with 413. |
| `POST /v1/mods` | Adds a link mod or changes its link: `player` (an admin's key), `name` (400 when it holds `:`), `link`. Checks it at once and answers the `mod`; 409 when the mod was removed while its link was checked. A mod that the link replaces stays listed until the check is done. |
| `POST /v1/mods/check` | Checks every link mod now, if `player` is an admin's key, and answers the list. |
| `POST /v1/mods/<key>/upload?player=<key>&name=<name>&version=<version>` | Keeps a mod of several files, if `player` is an admin's key. The body: one `path<TAB>hash` line per file (paths inside `Patch`, at most 100), an empty line, then the zip; at most 16 MB. The relay hashes the zip's files itself and keeps those hashes; a file list that names other files or hashes is refused with 400, and so is a `name` that holds `:`. |
| `POST /v1/mods/<key>/options` | Keeps the mod's Mod Config options, if `player` is an admin's key: `version`, the version the game's copy is (empty for a copy matching no version the catalog knows, kept as `?`), and `options`, at most 100, each with `key` (the option's symbol), `name`, `type` (`i`, `f`, `b`, `y` or `s`, as in a world's `settings`), `default` and `choices` (at most 64, each `value` and `name`). The newest version's options are kept, by the order of `versions`: the current version's for good, an older one's only until a newer one's arrive, and a copy of no known version's only until a known version's arrive; options older than those kept are answered with `kept` false and change nothing. Only a running game can read them, since mods build their options when they load; the World Admin tool lists them. The body may be up to 64 KB. |
| `POST /v1/mods/<key>/personal` | Marks a mod personal or takes the mark off: `player` (an admin's key) and `personal` (`true` or `false`); 403 for everyone else, 404 for a mod the catalog lacks, 400 for anything but a boolean. Answers the `mod`. The mark stays when the mod's kind changes between `link`, `upload` and `name`. |
| `POST /v1/mods/<key>/name` | Adds a mod by its name alone, of kind `name`, or renames one: `player` (an admin's key) and `name` (up to 32 characters without `:`, whose key must be `<key>`; 400 otherwise). Such an entry has no link and no files, is never checked and is personal when made; it exists for mods the catalog hands out no copy of, such as someone else's cosmetic mod. 409 when a `link` or `upload` mod has that key: mark that one personal instead. Answers the `mod`. A link or upload added under the same name later takes its place and keeps the mark. |
| `GET /v1/mods/<key>/file` | Hands out an uploaded mod's zip as bytes; 404 for any other kind. On Cloudflare it is one of the downloads the relay sends only a few of at once (see below). |
| `POST /v1/mods/<key>/delete` | Removes a mod of any kind, if `player` is an admin's key. |

### Trades

Two players of a world swap items through their games, and the relay referees the swap, so a disconnect or crash never copies or loses anything. Each game commits a hash of the offers both games agreed on; the relay marks the trade committed once both hashes match, in one write, and only then do the games apply it. The offers travel sealed with a key from the world's token, so the relay keeps their bytes only, for a game that crashed before it applied the trade to fetch again. A trade's id is 32 lowercase hexadecimal characters, which the games make.

| Request | What it does |
|---|---|
| `POST /v1/trades/<id>/commit` | Commits one side: `player` (the key), `world`, `partner` (the other player's id), `hash` (SHA-256 of the offers, hexadecimal) and `sealed` (the sealed offers in base64, at most 64 KB; 413 beyond). Both players must be players of the world, whom the directory lists as members and the creator has not removed (403 otherwise; the creator always is one). The first commit makes the trade `pending`; the partner's commit with the same hash makes it `committed`, a different hash `cancelled` with `reason` `differ`. The same commit again changes nothing; other offers from a player who committed already, or a commit naming another world or partner than the trade's, get 409. A player may open at most 20 trades that are pending or committed and not yet done, and at most 100 a day that end cancelled (429). Answers `state` and, when cancelled, `reason`. |
| `POST /v1/trades/<id>/cancel` | Cancels a pending trade with `reason` `cancelled`, if `player` is the key of one of its two players. A committed trade stays committed. Answers `state` and `reason` as above. |
| `GET /v1/trades/<id>?player=<key>` | Answers `state` and `reason` to one of the trade's two players, 404 to anyone else. A trade still pending 2 minutes after its first commit is cancelled with `reason` `expired`. |
| `GET /v1/trades?player=<key>&world=<id>` | Lists the world's committed trades the player has not marked done: `trades`, each `id`, `hash` and `sealed`, the offers as the player's own game sealed them. |
| `POST /v1/trades/<id>/done` | Marks a committed trade done for `player`, whose game applied and saved it (409 for a trade not committed). The trade is deleted once both players marked it done. |

Committed trades nobody finished are dropped after 30 days, cancelled ones after a day. The relay keeps each player's sealed offers beside the trade, not in it, and drops them as soon as the trade is cancelled.

### Bug reports

A player reports a bug from the game. The relay commits the report as a folder of plain files, `reports/<id>/` with `report.md` as its index, in one commit to the branch `REPORT_FILES_BRANCH` (default `main`) of the private `REPORT_FILES_REPO` (default `Pauliinchen/MGQ-Online-Bug-Reports`), so a report reads in the browser or after a `git pull`. Then it opens a public issue in `REPORT_ISSUES_REPO` (default `Pauliinchen/MGQ-Online`) with the player's title and text and a few public facts, linking `report.md` and the screenshot, which only the developer can open. It takes reports only with two GitHub tokens (secrets on Cloudflare): `GITHUB_ISSUES_TOKEN`, which may write issues in the issues repository, and `GITHUB_BUG_FILES_TOKEN`, which may write contents in the files repository alone, so no token of the relay can change the public repository the mod updates from. The relay keeps nothing of a report; it unpacks the text files and passes the screenshot's base64 to GitHub as sent. It handles one report at a time and reads a report's body for at most 60 seconds. On Cloudflare the reports go to a Durable Object of their own, so a large report never takes the memory the world directory needs.

| Request | What it does |
|---|---|
| `POST /v1/reports` | Takes a report from the player whose key is in `X-MGQ-Player`. The body, at most 15 MB: one line of JSON, a line break, then the base64 of each file in the order the JSON lists them, with nothing between them. The JSON (at most 16 KB): `title` (1 to 100 characters on one line), `text` (1 to 4000 characters), `version` (1 to 32 letters, digits, `.`, `+` or `-`), `facts` (at most 12 `[label, value]` pairs on one line each, the label 1 to 32 characters, the value up to 120) and `files`, 1 to 32, each with `name`, `length` (the characters of its base64, a multiple of 4; together they add up to the rest of the body) and `gzip` (`true` or `false`, false unless given). A name is up to 120 characters, a file or a folder and a file, each starting with a letter or digit, then letters, digits, spaces and `._()+-`, and no two alike whatever their case. `report.md` is required; `screenshot.png` is the one binary file, never gzipped, at most 4 MB of base64; every other file ends in `.md`, `.log` or `.txt` and is text, unpacked from gzip when flagged and read as UTF-8, at most 8 MB each and 24 MB together unpacked. Answers 201 with `issue` (its number), `url` and `id` (the report's, `<UTC day>-<8 hexadecimal characters>`); 400 for a body that breaks a rule, a gzip stream that does not unpack or a body still arriving after 60 seconds, 401 with `code` `player` without a player key, 413 for a body or file over its limit, 429 with `code` `rate` past 3 reports a player an hour, 10 a player a day or 6 an address an hour (a report refused for its body or a gzip stream counts against none); the relay answers 401, 429 and both 503s before it reads the body, which it then reads to its end and drops, 503 with `code` `off` without both tokens, 503 with `code` `busy` while the relay handles another report, and 502 with `code` `github` when GitHub refused or could not be reached, whose status the relay logs per step. |

The commit goes through GitHub's Git Data API: the relay first checks that every text file unpacks within its limits, so a refused report leaves nothing on GitHub, then uploads the screenshot and every text file over 64 KB as a blob of its own, also the small ones once the inline texts would pass 1 MB together; the other text files go inline in a tree on the branch's head, the commit `report <id>: <title>`, then the branch moved to it; when another report moved the branch meanwhile, the relay commits again on the new head with the blobs it uploaded, 3 tries in all. The issue is titled `[In-game] <title>` and labelled `in-game report` (left off when GitHub refuses the label); every `@` in the title, text and facts gets a zero-width space after it, so a report mentions nobody.

### World story

A Raid World plays one story, which the relay keeps beside the world room, on Cloudflare in the world room's own object: the counters it reads to tell which story is further (`p` for variable 1001, `r1141`, `r1142`, `r1143`, the finished routes, the story teleport's endpoint, the shared companions) and the story itself key by key, each switch, variable and self switch the games share, so it pushes what each write changed to every game at once. Released games (0.6.6 and before) keep the story sealed with a key from the world's token instead, which the relay only keeps; the first game naming `keys` in `X-MGQ-Features` that opens a world's sealed story writes it as keys, and from then on the relay sends games that do not name `keys` to update for that world (426 with `code` `update` at the story routes, 400 `update` at the world room). Classic worlds keep none (404, code `classic`). The routes take the player's key and the auth key in the headers, as the world room does, and answer the world's players only. The full contract is in [docs/DEVELOPER.md](../docs/DEVELOPER.md#world-story-on-the-relay-raid-worlds).

| Request | What it does |
|---|---|
| `GET /v1/worlds/<id>/story` | Hands out the story: its revisions, counters, part, locked and finished routes, endpoint, shared companions, checkpoints, and `keys` (with `keyed`: the lists `s`, `sf`, `v`, `ss`, `ssf`, `a`, `f`; `f`, the frozen raid boss fights, holds one key per troop, separated by semicolons, and `<troop>|0` once a fight ended) or the sealed `blob`. `?known=<rev>` answers a keyed story at that revision with `same` and without its keys. |
| `POST /v1/worlds/<id>/story` | Writes a keyed story: `base`, `counters` and `set`, the lists of the keys the write changed. Each key goes in unless a write after `base` changed it, which the first writer keeps; a frozen fight's end (`f<troop>` of `0`) is never replaced and goes in over a fight written since `base`. The answer names those in `kept` with the world's values, and `moved` tells whether other writes changed keys since `base`. Keys an admin pinned (see the admin routes below) stay out of the write, which takes the rest as if the write had not named them: the answer leaves them out of `kept`, so a released game takes its write as accepted whole and keeps the player's other keys, and when the write named another value than the world's for a pinned key, a second revision right after it, which changes no key in the store, sends every game `storyd` with the pinned values, which the writing game lays over its own story as it does another player's change. A base older than the writes the story remembers (the last 200), or a sealed story but its own revision, gets 409 `rev` with the world's story; a sealed write on a keyed story gets 409 `update`. A released game's sealed write: `base` (the revision it built on), `counters` and `blob` (the sealed story in base64, at most 280,000 characters). Taken when it built on the last write and its counters are not behind the story's; else 409 with the story and `code` `rev`, `behind` or `route` (while a route is locked, until the world returned from it, only a write on it or returning from it, finishing no route the world did not play; a write with no route under way also while the world's story has not started the locked route). A write with a route under way before the Great Decision (`p` below 40) is refused as `behind`; a story taken with one before is ranked as having none, and the next write repairs it: the route lock taken with it, its level caps and the checkpoint of the part it seemed to leave go. A write that first moves the world out of a part keeps the story before it as that part's checkpoint, which a later return to the part never replaces. |
| `GET /v1/worlds/<id>/story/checkpoint/<part>` | Hands out a part's checkpoint (`1`, `2`, `3`, `ad`, `mr`, `chaos`), 404 with `code` `none` for a part without one, or one a repair dropped. |
| `POST /v1/worlds/<id>/story/route` | Locks the route at the Great Decision: the first one wins (409 `route`, also while the world's story is on another route); a finished route (409 `finished`) and the third way before both others are finished (409 `closed`) are refused. |
| `POST /v1/worlds/<id>/story/companions` | Adds actor ids to the shared companions, which only grow. |

### Raid bosses

A Raid World's story bosses each have a pool whose HP the whole world shares, kept beside the story in the world room's own object. A pool keeps the share of the boss's raid max HP left, 0 to 1, with the max the first report named, since each game's difficulty and mods set the boss's max HP in its own game. It fills up again by 3% of its max a minute, also while battles fight it, and costs no writes for it: every read computes the share left now from the last report. The host of every battle fighting the boss reports what its players took off since its last report as each action ends, at most every two seconds, at each command phase and at the battle's end; the report that empties the pool defeats the boss for the world until an admin resets it. The routes take the player's key and the auth key in the headers, as the story's do, and answer the world's players only; Classic worlds keep none (404, code `classic`). A key may hold spaces and `#` (a boss of several enemies has a pool per enemy, such as `Metatronne and Sandalphone#1`) and is percent-encoded in the address, up to 72 characters; a world keeps at most 500 pools. The full contract is in [docs/DEVELOPER.md](../docs/DEVELOPER.md#raid-boss-pools-on-the-relay).

| Request | What it does |
|---|---|
| `GET /v1/worlds/<id>/bosses` | Hands out every pool a report touched (`bosses`, each with `key`, `left`, `max`, `defeated`, `at` and `by`) and `regenPerMinute`. `left` is the share left now; `by` names the player whose report emptied the pool. |
| `GET /v1/worlds/<id>/bosses/<key>` | Hands out one pool; a pool never reported is full, with `max` null. |
| `POST /v1/worlds/<id>/bosses/<key>/report` | Counts what a battle took off since its last report: `battle` (its id), `seq` (the report's number, rising within the battle), `delta` (the share of the max HP lost since the battle's last report, -1 to 1, negative for healing), `max` (the reporting game's raid max HP, which only the first report of a pool sets, at most 1e18) and `killed` (the boss died in the reporting game, which empties the pool). A `seq` the battle reported already counts nothing (`repeat`), so a report sent again counts once. A report on a defeated boss, or one that takes nothing off, changes nothing. Answers `boss`, the pool, and `repeat`. 400 for a body that is not as it should be, an old `dealt` body too; 413 with `code` `full` past 500 pools; 429 with `code` `rate` past 30 reports at once, then two a second, per player. |

**Admins** (the `ADMINS` setting) look after a Raid World from outside the game. Each route takes an admin's key in `X-MGQ-Player`, or as `player` in the address (GET) or the JSON body (POST); 403 for everyone else, the creator included, 404 with `code` `classic` for a Classic world.

| Request | What it does |
|---|---|
| `GET /v1/worlds/<id>/raid?player=<key>` | Hands out the story's counters without the sealed story and without a keyed story's keys (`story`), with `?keys=1` also `keyed` and, for a keyed story, `keys` (the lists as `GET .../story` hands them out), `pins` (`keys`, each pinned key to its value as an admin names it, such as `{"s12": true, "v1201": 5}`, and `rules`, the ranges an older relay pinned at off, such as `v1201-1218`), every pool with `hp` (the HP left now), `reports` and `byPlayer` (the id of the player whose report emptied it) besides what the players see, and `regenPerMinute`. |
| `POST /v1/worlds/<id>/raid/bosses/<key>/reset` | Deletes a pool, so it is full again and its defeat taken back; the next report sets its max again. |
| `POST /v1/worlds/<id>/raid/keys` | Sets keys of a keyed story by id: `s` (switch ids to `true` or `false`), `v` (variable ids to a whole number, a decimal, a text, `true` or `false`, kept as the games write them) and `ss` (`"<map>.<event>.<letter>"` to `true` or `false`), 1 to 2000 keys in all, the body up to 128 KB. The keys that change go in as a new revision, as a game's write does: the counters follow the keys (variable 1001, the route variables, the routes' clear switches), so the part, the route and the checkpoints move as they would for a write, `wrev` counts up and every game in the world room hears `storyd` with the keys changed, which a running game lays over its own story once it is quiet, as it takes another player's write; a game that wrote the same keys on an older revision keeps the admin's values as it keeps a first writer's. Answers the story's state with `set`, the lists of the keys that changed. 409 with `code` `none` for a story that is not keyed (sealed, or nobody wrote it yet), 409 with `code` `pinned` and `keys` for keys pinned at other values, 400 for a body that is not as it should be. The relay logs every change as `world <id>: admin <id> set keys of rev <n>: <lists>`. |
| `POST /v1/worlds/<id>/raid/pins` | Pins keys of a keyed story at values: `keys`, each key as the story names it (`s<id>`, `v<id>`, `ss<map>.<event>.<letter>`) to its value as for `.../raid/keys`, 1 to 2000 at once, at most 5000 pinned in all (413). Sets each key that holds another value as a new revision every game takes, as `.../raid/keys` does (none when every key holds its value already), and keeps the pins: a key pinned again takes its new value. No later write changes a pinned key, and `.../raid/keys` refuses another value for it with 409 `pinned`. Answers the story's state with `set` and `pins` (as the admin view above shows them); 409 with `code` `none` for a story that is not keyed. Logged as `admin <id> pinned <keys>`. |
| `POST /v1/worlds/<id>/raid/pins/clear` | Takes pins off: `keys`, the pinned keys, or rules an older relay kept, each named as the admin view shows them. The keys keep their values until a write changes them. Answers `cleared` (what it took off) and `pins`. Logged. |
| `POST /v1/worlds/<id>/raid/bosses/kill` | Defeats bosses for the world at once, such as every enemy of a troop: `keys` (1 to 500 pool keys as the games name them, not percent-encoded) and `max` (the raid max HP by key, more than 0 and at most 1e18), which a pool no game reported yet needs, since no game named its max; 400 naming those keys when `max` lacks them, and nothing changes. Each pool named is emptied with `by` `Admin` and `byPlayer` the admin's id, as a game's killing report would; a pool defeated already stays as it was. Answers `bosses`, every pool named as the admin view below shows it. Every game in the world room hears a `boss` frame for each pool it defeated, and so does every server battle of the world; a game then wins that boss's battle at once and the world overview shows it beaten. 413 with `code` `full` when the new pools would pass 500. |
| `POST /v1/worlds/<id>/raid/route/clear` | Takes back the route locked at the Great Decision, so the next player who chooses sets it again, and answers `cleared` (false when no route was locked). Refused with 409 and `code` `started` while the world's story is on the locked route, since another route locked then would turn away every write of both routes; once the world returns from the route, the lock is gone anyway. |

### Server battles

A co-op battle of two or more players goes to the relay's battle server (see [BattleServer/README.md](../BattleServer/README.md)), which hosts it with the game's own battle code; every player plays it back over a channel of the battle's own, which carries that battle's messages in plain text, so the server reads that battle alone and the world room stays end to end encrypted. Only the Node relay has a battle server, named by `BATTLE_SERVER` (`host:port`); without one, and on Cloudflare, every request answers 503 with `code` `no_server`, and the starter's game hosts the battle as before. The routes take the player's key and the auth key in the headers, as the world room does.

| Request | What it does |
|---|---|
| `POST /v1/worlds/<id>/battles` | Starts a battle on the battle server: `battle` (its id, 1 to 32 of `0-9a-z`), `seats` (the world seats of its players, 1 to 16, each seated in the world room now, the starter among them) and `setup` (what the server needs, in base64, at most 1,000,000 characters). Answers 201 with `battle` and `seat` (250, the server's seat on the channel) once the server took it; 503 with the server's refusal (`setup`, `scripts`, `data`, `mods`, `busy`, `timeout` after 5 s), 409 `seats` for a seat nobody sits on, 403 for a starter who is no player of it, 429 `rate` past 10 battles at once and one more every 6 s per player, 503 `full` past 16 battles of a world. |
| `wss://<relay>/v1/worlds/<id>/battles/<battle id>` | A player's channel of the battle, for its players and those the server took in later: told `seat <world seat>`, then every binary message from the server with the server's seat (250) in front; a player sends binary messages to seat 250 alone (any other closes the channel with 4000). `ping` is answered with `pong`. Before the end the relay sends `closed <why>` (`ended`, `server`, `arrive` when no player came within 60 s, `expired` after 2 hours, `deleted`) and closes the channel. |

Between the relay and the battle server one TCP connection per battle carries JSON lines: the relay's `serve`, `in`/`out` as players come and go, `message` (a player's message in base64), `boss` (a Raid World's boss pool) and `close`; the server's `serving` or `refused`, `send` (to a seat, -1 for every player), `boss_report` (what the battle did to a boss pool, which the relay counts as the starter's report and answers with the pool, and passes every other change of the world's pools on), `admit` (seats the battle takes in late, whose players may come onto the channel then) and `end`.

### Raid designs (Node only)

The Raid Designer and its `raid-designer` CLI keep one shared Raid design on the relay, split into entities (`rules`, `catalog`, `tier:<n>`, `boss:<32 hex>`, `skillDefault:<skill>`, `customSkill:<32 hex>`, `map:<n>`, `tileset:<n>`, `state:<n>`, `bossFight:<troop>`). The relay stores each entity's body as it comes and never reads it; the contract, with every body and exchange, is `docs/SERVER_FORMAT.md` in the MGQ-Online-Raid-Designer repository, and `core/fixtures/designs/` holds a copy of its fixtures, which the tests replay. The Cloudflare relay answers every route below with 404 and `code` `no_designs`.

- **Designers:** a designer names its key in `X-MGQ-Designer` (32 lowercase hex characters), its version in `X-MGQ-Designer-Version` (`0.0.0-dev` for a development build) and its design format in `X-MGQ-Design-Format`. Its id is the first 32 hex characters of the SHA-256 of `mgqmp designer <key>`, never a player id. The relay serves the designers its `designers` table lists; `DESIGNER_ADMINS` (designer ids, separated by commas) makes designer admins on every start, adding the missing ones under the start of their id until they rename themselves.
- **Gate:** an unlisted key gets 403 `not_designer`; a version below `DESIGNER_MIN_VERSION` (every version unless set) or a design format below the relay's lowest gets 426 `update` with `minimum` and `minFormat`, except on `me`, `release` and `release/file`, which a listed designer of any version reaches, so an outdated designer can always update itself; a designer who is no admin gets 403 `admin_only` on an admin route (builds, publish, rollback, format); a development build writes (push, builds, publish, rollback, format) only as a designer admin, or as anyone with `DESIGNER_ALLOW_DEV=1` on a local test relay (403 `dev_build` otherwise). The game gate of Versions does not apply to these routes.
- **Push rule:** a push is all or nothing. A change whose stored rev differs from its `baseRev` (0 for an entity that must not exist yet) comes back in a 409 `conflict` with the stored entity; a lower schema than stored gets 409 `schema`; more than 20 deletes need `confirmDeletes` from a designer admin (409 `deletes`). A delete keeps a tombstone; a delete of what is missing or deleted changes nothing. Every entity of a push gets the push's `seq` as its rev, and each entity keeps its last 50 revisions. A push from a released designer raises the design format and the lowest format to its `designFormat`. Pushes are limited to 30 at once and then one every 2 seconds per designer (429 `rate`), a push to 2 MiB and 200 changes, one body to 256 KiB (413 `too_big`).

| Request | What it does |
|---|---|
| `GET /v1/designs/me` | Any key: its `id`, and for a listed designer `name`, `designer`, `admin`, `seq`, `designFormat`, `minFormat` and `minVersion`. |
| `PUT /v1/designs/me` | Renames a listed designer: `{name}`. |
| `GET /v1/designs/entities?since=<seq>&after=<id>&limit=500` | The entities changed after `seq`, sorted by id, a page of up to 500, with `next` (the id to pass as `after`) while more follow; `since=0` leaves tombstones out. |
| `POST /v1/designs/push` | `{designFormat, message, confirmDeletes?, changes: [{id, kind, schema, baseRev, body}]}`, `body` null to delete; answers `{seq, accepted: [{id, rev}]}`. |
| `GET /v1/designs/entities/<id>/history?limit=50` | An entity's revisions, newest first. |
| `GET /v1/designs/designers` | The designers with `online` and what each edits, for designers and relay admins. |
| `PUT /v1/designs/designers/<id>` | Adds a designer or changes its `name` and `admin`, for designer admins and relay admins (an `X-MGQ-Player` key whose id is in `ADMINS`); a relay admin may do nothing else here. |
| `DELETE /v1/designs/designers/<id>` | Removes a designer, for the same; its sockets close with 4403. |
| `POST /v1/designs/builds` | `{seq}`, the current seq: starts a build, for designer admins; answers 202 `{build: {id, seq, status: "queued"}}`, 409 `moved` with the current `seq` for another seq, 503 `compiler` with a `message` while the relay cannot build. |
| `GET /v1/designs/builds` | `{live, previous, builds}`: the live and the previous build's ids (null for none) and the newest 20 builds with the live and the previous one, newest first, each `{id, seq, status, format, marshalSha, runtimeSha, snapshotSha, report, by, at}`. |
| `GET /v1/designs/builds/<id>` | The same with that build alone in `builds`; 404 `none` for a build the relay does not hold. |
| `GET /v1/designs/builds/<id>/snapshot` | The build's snapshot, gzipped (`application/gzip`), to tell what changed since; 404 `none` without one. |
| `POST /v1/designs/publish` | `{buildId}` of a build whose status is `ok`: makes it live and the live one the previous, for designer admins; answers `{live: {buildId, previousBuildId, by, at}, catalogDiff}`, 404 `none` for an unknown build, 409 `status` with its `status` for one not ok. |
| `POST /v1/designs/rollback` | Makes the previous build live again and the live one the previous, for designer admins; answers `{live}`, 404 `none` without a previous build. |
| `POST /v1/designs/format` | `{minFormat}`, from the current lowest format up to the design format: raises the lowest format, for designer admins; answers `{designFormat, minFormat}`. |
| `GET /v1/designs/release` | The newest designer release: `{version, minimum, notes, manifest, signature, size, sha256}`, the manifest's exact bytes and its signature in base64; 404 `none` while the relay holds none. |
| `GET /v1/designs/release/file` | The release's exe, whole or the part a `Range` header asks for (206, 416 for a range past its end), 3 an hour per designer (429 `rate`); 404 `none` while the relay holds none. |
| `wss://<relay>/v1/designs/socket` | The designer socket, under the same headers and gate as the read routes; a refused designer's socket opens and closes at once with 4403 (not a designer) or 4426 (update). |

- **Socket:** the relay greets a designer with `hello` (the seq, the designer, and the other designers online with what they edit) and tells every designer `pushed` after each push (its seq, designer and ids), `presence` and `left` as designers edit and go, `build` as a build changes its status, `live` (the build id, its marshal and runtime SHA-256 and who made it live) after a publish or a rollback, and `release` for a new designer release. A designer sends `{"op": "editing", "entity", "path"}` (nulls for nothing), told on at most once a second; what it edits is forgotten after 60 seconds without another, and once its last socket closes. The relay pings every 30 seconds and closes a socket that did not answer the last ping; a frame over 4 KB closes the socket. A designer pulls `since=<last seq>` on every connect, so a missed frame never matters.
- **Releases:** with `DESIGNER_GITHUB_TOKEN`, `DESIGNER_RELEASE_PUBKEY` and `DESIGN_DATA_DIR` set, the relay reads the latest release of `DESIGNER_REPO` every 30 minutes with the token, which never leaves the server, downloads `RaidDesigner-<v>-win-x64.exe`, `RaidDesigner-<v>.manifest.json` and its `.sig`, checks the manifest's ECDSA P-256 signature and the exe's SHA-256 against it, and keeps the exe in `DESIGN_DATA_DIR/releases`. The designer checks everything again. It logs a warning from 30 days before `DESIGNER_GITHUB_TOKEN_EXPIRES`.
- **Builds:** with `DESIGN_COMPILER`, `DESIGN_GAME_DATA` and `DESIGN_DATA_DIR` set, a build keeps the snapshot of the design at its seq (every entity but the tombstones, sorted by id, canonical JSON) in `DESIGN_DATA_DIR/work/<build id>`, then waits on a queue that compiles one build at a time, outside the lock pushes take, so designers push on while it compiles. It runs `DESIGN_COMPILER compile --snapshot … --game DESIGN_GAME_DATA --out … --seq <seq> [--previous <the live build's runtime.json>] --json` for at most 180 seconds. Before the first compile, and again whenever the binary changed, it runs `--version` and `preflight` and refuses with 503 `compiler` while the compiler's design format is below the lowest format or the game data is missing. Exit 0: the relay checks every file against the SHA-256 the report names, keeps them gzipped as blobs and the build `ok`; exit 2: `refused` with the compiler's report; anything else, a timeout or a file unlike its report: `failed`, with `failure` in the report. Statuses: `queued`, `compiling`, `ok`, `refused`, `failed`; a restart fails the builds it cut off. Builds are limited to 3 at once and then one every 5 minutes, publishing and rolling back together to 3 at once and then one a minute, per designer (429 `rate`). The ten-minute sweep keeps the newest 20 builds, the live and the previous one, and drops the blobs no build names.
- **World notice:** while `DESIGN_WORLD_NOTICE=1`, a publish also sends every world room the text `raid_design <marshal sha256> <runtime sha256>` and ends the pool of each boss key its `catalogDiff` names as removed or renamed (by the old key) in every Raid World, telling their games as an admin's reset does; a rollback sends the text alone. It stays off (the default) until a released game reads compiled format 3.

| Request (games and the battle server) | What it does |
|---|---|
| `GET /v1/raid-design` | With `X-MGQ-Features` and `X-MGQ-Design-Reader: <the highest compiled format the game reads>`: `{buildId, format, seq, marshal: {sha256, size}, runtime: {sha256, size}, at}` of the live build, or of the previous one when the game cannot read the live one's format; 404 `none` when it reads neither. `size` counts the bytes before gzip, `at` is when the build was made. |
| `GET /v1/raid-design/<sha256>` | A live or earlier build's `RaidDesign.rvdata2` or `runtime.json`, gzipped as kept (`application/gzip`, no `Content-Encoding`), with `Cache-Control: public, max-age=31536000, immutable` and `ETag: "<sha256>"` (304 for a matching `If-None-Match`); the reader gunzips it and checks its SHA-256. 20 at once and then one every 30 seconds per address (429 `rate`), requests from this machine, such as the battle server's, not counted; 404 `none` for any other hash. |

### World rooms

- **Connect:** `wss://<relay>/v1/world/<world id>?name=<name>`, with the player's key in the header `X-MGQ-Player` and the auth key in the header `X-MGQ-Auth` (released games send them as `player=<key>&auth=<auth key>` in the address instead, which is kept for them). The relay lets the game in only if the world is in the directory, the SHA-256 of the auth key is the world's `authHash`, and the creator has not removed the player: otherwise HTTP 404, 401 or 403 before the WebSocket opens, HTTP 409 while the creator is still uploading the starting save, and HTTP 400 when the world is a Raid World and the request's header `X-MGQ-Features` (features separated by commas) does not name `raid`, which games take as final, unlike a 409, and HTTP 400 with the code `update` when the world's story is keyed and the header does not name `keys`, and when the game names a version before `0.6.8` in `X-MGQ-Version`, or none, and the world's `mods` are longer than the 300 characters such a game holds, or its `modHashes` or `settings` longer than the 2000 characters each it holds. A game without `X-MGQ-Features`, or too old by its version, gets HTTP 400 with the code `update` before any of these checks, see Versions. Any other 400, a 403 or a 409 names why in the response header `X-MGQ-Refusal`, with the codes of the directory. Entering rooms and world rooms is limited per address, 30 at once and one more every 2 seconds (HTTP 429). When a player enters a world room again, the relay closes the player's earlier connection with 4009 and the reason `replaced`. The world's seats come from the directory; once every one is taken, the next game gets HTTP 409. After every change the room tells the directory who is in it.
- **Seats:** a game takes the lowest free seat, from 0. It is told `seat <own> <others…>`, the seats already taken in ascending order, such as `seat 2 0 1`. The others are told `in <seat>`, and `out <seat>` once it leaves.
- **Messages:** a game sends a binary message as its target seat, or 255 for everyone, followed by the payload. The relay passes it on with the sender's seat in place of the target, so the receiver knows who sent it. A message for a free seat is dropped.
- **Chat:** the games send each other their lines encrypted, as any message. The relay keeps a plain copy of the global chat for the admins:
  - After every global line, a game sends the text `chat <line>`. The relay keeps it in the world's chat (`GET /v1/worlds/<id>/chat`) with the sender's player id and name, and passes it to nobody.
  - Each connection may send 2 chat lines a second, after a burst of 10. The relay drops a line beyond that and answers the text `slow chat`; games that don't know it ignore it. A `chat` text without a line is ignored.
  - When an admin says something (`POST /v1/worlds/<id>/chat`), the relay sends the text `chat <name>` + tab + `<line>` to every game in the room; games that don't know the frame ignore it.
- **Story:** after every change of a Raid World's story the relay sends every game in the room the text `storyd <JSON>` for a keyed story: `rev`, `prev` (the revision it followed), `delta` (the lists of the keys it changed, empty for a route lock or a companion) and `state` (the story's state after it, without its keys), or `story <rev>` for a sealed story and a change whose frame would pass 60,000 characters, which the games fetch; games that don't know a frame ignore it.
- **Bosses:** after every change of a Raid World's boss pool (a report that changed it, an admin's reset of a pool there was, an admin's kill) the relay sends the text `boss <left> <max> <defeated> <key>` to every game in the room: the share of the max HP left now with up to 6 decimals (at least `0.000001` while the boss stands), the raid max HP as a whole number, `1` when the boss is defeated, else `0`, and the key last, since it may hold spaces and `#`, such as `boss 0.25 5000000 0 Metatronne and Sandalphone#1`; a reset sends a share of 1. Games that don't know it ignore it.
- **Difficulty:** after an edit that changes a Raid World's `difficulty`, the relay sends the text `difficulty <n>` to every game in the room; games that don't know it ignore it.
- **Squad:** after an edit that changes a Raid World's `squad`, the relay sends the text `squad <luka> <formation> <front> <raidFront>` to every game in the room, `luka` 1 when Luka may be replaced, else 0, such as `squad 1 6 2 1`; games that don't know it ignore it.
- **Raid bosses:** after an edit that changes a Classic world's `raidBosses` (a world without it counts as `false`), the relay sends the text `raid_bosses <0|1>` to every game in the room, 1 when the world fights raid bosses; games that don't know it ignore it.
- **Mods rule:** after an edit that changes `otherModsOff` or `mods` (compared as kept, a world without `otherModsOff` by its type), the relay sends the text `mods_rule <0|1>` + tab + `<the world's mods>` to every game in the room, 1 when the world turns other mods off; the mods never hold a tab or a line break. A game that now runs mods the world turns off leaves the world; games that don't know the frame ignore it. A game naming a version before `0.6.8`, or none, is not told a rule whose mods are longer than 4096 characters, which its DLL drops.
- **Limits:** each connection lasts at most 2 hours on its own; the game then connects again.

### Both

- The text `ping` is answered with `pong`, for keeping an idle connection open; any other text than `ping` and a world room's `chat` closes the connection. On Node a `ping` counts against the message limits; Cloudflare answers it without waking the room, so there it does not. A `chat` text counts on both.
- At most 512 KB per message and 60 messages per second over time (bursts of 240), per connection.
- **Close codes:** 4000 bad request, 4001 role taken, 4002 message too large, 4003 too many messages, 4004 nobody joined in time, 4005 the room lasted too long, 4006 the other side left, 4007 the world is full, 4008 the connection lasted too long, 4009 the creator removed the player, or the player entered from elsewhere (reason `replaced`), 4010 the world was deleted.

## Cloudflare (relay r1 until 0.6.6.1)

Up to 0.6.6.1 relay r1 ran on the free Workers plan at `relay.mgqmp.workers.dev`. Past the free plan's daily limits, requests fail until midnight UTC; nothing is billed. From 0.6.7 on r1 is the Node relay on our own server at `relay.mgqonline.org` (see Moving to a rented server), and the Worker's `MIN_VERSION` turns every older version away.

- **Try it locally:** `npm run dev:cloudflare` runs the Worker on this PC at `ws://127.0.0.1:8787`, without an account.
- **Log in once:** `npx wrangler login` (in PowerShell `npx.cmd wrangler login` if scripts are blocked) opens the browser to allow wrangler on the Cloudflare account.
- **Deploy:** `npm run deploy:cloudflare`.
- **Downloads:** the directory sends starting saves and uploaded mods' zips piece by piece as it reads them, without a Content-Length, and at most 3 at once and 1 per address. A download that finds no free slot waits up to 30 seconds for one, at most 10 waiting in all; past that, and past 20 downloads at once and one more every 30 seconds from one address, it gets 503 with `code` `busy`, the error "the relay is sending other downloads, try again in a moment" and `Retry-After: 10`. A download still running after 5 minutes is ended and its slot given to the next. The Node relay sends both whole and has no such limit.
- **Lowest version:** `MIN_VERSION` in the `[vars]` of `wrangler.toml`, see Versions.
- **Bug reports:** `npx wrangler secret put GITHUB_ISSUES_TOKEN --config cloudflare/wrangler.toml` and the same for `GITHUB_BUG_FILES_TOKEN` set the tokens once; the repositories and the branch are the `[vars]` in `wrangler.toml`.

## Moving to a rented server

1. On the server, install Node.js 24 or later (the SQLite database needs `node:sqlite`) and [Caddy](https://caddyserver.com), and point a domain at the server.
2. Copy `core/`, `node/`, `package.json` and `package-lock.json`, then run `npm install --omit=dev`.
3. Start `node node/server.js` as a systemd service, with these environment variables:
   - `MGQ_RELAY_DB=/var/lib/mgq-relay/relay.sqlite`: the SQLite database the worlds, their starting saves, the mod catalog, its uploaded zips, the trades, the Raid Worlds' stories and their boss pools and the release control are kept in, made on the first start (with its `-wal` and `-shm` files beside it). Without it everything stays in memory and is gone with the process. Back the file up with `sqlite3 relay.sqlite ".backup copy.sqlite"`, never by copying it while the relay runs.
   - `ADMINS`: the admins' player ids, as above.
   - `GITHUB_ISSUES_TOKEN` and `GITHUB_BUG_FILES_TOKEN`, and `REPORT_ISSUES_REPO`, `REPORT_FILES_REPO` and `REPORT_FILES_BRANCH` unless the defaults fit: where the bug reports go, see above. Without both tokens the relay takes no reports.
   - `MIN_VERSION`: the lowest version a game may name while no admin set one, `0.6.0` unless set, see Versions and Release control.
   - `HOST` and `PORT`: where it listens, `127.0.0.1:8080` unless set.
   - `DESIGNER_ADMINS`, `DESIGNER_MIN_VERSION` and `DESIGNER_ALLOW_DEV`: the designer admins' designer ids, the lowest Raid Designer version served and whether development builds push as anyone (`1` only on a local test relay), see Raid designs. The design tables live in the same database, which the relay brings up to its newest step (`PRAGMA user_version`) as it starts.
   - `DESIGN_DATA_DIR`: the folder the designer releases (`releases/`) and the builds being compiled (`work/`) are kept in, such as `/var/lib/mgq-relay/designs`.
   - `DESIGNER_REPO`, `DESIGNER_GITHUB_TOKEN`, `DESIGNER_GITHUB_TOKEN_EXPIRES` and `DESIGNER_RELEASE_PUBKEY`: the designer's private repository (`Pauliinchen/MGQ-Online-Raid-Designer` unless set), a fine-grained token with Contents: read on that repository only, its expiry date (such as `2027-10-01`) and the PEM of the release key (line breaks may be written `\n`); without the token, the key or `DESIGN_DATA_DIR` the relay serves no designer releases.
   - `DESIGN_COMPILER` and `DESIGN_GAME_DATA`: the Raid Designer's self-contained linux-x64 CLI, such as `/opt/mgq-designer/current/raid-designer`, and the game folder it compiles against, `/opt/mgq-battle/game`; without either, or without `DESIGN_DATA_DIR`, builds answer 503 `compiler`.
   - `DESIGN_WORLD_NOTICE`: `1` makes a publish tell the world rooms and end the pools of removed and renamed bosses, see Raid designs; off unless set, until a released game reads compiled format 3.
   - `BATTLE_SERVER`: the battle server's `host:port`, such as `127.0.0.1:8095`, which hosts the co-op battles; without it the starters host them, see Server battles. Run the battle server beside the relay as root (its sandbox needs it) with a game folder holding the game's `Data`, MGQ Online and Mod Config Remake, `BATTLE_RELAY_URL` pointing at this relay for the worlds' mods, see [BattleServer/README.md](../BattleServer/README.md).
4. The relay writes one line per request to stdout (`<time> <method> <path> <status> <ms> <address>`, the path without its query, so no key ever appears) and every error it catches to stderr, with its stack. Under systemd both go to the journal (`journalctl -u <service>`); the service file's `StandardOutput=append:/var/log/mgq-relay/relay.log` keeps them in a file instead. The rooms and the WebSockets live in memory, so a restart ends every connection; the games connect again on their own.
5. On its own the relay closes rooms and connections whose time is up every minute, checks the mod catalog's links half a minute after a start and then every five minutes, checks the mod's own releases every five minutes, and every ten minutes sweeps out worlds whose starting save never came, trades kept long enough and Raid design builds past the newest 20 with the blobs no build names, so the database does not grow with what nobody asks for again.
6. Have Caddy fetch the certificate and pass WebSockets on, with a `Caddyfile` like the one below. The relay counts its rate limits by the address Caddy appends to `X-Forwarded-For` last, for requests from this machine only.

   ```
   relay.example.org {
       reverse_proxy 127.0.0.1:8080
   }
   ```

7. Run one process. The rate limits per address are counted in memory, so several processes behind one proxy would each let an address have the full allowance, and the rooms are in memory too, so two games of one room must reach the same process. One Node process carries the relay's load with room to spare.
8. Take over what the Cloudflare relay keeps, before the new relay's first start: deploy the Worker with the migration routes, then run `MGQ_ADMIN_KEY=<an admin's player key> node node/migrate.js https://relay.mgqmp.workers.dev /var/lib/mgq-relay/relay.sqlite` on the server. Both relays answer the routes, for their admins only (403 for anyone else): `GET /v1/migration` lists the worlds, mods and trades (`format` 1 on Cloudflare; `format` 2 on a Node relay, which also hands out every Raid design table under `GET /v1/migration/designs` and each blob's bytes under `.../designs/blobs/<sha256>`), `GET /v1/migration/worlds/<id>` hands out a world's entry, chat, story, checkpoints and boss pools, `.../start` its starting save, `GET /v1/migration/mods/<key>` a mod's entry, `.../file` its upload, and `GET /v1/migration/trades/<id>` a trade's record and sealed offers. The tool writes into a database that does not exist yet, reads every record back and compares it with the relay's, and stops at the first that differs. It copies what the relay keeps at that moment, so whatever the old relay takes afterwards stays behind.
9. Point the relay list in the Multiplayer DLL at the new relay and release that version, then raise the old relay's `MIN_VERSION` to it, which turns every older version away, and copy once more right after, into a new database. A join code and a world code name their relay by id, so the id stays (`r1` moved from `relay.mgqmp.workers.dev` to `relay.mgqonline.org` in 0.6.7): every code made before reaches the new relay, and no older version reaches the old one any more.
