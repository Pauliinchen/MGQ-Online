# Developer notes

Monster Girl Quest! Online keeps its first name inside: the `Multiplayer` install folder, `Multiplayer.dll`, the `MGQParadox.Multiplayer` projects, `MGQ_Multiplayer`, the `MGQ_Mp` modules and the DLL's `mp_` functions. The `mgqmp` strings in join and world codes, key derivation labels and player ids must never change, since every world and player id on the relay derives from them.

## Layout

```

Directory.Build.targets               puts vswhere.exe on the PATH, which the NativeAOT link needs
GameScript/Multiplayer.rb             Ruby, what every way of playing together shares; loads the others
GameScript/Multiplayer/Scripts/       Ruby, the other scripts, see the table below
GameScript/Tests/                     Ruby, tests of the scripts outside the game, run.rb runs them all

.github/ISSUE_TEMPLATE/bug_report.yml the form players report bugs with
```

**Scripts.** `Multiplayer.rb` is a Patch folder mod: the mod loader loads `Patch/**/*.rb` sorted, capitals first, so it comes after `Discord_RPC.rb` of the Discord mod. At its end it loads the other scripts from `Patch/Multiplayer/Scripts/` itself (`load_scripts`), in the order of its `SCRIPTS`, which the table below follows. They are `.rbx` files because the loader recurses into folders: as `.rb` files it would load them a second time, in alphabetical order. A script may only use what loaded before it at load time; later ones are reached at run time (`defined?`). The order also decides how the battle scripts' hooks wrap each other, since they install them as the game starts running, the last loaded first. A script that is missing or fails to load is logged to the in-game log, and the others load all the same.

**Hooks.** A game method that more than one script follows, such as `Scene_Map#update_scene`, `Spriteset_Map#update` and `#dispose`, `Game_Map#update`, `Graphics.update`, `SceneManager.run`, `Scene_Title#start` and `#update` or `Game_Interpreter#execute_command`, is wrapped once, by `core_hooks.rbx`; each script registers a block with `MGQ_MpHooks.before` or `.after` under its own name instead of wrapping the method itself. The blocks run on the object the method runs on, with its arguments, in the order nested wraps would: before blocks from the last script loaded to the first, after blocks from the first to the last. So `battles_pvp.rbx` still puts the shared data back before `world.rbx` closes the world as the title screen starts. A failing block is logged once and the others run on. A hook that changes what a method does or returns is a wrap of that script's own, made with `MGQ_MpHooks.around` from a block that gets the object, the arguments and the original, registered under the script's name as well, so a script loaded again replaces its wrap instead of wrapping the method once more. Only what the registry cannot express stays a plain alias guarded by a `hookable?`: `world.rbx`'s redirect of `File` and `Dir` into a world's save folder and its `Bitmap#initialize`. Holding the player is wrapped once too: a script registers with `MGQ_MpHooks.hold_player`, and while any block says so the player stands still (`Game_Player#movable?`) and the menu stays shut (`Scene_Map#update_call_menu`), as during a held encounter or the leader's story scene.

**`package/Multiplayer/`:** the player `README.txt`, and the updater: `Update.bat` runs `Update.ps1` (Windows PowerShell 5.1), which downloads the latest release's zip and extracts it over the game folder. The player starts it, or the game does: once a newer release is out, *Multiplayer* on the title screen offers *update and install* (`MGQ_MpWorld::UpdateOffer`), `mp_update_game` starts `Update.bat -GameProcess <pid>` in its own console and the game quits (under Wine it answers 2 and starts nothing, since Wine's cmd has no PowerShell, and the box tells to update by hand, `WINE_TEXT`); the updater takes that process once as it starts, holding its handle (`Get-StartingGame`), so a later wait never waits on another program Windows gave the same id, waits for it, updates, and starts `Game.exe` again, with `MGQMP_OPEN_WORLDS=1` set when it succeeded, which makes the title screen open the world screen once (`MGQ_MpWorld.open_after_update`). Only an install that already has this updater offers it, since the installed scripts run it. It reads the installed version from the DLL's `ProductVersion`, so it needs no version file, and prints the release's notes to the console (see [Releasing](#releasing)). Unlike the Discord mod's updater, it also **cleans up after refactors**: the `ShippedFile` item in `MGQParadox.Multiplayer.csproj` is built from the same `ModFile`/`PatchFile` globs the package itself is, so every publish writes a `Patch/Multiplayer/Manifest.txt` that always lists exactly what that release ships, no matter how many scripts get renamed, merged or split later. `Update.ps1` reads the *old* `Manifest.txt` before extracting and the *new* one after, and deletes whatever dropped out (a manifest lists only files a release shipped, so `Player.ini`, `Favourites.ini`, the worlds and the logs, which share `Patch/Multiplayer/` with them, are never at risk). An install with no `Manifest.txt` yet (from before the updater existed, or a hand-extracted zip) simply skips cleanup instead of deleting anything. Every path goes to cmdlets through `-LiteralPath`, and the download, the extraction (`Expand-Release`) and the game's start through .NET, since Windows PowerShell takes `[` and `]` in a path as wildcards and a game folder such as `MGQ Paradox [EN]` would break them.

## Build and test

You need the .NET 10 SDK and the Visual Studio workload **Desktop development with C++**, whose linker NativeAOT uses.

Publishing the DLL project assembles the complete release layout in `Shipping/` at the repository root. Copy its content into a game folder to install or update the mod there:

```
Patch/                      Multiplayer.rb  0_ModConfigRemake.rb
Patch/Multiplayer/          Multiplayer.dll  Manifest.txt  README.txt  Update.bat  Update.ps1
Patch/Multiplayer/Scripts/  *.rbx
```

- **Mod Config Remake ships with the mod.** A publish on this PC copies it from the Mod Collection checked out beside this repository (`..\MGQ-Paradox-Mod-Collection`) into `package/Patch/` (ignored by Git); the release workflow downloads it from the Mod Collection's latest release instead. Without it the publish stops with an error.

- **Publish, not build:** only a publish runs NativeAOT, so a plain build gives no usable DLL.

  ```powershell
  dotnet publish MGQParadox.Multiplayer -c Release -p:Version=0.1.0
  ```

- **Release publishes** also zip it: `bin/Release/MGQ-Online-<Version>.zip`.
- **Every publish replaces `Shipping/`.** Close the game before copying it over an install: `Multiplayer.dll` is locked while the game runs.
- **Logs:** `Multiplayer <session start>.log` (the DLL) and `Multiplayer InGame <session start>.log` (the scripts: what the mod did, decided and refused, and errors), both in the game folder's `Logs` folder, which every mod writes its logs to. Each game session writes its own pair, stamped with the time the game started (`YYYY-MM-DD HH-MM-SS`, local time), without a line or size limit; as a session starts, the scripts delete the logs of every session older than the last five (`Log::KEPT_SESSIONS`, `Log.prune`). Only the scripts' logs count the sessions, since the DLL names its log after its own start when Windows cannot tell the game's, as under Wine; a log stamped up to a minute before the oldest kept session stays (`SESSION_SLACK`), and only the files actually deleted are counted in the log. A game the World Admin tool starts for the options dump deletes nothing, and names its scripts' log `Multiplayer InGame <session start> options dump.log`, which counts no session but goes with the sessions older than the kept ones. The DLL logs the world's messages as one line about every minute (`WorldTraffic`: messages and kilobytes in and out, by kind, and the seats they came from), plus each message it could not send, and the scripts log their hooks as one line per script with how many methods it follows and wraps (`MGQ_MpHooks.report`, after loading and every frame), plus each one registered again or failing.
- **Two games on one PC** can play each other: both go through the real relay as they would between two homes.
- **A relay on this PC:** run `node Relay/node/server.js` (port 8080, `ADMINS` for admin ids, `MGQ_RELAY_DB=<file>` to keep worlds, saves, mods and trades in a SQLite database instead of memory) and start the game with the environment variable `MGQMP_RELAY=ws://127.0.0.1:8080`; the DLL then talks to that relay instead of the live one, which lets a build with relay changes be tried before the relay is deployed.

### Tests

`MGQParadox.Multiplayer.Tests` covers the DLL without the game: the join code, its relay room and codes of other versions, messages, their encryption (another token, a changed, repeated, missing or returned frame), the link (messages both ways, pings keeping a quiet link open, goodbye, silence, oversized messages) and whole exchanges between two sessions, including the party both sides name and what hosting and joining say when the relay finds no host, cannot be reached or is unknown. Everything meets at a relay inside the test process (`TestRelay`), which never reaches the real one. It builds into an executable that runs itself:

```powershell
dotnet run --project MGQParadox.Multiplayer.Tests
```

The tests run 32-bit like the game and need the x86 .NET 10 runtime (`C:\Program Files (x86)\dotnet`); with `DOTNET_ROOT` pointing at the x64 install they need `DOTNET_ROOT_X86` pointing at the x86 one.

`GameScript/Tests` covers the scripts outside the game, one `*_test.rb` file per area (the loader, the shared hooks, the open world, parties, battles, worlds, the hotkeys and the boxes on screen), with stand-ins for the parts of RGSS and the game each script touches. Each file runs in a Ruby process of its own, since each brings its own stand-ins; `support.rb` gives them `check` and `load_script`, `world_support.rb` the open world's stand-ins that the overworld, duel and overview tests share, and `battle_support.rb` the live battle's that the co-op, hotjoining and team duel tests share. With Ruby 3.3 or later:

```powershell
ruby GameScript/Tests/run.rb        # -v shows every check
```

The *Scripts* workflow runs them on every push, and the *Release* workflow before it builds a release. They run on a newer Ruby than the game's (1.9), so they do not catch what only that one lacks. Drawing, input and the game's own battle and event engine stay untested: those need the game.

## Conventions

- **File headers.** Every `.cs` and `.rb` file starts with a header block listing the file name and a changelog, newest entry first. Entries by the same author on the same day are grouped. Only changes after the first commit are recorded; before that, a file carries just `Created`.
- **Documentation comments.** Every type and member is documented: XML comments in C#, YARD-style comments in Ruby. The summary is mandatory, parameters and return values whenever they apply, and remarks only where they add something. Keep them short, and always describe the current state.
- **Inline comments.** Kept to a minimum, only where the code cannot say something itself: a constraint, a trap, or the failure a line prevents.
- **Names.** Magic strings and numbers get a named constant.
- **Language.** Code, comments and documentation are English.

## Releasing

1. Push your changes.
2. On GitHub, go to **Releases → Draft a new release**, create a tag like `v0.1.0`, write the notes, and click **Publish**. `Update.ps1` prints these notes to the console as they stand, so write them as something a player reads there, not as a commit log.
3. The *Release* workflow runs the tests, builds the mod and attaches `MGQ-Online-0.1.0.zip` to that release. Keep that zip name: `Update.ps1` of every install looks for `MGQ-Online-*.zip`. If the run failed, fix the cause on `main`, then start **Actions → Release → Run workflow** with the release's tag.

## Runtime

- **Nothing blocks the game.** The DLL's threads run the network; every export returns at once.
- **Nothing throws into the game.** Every export and the DLL's threads catch everything; an exception escaping them would end the game.
- **The connection.** Hosting waits in a room of the relay, and joining enters it; the first frames swap what each game hands over (a PvP battle's team) and then stay open as the link, which carries the modes' own messages (`mp_send`, `mp_receive`). The link pings after 2 s without another frame, counts as `closed` after a goodbye and as `dropped` after 10 s of silence, which a running game never lets happen. `mp_state` describes it: `state`, `code`, `invite`, `error`, `opponent`, `link`, `role`, `party`, `ignored`, then the payload. `mp_status` describes it without the payload, for the checks the scripts make many times a second.
- **Update check:** `MGQ_Multiplayer.start` calls `mp_check_for_update` once per session, and the `Graphics.update` hook polls `mp_newer_version` every 30 frames until it answers (`MGQ_Multiplayer::UpdateCheck`). Once a version comes back, `MGQ_Multiplayer.outdated?` is true, which `MGQ_MpWorld.available?` and `MGQ_MpBattlesPvp.available?` both require to be false: the title screen's Multiplayer command greys out (`MGQ_MpWorld.add_title_command`) and `Scene_Title` shows `MGQ_MpWorld::UpdateNotice` (two lines below the translation's version and Discord's own notice, which takes up to two lines from y=24), and F11 on the map answers with `MGQ_Multiplayer::UPDATE_MESSAGE` instead of opening the PvP lobby (`MGQ_MpBattlesPvp.on_map`). Different mod versions never speak the same protocol on purpose, so this keeps an outdated game from confusing a friend's newer one rather than failing mid-exchange.

### Worlds (DLL)

A world is a lasting place several games play in at once, up to 32. Its **world code** (`mgqmp2;<token>;<relay>;<seats>`) never changes, and whoever holds it may enter the world; the game keeps it in the world's folder, which `mp_world_id` names by a hash of the token, so the folder never gives the code away.

- **The directory.** The relay lists every public world, and the hidden ones the asking player joined (see [Relay/README.md](../Relay/README.md), world directory). `mp_dir_refresh` fetches the list with the player's key on a thread of the DLL's own, and `mp_dir_list` hands it out as it stands: `state` and `error`, then one tab-separated line per world (`world`, id, seats, players online, creator's id, when last active, creator's name, name, starting save `none`, `pending` or `ready`, 1 when hidden, 1 when players choose their start, 1 without a password, 1 when featured, 1 when only games with the same data may enter, the creator's game data, the mods it needs, its description, the creator's hashes of required mods outside the catalog, its mod settings, its type `classic` or `raid`, and how a Raid World shares companions `off`, `story` or `all`; fields added later go at the end, and the game script reads a line without the last two as a Classic world sharing none) and per player (`member`, id, 1 when online, name). The DLL reads the relay's JSON by hand, since NativeAOT leaves out what serializing by reflection needs. Every request of the DLL to the relay, and its world room's WebSocket, names what the game plays in the header `X-MGQ-Features` (`raid`, `DirectoryClient.Features`); the relay keeps games that do not name `raid`, as released ones never do, out of Raid Worlds.
- **One action at a time.** `mp_dir_create` (name, password, seats, 1 when hidden, 1 when players choose their start, starting save, description, mods, the creator's game data, 1 when only games with the same data may enter, the creator's mod hashes, the mod settings, the type `classic` or `raid`, and how a Raid World shares companions `off`, `story` or `all`, both empty for the defaults), `mp_dir_unlock` (world, password), `mp_dir_delete` and `mp_dir_ban` (world, player), and `mp_dir_fetch_start` (world code, folder) run on a thread and return at once, refusing while one runs; `mp_dir_action` gives `state` (`idle`, `busy`, `done`, `failed`), `kind`, and `code` with the world's `world` id, after `mp_dir_unlock` also its `name`, `start` and `choose`, or `error`; `mp_dir_clear` makes room for the next. `mp_copy_text` puts a hidden world's id on the clipboard for its creator.
- **Game data.** `MGQ_MpWorld::GameData.fingerprint` is a format number and one CRC32 per part of the database (actors, classes, skills, items, weapons, armors, enemies, states, troops, common events, maps) over the ids that exist: entries with a name, troops with members, common events with commands, and the map ids. It reads whether an entry has a name, never the name itself, so the translated and the untranslated game give the same one as long as both name the same entries. The creator's game sends it as `data` with a new world, with `strict` when only games with the same data may enter; the relay only keeps both. The world screen compares it with its own, from the list, before a world is entered; a world this PC has saves of is not entered while the list has not arrived. A differing game is asked first (`data_allows?`), or refused in a `strict` world. A world without `data`, or with another format, is not compared. The creator replaces a world's `data` with their game's as it is now from the details' *Your game* row (`mp_dir_set_data`, the relay's `edit` route, which takes `data` from the creator only), for when a mod they play with changed.
- **Cancel.** Every screen of the mod that closes asks `MGQ_MpUi.cancel?`: the game's cancel button past the capture, or the numpad's 0 read from Windows with Num Lock on and off (`NUMPAD_CANCEL_KEYS`, 0x60 and Insert), since the game takes it only with Num Lock on; `Key.triggered?` reads those keys at every `Input.update` (`Key.read_watched`), watched from the start (`Key.watch`). A text box asks `numpad_cancel?` alone, as the game's cancel button is X too. `Key.pressed?` takes a key nobody asked about in the frame before as let go, counting frames at `Graphics.update` (`Key.next_frame`), since a game window's cancel runs `Input.update` twice in a frame; so the numpad's 0 that closed one screen still closes the next.
- **Text boxes.** `MGQ_MpUi::TextEdit` (ui_text_box.rbx) is the editor every text box of the mod types through: the text, the cursor in it, the keys that move it (left, right, Home, End) and remove characters (Backspace, Delete), the longest text and the characters it takes, and the blinking. Its owner feeds it the typed characters (`type`, which answers `:enter` and `:escape` for the owner to act on) and calls `update_keys` once a frame, then draws: `visible` picks the part of a long text a box of one line shows around the cursor, and `MGQ_MpUi.wrap_spans` breaks a text into lines that keep every character's place, for a box of several lines, where up and down move by line (`update_keys` with the lines). `MGQ_MpUi::TextBox` draws a box being typed into on any picture, a sprite's or a window's: `draw_line` a box of one line, `draw_area` one of several, each with the cursor in the color of the text; the owner draws the background and what the box shows while nobody types. The chat box and the world screen's forms use both; a new box should too, instead of typing or drawing logic of its own.
- **The list box.** `Sprite_MpListBox` (ui.rbx) is a large box of headings and items drawn like the World overview, above every window; `Sprite_MpListBox::View` holds its lines, the item picked and the scroll. The world screen opens it with a world's players (online, then offline), its mods (`MGQ_MpWorld.mods_of` splits them at semicolons) or its whole description, from the world's choices, from the details (`Window_MpWorldDetail#targets`: the right arrow moves the cursor onto them, `update_focus`) or with a click (`target_at`).
- **The left side.** The worlds scroll in `Window_MpWorldList`, which draws a scrollbar on a sprite of its own; the commands sit in `Window_MpWorldCommands` below it. `MpWorldListPane` stands for both towards the screen and lets the player pick one of the two as a whole first (`pick`, the cursor drawn around the window through `MGQ_MpBoxCursor`), so the commands are reached without moving past every world: up and down pick, confirm moves into the picked window onto the row the cursor left there (`enter`), cancel moves back out (`back_out`), and cancel while a window is picked, or the commands' *Back*, leaves the screen. The pane reads those keys itself (`update`), a frame after it took the input.
- **Required and essential mods.** A mod written as `?Name` in a world's mods is essential (`MGQ_MpWorld.essential_mods`): no script is looked for, which suits mods of data files; it shows in green while the game data check finds this game matching the world's, and in gold while it differs or cannot be compared. A mod written as `!Name` is required (`required_mods`). `installed_mod?` looks for a script of that name among the `.rb` files of the `Patch` folder, read once per session and compared without case, `.rb`, spaces, underscores and hyphens; `on_enter` checks them before the game data check, by their files' hashes where the relay's catalog or the creator knows them (see [World mods](#world-mods-world_modsrbx)), else by file name only.
- **Hidden worlds by id.** *Add a hidden world* looks the id up (`mp_dir_find`, the world's lock, which names it) and keeps it in `Added.ini` in the mod folder (`MGQ_MpWorld::Added`). Every refresh first hands those ids to the DLL (`mp_dir_watch`), which asks the relay for them with the list (`ids`), so the world shows with its details before the player ever entered it; entering then goes the way of any listed world. *Remove from my list* forgets an id whose world was never entered, and only the 50 ids added last are kept (`Added::MAX`, the relay's `maxListedIds`), so the ids of deleted worlds do not crowd new ones out. Whoever holds a hidden world's id therefore sees its details, but still needs its password to enter.
- **The password locks the token.** Making a world makes a new token and locks it with the password (`WorldLock`: PBKDF2-SHA256, 600,000 iterations, then AES-GCM; the DLL derives PBKDF2 itself (`Pbkdf2Sha256`), since .NET's goes through a BCrypt pseudo-handle no Proton release supports; locks of released versions have 200,000), so the relay only ever keeps the lock. An empty password locks it too, and marks the world `open` in the directory, so the games open its lock with the empty password without asking. Opening a world fetches its lock, which comes with the world's name, seats, starting save state and whether players choose their start, so a hidden world opens by its id alone, and opens it with the password; a wrong password fails the tag. The world's id is `Relays.WorldRoomOf(token)`, which the opened token must match.
- **Proving the token.** Every connection sends the auth key (`WorldKeys.AuthKeyOf`: HKDF of the token, apart from the frames' keys and the room id), whose hash the directory keeps. It also sends the player's key and name, which `mp_set_player` sets from `Patch/Multiplayer/Player.ini`; the relay turns the key into the id everyone sees (`WorldKeys.PlayerIdOf`, which `mp_player_id` hands out), and only the creator's key may delete the world or remove a player.
- **The starting save.** `mp_dir_create` takes the starting save's files as lines of `<name>=<path>`, paths relative to the game's folder (`ModFolder.GamePathOf`). `StartingSave.Seal` zips them and encrypts the zip with AES-GCM under a key from the token (HKDF, apart from the auth key) before the world is made, so a save that cannot be read, or sealed is larger than the relay's 8 MB (`StartingSave.MaxSealedBytes`), leaves no world behind; the relay deletes a world whose save has not come 10 minutes after it was made. The world is made with `start: true`, which keeps everyone out until the upload arrived; a failed upload deletes the world again. `mp_dir_fetch_start` downloads it with the auth key and unpacks it into the folder, plain file names only, at most 8 files and 64 MB.
- **No host.** `mp_world_open` takes a seat in the world's room at the relay, whose room id is the world's id. Once every seat is taken, the next game waits and tries again, with `error` saying the world is full; it waits the same while the starting save is still on its way or the relay took too many tries from its address, which the relay names in the `X-MGQ-Refusal` header. The player's key goes in the `X-MGQ-Player` header, never in an address. A world the directory lacks, a token that no longer fits, a player the creator removed, a world with as many players as it may, or a Raid World the relay keeps the game out of (400 `raid_unsupported`, which needs a newer mod) ends the session for good (`failed`), as does a close code 4009 (removed, or with the reason `replaced` when the same player entered from another game) or 4010 (deleted) from the relay.
- **Coming back by itself.** A cut connection, a silent relay (60 s) or the relay's 2-hour limit per connection leads back into the room, after 2, 5, 10, then every 30 s, the delays starting over after a connection that lasted 30 s. Meanwhile `state` is `reconnecting`, and the game plays on. The seat may be another one afterwards.
- **The ping.** The writer sends the relay a text `ping` on connecting and every 5 s (`PingInterval`), which also keeps the connection open, and the relay answers `pong` without waking the room. The time from the last ping to its pong is the ping, `ping` in milliseconds in `mp_world_status` while the connection is open; a ping whose pong never came is given up at the next.
- **One key per sender.** `WorldCipher` derives each game's key from the token and a salt the game picks per connection and sends in front of every frame; the sender's seat and the target seat, which follows the counter, are authenticated, so a frame passed on under another seat or to a game it was not meant for fails. A sender's counters only have to grow, since frames it sends to one seat skip the others. Salts of games that left, or whose seat another game took, are refused from then on. One cipher lasts for every connection of an open world (`Renew` picks a new salt per connection), so frames read before a break are refused again after it.
- **Only a carrier.** The DLL never reads the messages and knows no players, only seats: who plays on a seat is for the game scripts to tell each other. `mp_world_receive` hands out one inbox entry at a time: `kind=seat` with `seat` and `others` after every (re)connect, `kind=in` or `kind=out` with the `seat` that came or went, `kind=message` with the sender's `seat` and the text, `kind=chat` with the `name` of an admin and the line the relay said for them, and `kind=story` with the `rev` a Raid World's story has now (see [World story on the relay](#world-story-on-the-relay-raid-worlds)). `mp_world_send` sends to one seat, or to every other game with -1, and refuses while the game holds no seat. `mp_world_status` gives `state` (`idle`, `connecting`, `open`, `reconnecting`, `failed`), `seat`, `others`, `ping` and `error`.
- **The relay reads the chat.** `mp_world_say` mirrors a line of the world's chat to the relay as the text frame `chat <line>` (`WorldSession.Say`, through the writer's queue like a frame, `RelayWorldChannel.SendText`), which the relay keeps for the world's admins and passes to nobody; the line itself still goes to the others sealed through `mp_world_send`. The relay's `chat <name>` + tab + `<line>` text frame, what an admin said in the World Admin tool, becomes the `chat` inbox entry (`TakeChat`); a DLL that does not know the frame logs and ignores it, as it does any text it does not know.
- **Trades.** `mp_trade_commit` (world, trade id, partner's id, both offers as one line) hands a trade to the relay on a thread of its own (`WorldTrades`): the SHA-256 of the offers, and the offers sealed (`TradeSeal`: AES-GCM with a key derived from the world's token, the trade id bound in), so the relay compares hashes and never reads the offers; then it asks the relay about once a second until the trade is committed or cancelled, 150 s at most. `mp_trade_state` reports it (`trade`, `state`: sending, waiting, committed, cancelled or failed, `reason`, `error`), `mp_trade_cancel` cancels a trade the relay has not committed, and `mp_trade_done` marks it applied. `mp_trade_pending` fetches the committed trades this player has not marked done, which `mp_trade_pending_list` hands out unsealed, one `trade=<id>	<offers>` line each after the state. Sealing needs the open world's token, which `WorldSession` keeps for the world it opened (`OpenWorld`), also while it reconnects.
- **A world code in the wrong place.** A world code given to a PvP join says where worlds are entered.

### Keyboard

RGSS only knows buttons, so the text screens get what is typed from the DLL. While `mp_typing` is on, `GameWindow` hands the window's `WM_CHAR` characters and `WM_KEYDOWN` presses to `Keyboard`, and `mp_take_typed` hands out what came since the last call: `keys=`, how many keys went down, then the characters, Enter, Backspace and Escape among them as `\r`, `\b` and `\e`, and the clipboard's text in place of Ctrl+V. Windows makes `WM_CHAR` only when the message loop translates key presses; until the first one arrives, `Keyboard` works the characters out from the presses itself (`ToUnicodeEx`, which leaves the keyboard's state alone), which combines no accents typed as dead keys. The in-game log does not tell which way it went, the DLL's `Multiplayer` log does ("the game window gets typed characters"). While typing is on, `Link.typing` also sets `$mgq_text_input`: mods whose hotkeys read Windows directly, as Party Sheet of the MGQ-Paradox-Mod-Collection does, check it, since `Capture` only reaches the game's `Input`.

### Background

RGSS pauses a game whose window is not in front: RGSS301.dll keeps the last `WM_ACTIVATEAPP`'s flag and its frame loop waits while it says inactive. A live battle cannot wait for either player, so `GameWindow` subclasses the game's window (class `RGSS Player`) and tells RGSS the game is always active; `Multiplayer.rb` turns it on at start (`mp_keep_running`). The keyboard only reaches the window in front, but gamepads reach every game, so `Background.guard_input` has `Input` report no buttons while another window is in front. It wraps `Input` through `core_hooks.rbx` once the first scene starts, since the game's plugins, the gamepad one among them, load after the Patch folder, and `Capture` reads the buttons past it while it holds them (`Capture.reading?`). Once the last screen gives the buttons back, `Input` reports none until the next `Input.update` (`Capture.released?`), so the press that closed it, such as the Escape that closed the chat box, never reaches the game too, as when a battle's wait took it for leaving the battle. Each `Input.update` asks Windows once whether the game is in front, since the game's `Graphics.frame_count` raises until the game first sets it.

When the game closes, the in-game log's last line says how (`closing_text`): "the game closes", "it was quit" for `exit`, or the error that ended it, so a log that stops without one tells a crash. A second `SceneManager.run`, which only F12 starts, is logged as a reset.

Without it, a live battle's messages stay in the message window, which moves on by itself after 90 frames on both sides.

## Worlds (`world.rbx`)

**Flow.** *Multiplayer*, below *Continue* on the title screen (`Window_TitleCommand#make_command_list`), opens `Scene_MpWorlds`, laid out like Mod Config Remake: the worlds at the left, the chosen one's details at the right (who made it, players online of its seats, whether it is hidden, and everyone who ever joined, those online marked), then *Create new world*, *Join a hidden world*, *Change your name* and *Back*. The list is every world the directory shows the player plus the worlds on this PC it no longer has, Raid Worlds first (drawn in red, `MGQ_MpWorld::RAID_COLOR`, also above favourites and in place of a featured world's gold; one the directory no longer lists keeps its place and colour by its `world.ini`), then favourites (marked `*`), then the featured worlds (drawn in gold, `MGQ_MpWorld::FEATURED_COLOR`; only the relay's admins make them, with the admin tool outside this repository), then those played last, then by name (`MGQ_MpWorld.entries`); it is fetched when the screen opens and every 10 s, and keeps the cursor on the world or command it was on. A world offers *Enter the world*, *Mark as a favourite*, *Delete my saves of it*, and for its creator *Remove a player*, *Delete the world for everyone* and, for a hidden world, *Copy the world id*. *Enter* asks for the password only while this PC has no folder of the world and the world has a password. While a directory action runs, the screen says what it waits for and holds the input.

**Forms.** While the list points at *Create new world* or *Add a hidden world*, the right side shows its form (`MGQ_MpWorld::Form`, drawn by `Window_MpWorldForm`), and confirming moves the cursor into it; Cancel goes back to the list and keeps what was filled in. Up and down move between rows, left and right between the two fields on one row, and the lines at the top show the hint of the field the cursor is on. A switch (`:switch`, drawn and turned by `Window_MpWorldForm` for the world screen and the story's choices alike, `draw_switch`, `turn_or_move`) shows its outcome between arrows; confirm turns it onward, an arrow turns it unless it points at the other field of the switch's row, and one that cannot be used buzzes. *Create new world* has *Name*, *Password* (may be empty, as in the other form), *Max Players* (digits only, 2 to 32, 4 at first), *Hidden*, the switch *World type* (Classic or Raid, fixed once created), the switch *Sharing companions* (Off, Story companions, or Story companions and battle recruits; greyed out for a Classic world, whose `needs` is a block), the checkboxes *Shared save* and *Player's choice* and *Save* (*Save* is greyed out until *Shared save* is ticked; opens the save screen, see [Starting save](#starting-save-world_save_distributionrbx)), all in the panel *World*, which keeps the form on one page; *Mods* and the checkbox *Allow data mismatch* in *Game data*; the description, a box of several lines, in *Description*; and *Create the world*. A field's `group` names its panel, and `Window_MpWorldForm#places` lays the panels out below each other, as `Window_MpWorldDetail` draws a world's details; both share `MGQ_MpWorldPanels`. *Edit the world*, offered to a world's creator and the relay's admins, opens a third form in place of the details (`Form.edit`, kept as `@forms[:edit_world]` only while it is open) with what may change after a world was made: *Max Players*, *Mods* and the description. `mp_dir_edit` (world, seats, description, mods) sends them to the relay's `POST /v1/worlds/<id>/edit`; a world's folder takes the new seats into its code the next time the world is entered from the list (`World#describe`). *Join a hidden world* has *World id* (32 characters of 0-9 and a-f, pasted with Ctrl+V), *Password* and *Join the world*, which opens the lock by the id and enters the world, fetching its starting save when it has one. Sending a form that is not complete names the first field that is wrong and moves the cursor there. The scene is the same object when the text or save screen returns, so the forms keep their values and the cursor goes back to the field it left from.

**Typing.** A text box is typed into in place: confirming it takes the keyboard (see [Keyboard](#keyboard)) and shows a caret; Enter keeps the text once it passes the field's check (`Form#check`: not empty, Max Players in range, a whole world id), otherwise the reason shows and the typing goes on; Escape puts the text back; characters the field does not take buzz. The form takes the cursor again only once OK and Cancel are let go, so the Enter that ended the typing does not start it again. A button or direction pressed in a frame no key went down, as only a gamepad does (directions by their first frame, since a held arrow key reports its direction without going down again), moves the typing to `Scene_MpText` with the game's letters shown; so does confirming a text box while the game's window is not hooked (`Background.running?`), since the keyboard cannot reach the game then. What the text screen hands back passes the same check.

**Names and passwords.** The first visit asks for the player's name unless the Discord mod knows it (`MGQ_Multiplayer::Player`: the name chosen for Multiplayer, else the one on Discord; PvP battles pass it on too). `Scene_MpText` shows the text in a box, as stars for a password, and takes the keyboard: Enter confirms, Escape leaves, Backspace removes the last character. The game's own letters stay hidden until a button is pressed in a frame no key went down, and show from the start when the game's window is not hooked or a form's text box asked for them. A key that types also moves the game's own buttons, such as Z for OK, so the letters ignore the buttons in a frame the keyboard was used. Cancel on the letters with nothing typed leaves.

**On disk.** `Patch/Multiplayer/Player.ini` keeps the player's key (`mp_new_id`), chosen name and bound keys (`MGQ_MpHotkeys`); `Patch/Multiplayer/Favourites.ini` the favourite worlds' ids. Each world entered has `Patch/Multiplayer/Worlds/<id>/` (`mp_world_id`), with `world.ini` (name, world code, the directory's id of the world, its `type` and `share` once the directory told them, when it was made and last played) and `Save/`. *Delete my saves of it* deletes the folder, and with it that this PC knows the password.

**Raid Worlds.** A world is Classic or a Raid World, which its creator picks once (`type`, see [Relay/README.md](../Relay/README.md)). `MGQ_MpWorld.raid?` is the one question every script asks (false outside worlds), and `MGQ_MpWorld.companion_sharing` tells how the open Raid World shares companions (`:off`, `:story` or `:all`; `:off` outside Raid Worlds), both from the open world's `World#raid?` and `World#companion_sharing`, which `world.ini` keeps. The details name the type, and for a Raid World how it shares companions.

**Its own saves.** Entering a world writes the player's own system save, then redirects every path below the game's `Save` folder to the world's (`Files`: the path-taking methods of `File` and `Dir`, and `Bitmap.new` for thumbnails), and loads the world's system save, or makes one (`System`): the Library, the system switches and the global system with the affection, which the game otherwise shares between all saves and loads once per start. The game names `Save/` in many places, its backups, thumbnails and temporary file included, so the paths are changed where they reach the files. Paths only move while a world is open, and a path such as `SaveData.ini` never does. The game's options live in each save, so they are unaffected.

- **Entering** loads the world's latest save, an autosave included, with the game's own `Scene_Load#on_load_success`. A world without saves goes back to the title screen, whose own `command_new_game` starts the new game, so everything the game and other mods do for one happens. Entering also takes a seat in the world's room (`mp_world_open`), which tells the directory the player is online.
- **Leaving** happens whenever the title screen starts other than for that new game: after *To Title*, a reset or a game over. It leaves the room, writes the world's system save and puts the player's own back.
- **PvP battles** through the PvP battle screen are off while a world is open (`MGQ_MpBattlesPvp.available?`): a world keeps a connection of its own, and both would claim the Discord status. Its players duel instead (see [Duels](#duels-battles_duelrbx)), and the World overview's key (F11) opens the World overview.

## World story on the relay (Raid Worlds)

A Raid World plays one story, which the relay keeps: the counters it reads to tell which story is further, and the rest of the story sealed with a key from the world's token, which it never reads. The relay side is `Relay/core/story.js`, the DLL side `RaidStory` (`Network/World/RaidStory.cs`, `StorySeal.cs`, `DirectoryClient.Story.cs`) behind the `mp_raid_*` exports of `Exports/Exports.Raid.cs`. Classic worlds keep no story.

**Where it is kept.** On Cloudflare in the world room's own Durable Object (`World` in `worker.js`), never in the directory object: the Worker sends `/v1/worlds/<id>/story…` straight to the world room, which answers it. One storage value holds the counters and the sealed story (one row written per write), and one value per part holds its checkpoint. The world room asks the directory whether a player holds the world's token (`/internal/member`), keeps the answer (the world's type, the hash of its auth key, the players let in, each with when) and checks later requests itself, asking again for a player let in over 10 minutes ago; a removed player is forgotten, an answer that came while a removal or the deletion ran is not kept, and deleting the world deletes its story, again after a request that was under way. The directory refuses the question while the world's starting save is still being uploaded (409 `pending`), since the sweep of a stale world removes only its entry. The Node relay asks its directory in-process, removes a deleted world's story and pools again after a request that was under way and keeps the stories in memory or in the SQLite tables `stories` and `story_checkpoints`.

### Routes

Every route takes the player's key in `X-MGQ-Player` and the auth key in `X-MGQ-Auth`, as the world room does. 404 for a world the directory lacks, 400 for a missing key, 401 for a wrong auth key, 403 for a removed player, 404 with code `classic` for a Classic world. Each answers JSON.

| Request | Body | Answer |
|---|---|---|
| `GET /v1/worlds/<id>/story` | | 200 *state* with `blob` |
| `POST /v1/worlds/<id>/story` | `{"base": <rev>, "counters": {...}, "blob": "<sealed>"}`, at most 300,000 characters | 200 *state* without `blob`, with `"accepted": true`; 409 *state* with `blob`, `error` and `code`; 400 for wrong fields, 413 for a longer body, 429 with code `rate` past 20 writes at once, then one per 3 s, per player |
| `GET /v1/worlds/<id>/story/checkpoint/<part>` | | 200 the checkpoint as *state* with `blob` and `part`; 404 with code `none` when the world keeps none of that part; 400 for another part |
| `POST /v1/worlds/<id>/story/route` | `{"route": "ad" \| "mr" \| "chaos"}` | 200 *state* with `blob` and `"locked": "<route>"`; 409 *state* with `blob` and `code` |
| `POST /v1/worlds/<id>/story/companions` | `{"ids": [<actor id>, ...]}`, 1 to 500 ids of 1 to 99,999 | 200 *state* with `blob`; 413 past 2000 shared companions |

**State** (every answer): `rev` (counts every change: a write, a route lock, a grown companions list), `wrev` (the revision of the last write, whose sealed story `blob` is), `p`, `r1141`, `r1142`, `r1143`, `clear` (the finished routes the last write named), `part` (`1`, `2`, `3`, `ad`, `mr` or `chaos`), `route` (locked: `none`, `ad`, `mr` or `chaos`), `done` (the routes the world finished, in the order it did), `end` (`{"map", "x", "y"}` or `null`), `comps` (shared companions' actor ids, ascending), `checkpoints` (the parts with a checkpoint), `at` (when the last write came, milliseconds since 1970), and `blob` (the sealed story in base64, empty before the first write) where the table says so. A world nobody wrote for answers `rev` 0, `part` `1` and an empty `blob`.

**Counters** of a write: `p` (variable 1001), `r1141`, `r1142`, `r1143` (the route variables; at most one above 0), whole numbers of 0 to 1,000,000; `clear`, the routes whose clear switch is on in the story (7096 `ad`, 7097 `mr`, 7039 `chaos`), each once; `end`, the story teleport's endpoint `{"map": 1-9999, "x", "y"}`, `null` to forget it, left out to keep the one the relay has.

### Writes

- **Accepted** when `wrev <= base <= rev` (the write built on the last sealed story; a route lock or a companion since does not turn it away) and the counters are not behind the story's. Else 409 with the world's state and sealed story, and `code` `rev` (built on an older story), `behind` or `route` (see Route lock); the game takes the world's story, and for `behind` and `route` drops its own step.
- **The story's order** (`storyKey`): `[returned, p, step, cleared]`, compared left to right, where `cleared` is how many routes `clear` names, `returned` how many of them are not the route under way, and `step` the counter of the route under way (the route whose variable is above 0), 0 for none. A finished route returns the world to the Great Decision with 1001 at 39 and the route variables at 0 (CE 154, 267/268), which `returned` counts as further. So the order grows through `p` 39 → AD 1 … 76 → AD 76 with `clear` `ad` → `p` 39 with `clear` `ad` → MR 1 … A write with the same counters is accepted: most events move no counter, and the revision keeps writers apart.
- **Parts** (`partOf`): the route under way if any, else Part 1 while 1001 < 19 (Tartarus Escape sets 19), Part 2 while 1001 < 34 (the Middle Chapter's epilogue sets 34), else Part 3, the Great Decision included (1001 is 40 there before the route variable is set, and 39 after a return).
- **Checkpoints**: a write that changes the part keeps the story before it (its last write) as that part's checkpoint, replacing an older one of the same part (Part 3's is the newest Great Decision). So a part's checkpoint is the story as the last write before the part's ending left it; a game should write the story before an ending's first step. Nothing is kept from a world without a sealed story yet.
- **Route lock**: the first route locked wins (`POST …/route`, the same route again answers 200). Refused with 409 and `code` `route` while another route is locked or under way, `finished` for a route in `done`, and `closed` for `chaos` until both `ad` and `mr` are in `done`. While a route is locked, until the world returned from it, a write must be on it or return from it (no route under way, the locked route in `clear`) and may finish no other route the world did not play, else 409 `route`: so a further story from another route (a loaded save) cannot throw the route's progress away or finish a route nobody played. Until the world's own story is on the locked route, a write with no route under way goes on too, since the player who locked it writes the route's first step only once their scene ended. A write with a route variable above 0 locks that route; the lock ends once a write shows no route under way and the locked route is in `done` (the return to the Great Decision).
- **Finished routes**: every route a write names in `clear` joins `done`, which only grows.
- **Shared companions** only grow; adding ids the list holds writes nothing.

### Push

After every change the relay sends the text frame `story <rev>` to every game in the world room (`storyText`). Games never send it. Released DLLs log it as an unknown text and drop it. This DLL (`WorldSession.TakeStory`) hands it to the game script as the inbox entry `kind=story` with `rev=<rev>` (`mp_world_receive`); the game script fetches the story when that revision is above the newest it knows (`rev` of `mp_raid_story_state`), so its own changes do not make it fetch again.

### Exports

Each starts a request on a thread of its own and returns at once; one request of each kind runs at a time. Text arguments are UTF-8 and null-terminated; `world` is the world's id (`mp_world_id`), and the world must be the open one, whose token seals the story. Win32API notation for `Link::EXPORTS`:

| Export | Arguments | Returns |
|---|---|---|
| `mp_raid_story_fetch` | `'p'` world | 1 started; 0 while a fetch runs, without a player, outside that world |
| `mp_raid_story_post` | `'plpp'` world, base revision, counters, story | 1 started; 0 while a write runs, without a player, outside that world, or for counters, a base below 0 or a story (empty or over 200 KB in UTF-8) that are not as they should be |
| `mp_raid_story_state` | `'pl'` (READ_ARGUMENTS) buffer, size | the length, negated when the buffer is too small; 0 before anything was asked |
| `mp_raid_story_headers` | `'pl'` (READ_ARGUMENTS) | as `mp_raid_story_state` without the story's text, for polling while a request runs |
| `mp_raid_checkpoint_fetch` | `'pp'` world, part (`1`, `2`, `3`, `ad`, `mr`, `chaos`) | 1 started; 0 while one runs, without a player, outside that world, for another part |
| `mp_raid_checkpoint_state` | `'pl'` (READ_ARGUMENTS) | as `mp_raid_story_state`, 0 before the first checkpoint fetch |
| `mp_raid_route_lock` | `'pp'` world, route (`ad`, `mr`, `chaos`) | 1 started; 0 while a lock runs, without a player, outside that world, for another route |
| `mp_raid_companions_add` | `'pp'` world, actor ids separated by commas | 1 started; 0 while an add runs, without a player, outside that world, for ids that are not whole numbers above 0 |

**Counters** for `mp_raid_story_post`: `key=value` pairs separated by semicolons, `p`, `r1141`, `r1142` and `r1143` required (whole numbers of 0 or more, at most one route variable above 0), `clear` optional (finished routes separated by commas: `ad` for switch 7096, `mr` for 7097, `chaos` for 7039), `end` optional (`map,x,y`; empty to forget the endpoint; left out to keep it), e.g. `p=40;r1141=12;r1142=0;r1143=0;clear=mr;end=1650,30,51`. **Story**: the text the game script packed (`coop_story.rbx` `pack`: deflated, base64, one line); `StorySeal` seals its UTF-8 bytes (AES-GCM, HKDF key from the token with info `mgqmp world story v1`) and unseals the relay's `blob` back into it.

**`mp_raid_story_state`** is a message (header lines, a blank line, the text) like the other states:

- The newest story the relay told of the world the last request started for, from any answer, a newer revision never replaced by an older one; a request for another world forgets the story before, and a late answer of the world before is not kept: `world`, `rev`, `wrev`, `p`, `r1141`, `r1142`, `r1143`, `clear`, `part`, `route`, `done`, `end` (`map,x,y`, missing for none), `comps`, `checkpoints` (lists separated by commas, missing when empty), and the story's unsealed text after the headers (empty before the first write, and for a story that does not open with the world's token, which is kept without it so the game can write over it). A write the relay took leaves the text that was written.
- One header per kind of request that ran, with its revision, code and error: `fetch` (`busy`, `done`, `failed`), `post` (`busy`, `accepted`, `conflict`, `failed`), `lock` (`busy`, `locked`, `taken`, `failed`), `companions` (`busy`, `done`, `failed`); each with `<kind>_rev` (the revision the answer told: an accepted write's own), `<kind>_code` (the relay's code: `rev`, `behind`, `route`, `finished`, `closed`, `rate`, …) and `<kind>_error` (why it failed, for the player). A `conflict` or `taken` already holds the world's story in the headers and the text.
- A request that cannot reach the relay tries again after 2, 5 and 10 s, then fails. A write whose answer was lost comes back on its next try as 409 `rev` with the world's story; when that story's text is the write's own, it counts as `accepted`.

**`mp_raid_checkpoint_state`**: `state` (`busy`, `done`, `none`, `failed`), `part`, `error` when failed, and when done the checkpoint's story headers (as above, `rev` and `wrev` both the revision of its write) and its unsealed text after them.

### In the game (`world_story.rbx`)

`MGQ_MpWorldStory` follows the story after the map's update (`tick`), behind menus and battles too, while a Raid World the directory knows is open (`active?`); the world's id is its `directory_id`. Classic worlds never reach it.

- **Fetching** (`start_fetch`): as the world opens (`note_world`), after a loaded save or a new game (`loaded`, after `load_game_without_rescue` and `setup_new_game`; not after `extract_save_contents`, which a duel's end calls to put the game back), on the relay's push and once a minute (`POLL_FRAMES`) in case a push was lost. The push is the inbox's `kind=story`, which `overworld_sync.rbx` hands to the route `MGQ_MpOverworldSync::STORY_FIELD` marked `:relay` like an admin's chat line (`pushed` ignores a message without it); it fetches only a revision above the newest the game knows. While a request runs, the DLL's headers are read every `STATE_FRAMES` (`mp_raid_story_headers`), and the whole state with the story only once a request's header ended (`ended?`), which takes it; a state whose `world` is not the open world's is never taken, and a request that ended in it is asked again (`other_world`).
- **Laying it over** (`take_pending`, `take_world`): a newer story (`wrev` above the last taken) waits until the player's own map event, battle, transfer or duel ended (`quiet?`). A world without a story, or with one this game cannot open (`wrev` above 0, no text), takes the player's (`force_post`, on the world's `wrev`), unless another route is locked there or the relay refused the player's step: then the game waits for the world's story (`wait_for_world`, mode nil). Judged afresh (after a load, a new game or entering): a player further than the world (`key_of`, the relay's `storyKey`) whose story the relay would take (`continues?`, the relay's route rule) writes their story as the world's, the furthest story winning (`start_ahead`), but never again after the relay refused that step (`pending[:drop]`), which takes the world's story instead; a player behind the world and in an earlier part (`part_of`, the relay's `partOf`) is behind (`fall_behind`, mode `:behind`, notice once per world): they write nothing, and `world_catchup.rbx` puts them on their part's checkpoint and moves them on by their level (see [Catch-up](#catch-up-world_catchuprbx)); a player the catch-up moves into the world's story (`MGQ_MpWorldCatchup.joins_world?`, after `refetch`) takes it whatever their part, and one whose own progress reaches the world's part (`check_progress`) fetches again, unless the catch-up keeps them behind below their gate (`kept_behind?`, `MGQ_MpWorldCatchup.keeps_behind?`), as when the world returns from a route to the player's part. Otherwise the world's story is joined with the player's own values (`MGQ_MpCoopStory.mix` with every chest of `MGQ_MpCoopStoryRewards::CHESTS` and the map's, `chest_list`); variables no story carries, such as lists, stay the player's (`keep_unsent`). What the player changed since the story they built on (`@base`; before the first story taken, the one they brought in, `entry_story`, so progress made while the relay could not be reached is not lost) stays where the world's story did not change it (`keep_own`), so a step being written is not lost.
- **What is the player's own** in a Raid World: `PERSONAL_SWITCHES` and `PERSONAL_VARIABLES`, affection, awakening, the roster, every chest, the side (switches 4/5, after the Great Decision too, `personal_switch?`) and every choice's outcome (`MGQ_MpCoopChoices.personal?`: `raid_keys`, the switches and variables of every branch, 7002/7003, 7007/7008, 7016/7017, 1029, 1056, 1061, 1065 among them). The chests that hold the story's key items (`MGQ_MpWorldCatchupData::CHESTS`, `world_chest?`) are the world's: their self switches go with the story, so each opens once for the world; one the player opened stays open under the world's story or a checkpoint (`keep_open_chests`) and goes with their next write.
- **Writing** (`post_due?`, `send_post`): only in mode `:world`, never while a newer story waits or another write or lock runs. A change of the story's progress (`PROGRESS_VARIABLES`: 1001, 1140-1143 and the areas' progress; `PROGRESS_SWITCHES`: the castle's bosses and the route clears 7096/7097/7039; `check_progress` every `CHECK_FRAMES`) goes out after `SETTLE_FRAMES`; other changes of the shared story, compared with `@base` (`scan`, `scan_due?`) every `SCAN_FRAMES` after an event of the player's own or their telling ended, after progress, kept changes or an accepted write (`@watch`), else every `IDLE_SCAN_FRAMES` while no event of theirs runs (for parallel events), never during the player's telling, go `DEBOUNCE_FRAMES` (5 s) after the last one, at most `LONGEST_WAIT_FRAMES` (30 s) after the first; changes of the player's own values write nothing. While the player tells the story nothing is written but the route lock, a write going again included, since other games would take the scene half done; when the telling ends, what it changed goes out after `SETTLE_FRAMES` (`told`). A story transfer of the player's telling (`story_transfer`, after `Game_Player#perform_transfer`) is the story's endpoint, written then; the place a telling ended is the endpoint of the next write (`note_telling`). The write holds the counters (`counters_text`: the route under way alone, the clears, `end` only when it moved and until a write carrying it is accepted) and the story without the player's own values and chests (`story_text`, `story_lists` and `pack`; without what it turned off when larger than `MAX_FULL_BYTES`), on `@wrev`. Accepted, the story written is the new `@base`; refused (`conflict`), the world's story comes back to lay over the player's, dropping every change of the player's since their base for the codes `behind`, `route`, `finished` and `closed` (`DROP_CODES`), keeping those the world lacks for `rev`, after which what was kept goes again on the new revision; failed, it goes again after `RETRY_FRAMES`, `RATE_FRAMES` for `rate`.
- **The Great Decision**: a route the world has not taken (`route` `none`) is locked (`mp_raid_route_lock`) before the write that starts it, when the relay would lock it (`lock_route`: not finished, the third way once both others are; else the write goes alone and the relay judges it); refused, the world's story comes back without the player's step, the companions the player's own branch of common event 380 took away come back (`restore_roster`, noted in `decision_list`) before the world's route plays its own half, the notice names the world's route and the player teleports to the story. The game's own choice of the routes (common event 380, `decision_choice?`) offers only `decision_routes` (`before_command`, a `Game_Interpreter#execute_command` hook, which gives the interpreter a copy of the list with the other branches left out, `decision_list`): the locked route while the world has not finished it, else those not finished, the third way only once both others are and never before, so nobody reaches its bad end. `Game_Interpreter#ssw` reads `:ed1` and `:ed2` from the world's clear switches 7096 and 7097 (`world_ending`), which the third way's dialogue asks. A player the world's story carries past the decision (`followed`) gets `MGQ_MpCoopChoices.raid_decision`: the screen of choices offers the world's route alone and plays the player's own half (`raid_decision_commands`): the outcome's part of common event 380 without its transfer (the companions a different side changes), the side switches, and the screen faded in.
- **The return**: the Reaper's reset menu (common event 265, which drops companions) never runs. At a finished route's credits (`route_credits?`: the Angelic Dominion or Monster Realm route under way with its clear switch on, which the credits on map 1021 set) `before_command` puts the game's own return of the player's side in its place (`return_list`, `return_commands`: common event 267 or 268 without its scripts, so without the companions it adds: the Final Chapter's reset 154, 1001 = 39, the warps, variable 57 = 407 and the transfer through map 544), so the players on the credits' map come along as the telling's transfer takes them. At the Reaper's offer in Hades (common event 149) the call is replaced by a fade-in with a notice (`reset_list`); anywhere else, such as the Chaos route's bad end on map 1889, whose event runs by itself and only left the map through the menu, also by Erase Event, and the player teleports to the story: one player must not take the whole world back. The next write names the cleared route, which the relay marks done and whose lock ends. Every other game whose route under way the world finished and left (`wait_for_return`: in its `done` or `clear`, the world's route under way another) plays its own half first (`returned`, `play_queued`: common event 154, which takes the route's passes, resets its maps' chests and the route's progress, variable 1002, and the transfer to the Great Decision's hall through map 544), with a notice, and then takes the world's story, wherever the world went since.
- **Watching a telling**: once a player on the map whose scene the player watched (`Scope.watches?`) stops telling (`note_teller`), the player's own story events wait (`awaits_teller?`, through `MGQ_MpCoopEvents.hand_over`) until the world's story of a later write was taken, at most `AWAIT_TELLER_FRAMES` (10 s), since the teller's write takes seconds to arrive and the scene would play again.
- **Saves** hold the story as it is, the world's laid over the player's own (`MGQ_MpCoopStory.save_contents` returns the contents unchanged in a Raid World).

### Catch-up (`world_catchup.rbx`)

`MGQ_MpWorldCatchup` carries a player behind a Raid World's story along, on the tables of `world_catchup_data.rbx` (`MGQ_MpWorldCatchupData`, generated by `GameScript/Tools/raid_data.rb`). It runs after the map's update (`tick`), every `CHECK_FRAMES` while the player is free (`MGQ_MpWorldStory.quiet?`), and whenever `world_story.rbx` lays a story over the player's (`carried`).

- **Behind** (`behind`, from `MGQ_MpWorldStory.fall_behind`): the player gets the checkpoint of their own part (`mp_raid_checkpoint_fetch`, `mp_raid_checkpoint_state`), laid over their story with their own values (`take_checkpoint`, `MGQ_MpCoopStory.mix` with `chest_list`, `keep_open_chests`) while they are still behind, once per save (the notes' `checkpoint`), so side quests played while behind stay. A part the world keeps no checkpoint of (the world's first story was further), or whose checkpoint this game cannot read, leaves the player on their own story there (`without_checkpoint`), or moves a player moving on to it into the world's story. A failed fetch, which may name no part, is tried again after `RETRY_FRAMES`. A player on a route the world never took moves into the world's story at once.
- **Story held** (`holds_story?`, asked by `coop_events.rbx`): while behind, a story event the player starts does not start and tells them "Reach level N to continue the story." (`refusal_text`, once per event in `REFUSE_FRAMES`, `held_behind`); story that runs by itself (a map event's autorun, a common event's) waits silently, so a teleport onto its map cannot loop; a talk turning into story ends there (`guard`). Side events, talks, shops, chests and battles run.
- **Level gate** (`gate_reached?`, `reached?`): the highest base level among the player's characters against their part's gate (`PARTS`); a character at their own `max_level(:base)` below the gate (another mod's cap) counts as reaching it. Reached, the player moves on (`move_on`, notice "Level N reached: catching up to ..."): to the next part the world played (`world_parts`: Parts 1 to 3, the routes in `done`, the route under way) that has a checkpoint (`next_part`), else into the world's own story (`join_world`, `MGQ_MpWorldStory.refetch`). They never play the part's ending. A player leaving a route the world finished first gets the personal half of the world's return to the Great Decision (`return_from_route`, `MGQ_MpWorldStory.returned`). Then the rule repeats, one part per gate.
- **Rows by story position** (`review`, `passed?`): a row counts once the story is in the row's part or a later one and the row's marks hold, so an optional event nobody played is never past; a route's rows also once the route is finished (its clear switch), whatever part the story is in, since the return clears its marks; side content by its marks alone. The row's side (before the Great Decision the side the player chose then, noted in the save's notes, `note_side`) and the choices' outcomes among its marks (`MGQ_MpCoopChoices.personal?`) are always read from the player's own story. Each row counts once per save (`ledger`, `$game_system`'s `@mgq_mp_catchup`, per world). A row the player's own game played gives nothing, since the game gave it; one a story laid over theirs carried them past (`carried`: what was passed before is noted done first) gives what it gives, as long as its marks tell that its event ran (`carries?`, the row's `ran`; one only there to play stays the player's own to play, and is noted done once their own story is past it): the story's skills and items (`REWARDS`); the companions a first playthrough loses for good (`REMOVALS` with `first`, variable 912 at 0) leave, unless a join of the same look comes after each of those removals or at the same place (`after?`: a later place, or later in the same event's list); temporary leaves only order the joins. Choices the story carried the player past go through the screen of `coop_choices.rbx` as before (`MGQ_MpWorldStory.followed`).
- **Key items and story chests for everyone** (`world_items`): every key item row (`KEY_ITEMS`, given or taken) and story chest (`CHESTS`) the world's last story is past (`@world_told`) comes to every player once, whatever their part; a chest the world opened shows open for them too (`open_chest`).
- **Companions by level** (`companions`, `note_join`, `bring_waiting`): a join the player's story is past waits for its gate (notes `c` carried, `o` held back) unless its companion is there or the player's own game left them out. Once the player's level reaches the gate the companion joins as the game's own join does (`bring_in`: `persona_change`, `recover_all`, `add_actor`, standby by the game's own cut when the team is full, `add_stand_actor` while a story's temporary party plays), raised to the gate unless the join is a first one at the start level; a companion there already is raised to a carried join's gate. Never twice (`in_roster?`; the roster is read once per look, `roster_view`). A removal passed after a join waited drops it. A story event of the player's own that hands out a companion during their telling before the gate of that companion's join in the player's part (`hold_join?`, around `Game_Party#add_actor` and `add_stand_actor`) is held back, notice "<name> joins you once you reach level N.", and the join waits for its gate.
- **Shared companions** (`MGQ_MpWorld.companion_sharing`): every companion new in the player's roster (`note_roster`) goes to the world's list (`mp_raid_companions_add`, at most one write per `SHARE_FRAMES`): the story's companions with *Story companions*, every one with *battle recruits* too. Each companion on the list (`comps`) joins a player who lacks it on reaching its gate (`share_in`): a story companion at its first join's gate and persona, a battle recruit at its database start level; never one the player had, nor one their story took away for good (a lasting removal passed on a first playthrough, `taken_for_good`).
- Notices go to the notification box (`MGQ_MpNotices.message`). A loaded save or new game forgets the session's requests (`loaded`); the notes stay in the save.

## Raid boss pools on the relay

Each story boss of a Raid World has a pool the whole world wears down together (plan section 9: pool x5, an untouched pool full again within the hour). The relay side is `Relay/core/bosses.js` (the admin routes `Relay/core/raid_admin.js`), the DLL side `RaidBosses` (`Network/World/RaidBosses.cs`, `DirectoryClient.Bosses.cs`) behind the `mp_raid_boss*` exports (`Exports/Exports.RaidBosses.cs`). Classic worlds keep none.

**Where it is kept.** Beside the story in the world room's own Durable Object: one storage value per boss (`boss:<key>`), written only by a counted report and an admin's reset; regeneration costs no writes, since every read computes the hit points from the last report. Access is checked as for the story (`/internal/member`, kept by the world room), the admin routes ask the directory (`/internal/raid-admin`); deleting the world deletes its pools. The Node relay keeps them in memory or in the SQLite table `boss_pools`.

**Pool.** In kills, not HP, since each host's difficulty and mods set the boss's max HP: `max` 5, `regen` 5 kills an hour; hit points now = `min(max, hp + (now - at) * regen)`, 0 for a defeated boss, which never fills up again. The key is the one the game sends (the milestone or troop key), 1 to 64 characters without control characters or spaces at either end, percent-encoded in the address; a world keeps at most 500 pools.

### Routes

The player routes take the player's key in `X-MGQ-Player` and the auth key in `X-MGQ-Auth`, with the story routes' refusals (404 no world, 400 missing key, 401 wrong auth key, 403 removed player, 404 code `classic`). Each answers JSON.

| Request | Body | Answer |
|---|---|---|
| `GET /v1/worlds/<id>/bosses` | | 200 `{"bosses": [*pool*, ...], "max": 5, "regen": 5}`, the pools a report touched, by key |
| `GET /v1/worlds/<id>/bosses/<key>` | | 200 *pool*; a pool never reported is full; 400 for a key that is none |
| `POST /v1/worlds/<id>/bosses/<key>/report` | `{"battle": "<id>", "dealt": <share>}`, at most 4 KB; `battle` 1 to 64 letters, digits, `_` or `-`; `dealt` a number of 0 or more, counted up to 1 | 200 *pool* with `dealt` (the kills taken off: 0 for a repeat or a defeated boss), `emptied` (this battle's report emptied the pool; true again when the same battle is sent again) and `repeat` (the battle was counted before); 400 for wrong fields, 413 for a longer body and with code `full` past 500 pools, 429 with code `rate` past 6 reports at once, then one per 20 s, per player |

**Pool**: `key`, `hp` (now, three decimals), `max`, `regen` (kills per hour), `defeated`. Each pool remembers its last 32 battles, so a report sent again (a retry after a lost answer) counts once. A report on a defeated boss changes and writes nothing. A report that leaves less than 0.0005 kills, which answers as 0, empties the pool. Once emptied, the boss stays defeated for the world until an admin resets it.

**Admin routes** (`ADMINS`): the admin's key in `X-MGQ-Player`, else `player` in the address (GET) or the JSON body (POST, at most 4 KB); 403 for anyone else, the creator included, 404 for no world, 404 code `classic` for a Classic world.

| Request | Answer |
|---|---|
| `GET /v1/worlds/<id>/raid` | 200 `{"story": <state without blob>, "bosses": [*pool* with "at", "reports", "by"], "max", "regen"}` (see the story's *state*; `by` is the player id whose report emptied the pool) |
| `POST /v1/worlds/<id>/raid/bosses/<key>/reset` | 200 the full *pool* with `reset` (whether there was one); the pool is deleted, so it is full and undefeated |
| `POST /v1/worlds/<id>/raid/route/clear` | 200 the story's *state* without `blob`, with `cleared` (whether a route was locked); a cleared lock counts the revision up and pushes `story <rev>`. A world whose story is on that route already locks it again with its next write |

### Push

After every counted report and every reset the relay sends the text frame `boss <hp> <key>` to every game in the world room (`bossText`), the hit points with up to three decimals, the key last since it may hold spaces. Released DLLs drop it as an unknown text. This DLL (`WorldSession.TakeBoss`) hands it to the game script as the inbox entry `kind=boss` with `key=<key>` and `hp=<hp>` (`mp_world_receive`).

### Exports

Each starts a request on a thread of its own and returns at once; one fetch and one report run at a time. Text arguments are UTF-8 and null-terminated; `world` is the world's id (`mp_world_id`), and the world must be the open one. A request that cannot reach the relay tries again after 2, 5 and 10 s, then fails; a report tried again counts once, by its battle id.

| Export | Arguments | Returns |
|---|---|---|
| `mp_raid_bosses_fetch` | `'p'` world | 1 started; 0 while a fetch runs, without a player, outside that world |
| `mp_raid_boss_report` | `'pppp'` world, boss key, battle id, the share dealt as text (such as `0.75`, a point for decimals) | 1 started; 0 while a report runs, without a player, outside that world, or for a key, battle id or share the relay would refuse |
| `mp_raid_boss_state` | `'pl'` (READ_ARGUMENTS) buffer, size | the length, negated when the buffer is too small; 0 before anything was asked |

**`mp_raid_boss_state`** is a message (header lines, a blank line, the text) of the world the last request started for; a request for another world forgets the pools before:

- `world`; `max` and `regen` once a fetch came back.
- One header per kind of request that ran: `fetch` and `report` (`busy`, `done`, `failed`), each with `<kind>_code` (the relay's code: `classic`, `rate`, `full`, …) and `<kind>_error` (why it failed, for the player).
- For the last report: `report_key` and `report_battle` from its start; once done `report_hp` (the pool's kills left), `report_dealt` (the kills it took off), `report_emptied`, `report_defeated` and `report_repeat` (`1` or `0`). The game's story goes on after the battle only once the pool is empty: `report_emptied=1`, or `report_defeated=1` when another battle emptied it first.
- After the headers one line per pool the relay told (a fetch replaces them all, a report its own), by key: `key`, tab, the kills now (filled up at the pool's rate since the relay told them, at most full, three decimals), tab, `max`, tab, `1` when defeated else `0`.

### In the game (`battles_raid_pool.rbx`)

`MGQ_MpRaidPool` counts a Raid World's story boss battles against their pools. Classic worlds, and a player whose story is in an earlier part than the world's (`MGQ_MpWorldStory.mode` other than `:world`), are never touched.

- **Which battles count** (`set_up`, after `BattleManager.setup`; `refusal`): the map's interpreter runs a map event (`in_map`, around `Game_Map#update_interpreter`) whose battle command started the battle (`at_command`, around `command_301`), so a co-op guest's battle, a random encounter and a common event run on its own never count; the troop is the last phase of its fight (`MGQ_MpRaidBosses.last_phase?`) and not in `UNPOOLED` (the Great Decision, which sets the world's route, and the fights whose events put a party of their own together, add companions for the fight alone, change a persona, split the party or change the party's size, none of which can be put back); neither a Hades rematch (switch 97) nor the Colosseum (switch 87) runs; the story has not beaten the milestone (`BEATEN`: the variables and switches the story writes after each milestone's last fight, alternatives split by `|`, conditions by `&`); and the event wrote none of the story's progress before the battle (`moved_progress`, `MGQ_MpWorldStory::PROGRESS_VARIABLES` and `PROGRESS_SWITCHES`), which the relay would refuse to take back.
- **Keys**: a fight a milestone lets the player take in any order has a pool of its own under its boss's name (`FIGHTS`: Sisel, EX-Kyubi and the other Chaos route quartet, the five Deadly Sins vessels, Goddess, Demon and Fiend); every other pool is its milestone's, with ` (cap <n>)` where milestones of several caps share a name, such as `Tamamo (cap 61)` (`key_of`). The two routes' Doppel Lukas share one, so on the second route its pool is defeated already.
- **The story as the event found it**: as a map event starts on the map's interpreter (`event_started`, after `Game_Interpreter#setup`), the switches, variables and self switches are copied (`raw_story`), and how the map looks and sounds (`raw_scene`: the battle BGM, the BGM and BGS playing, the player's transparency, the followers' visibility, the pictures shown, and the screen's tone, brightness and weather), which a boss event sets up for its battle and puts back only after it; as its battle counts, what changed since (`writes_since`) is kept with the battle (`Fight`), whatever wrote it before the battle, every earlier phase of the event included.
- **Reporting** (`battle_ended`, before `BattleManager.battle_end`, installed at `SceneManager.run`): the share of a kill (`dealt`: what the troop's enemies that appeared lost of their max HP together, at most 1, so a boss's helpers never count as a whole kill) with a battle id of its own (`new_battle_id`) through `mp_raid_boss_report`. A lost battle reports too and keeps its fight for the game's retry (`retrying`, around `BattleManager.retry_battle`), which counts as a battle of its own; the chat log tells the kills left once the relay answered (`watch_loss`). A battle whose starter became another player's guest (the Raid tie-break) reports nothing: its host does.
- **Holding the event**: after a won battle the event's next command waits in the interpreter's fiber (`before_command`, a `Game_Interpreter#execute_command` hook; `tick` when the event had no command left) for the relay's answer, at most `WAIT_FRAMES` (10 s), with a notice. The answer of that battle id only (`answer_for`) decides (`outcome_of`): an empty pool (`report_emptied`, or `report_defeated` when another battle emptied it first) lets the event run on, and the story moves on for the world through the story's normal write; a report the DLL did not start, one that failed or no answer in time let it run on too, so the relay never blocks the story. The game's autosave after a won battle, which `process_victory` makes after a retry since no event waits for its result then, waits for the answer too (`auto_saving`, around `DataManager.auto_save_game`) and is made once the answer decided (`release_save`), so no save holds the event past a boss that falls back.
- **Falling back** (`fall_back`) while kills are left: what the event changed before the battle is put back past the game's setters (`restore`), and how the map looked (`restore_scene`: pictures shown since are erased, one the event erased stays erased, and the BGM and BGS come back unless the same one plays); the map's interpreter is cleared as the game's defeat clears it, its fiber left behind, the event unlocked, and erased until the map is entered again when its page, with the story put back, starts by itself (`AUTORUN`), since it would start again at once; the notice and the chat log say "<boss> falls back. Raid HP left: <hp>/<max>." What the event did besides the story and the map's look, such as a transfer or a companion it added, stays.
- **The push**: `overworld_sync.rbx` hands the inbox's `kind=boss` to the route `MGQ_MpOverworldSync::BOSS_FIELD`, marked `:relay`; `pushed` tells the chat log about another battle's report or a reset (a full pool, "<boss> stands again", `push_line`), not about the player's own report of the last `OWN_PUSH_FRAMES`.
- Not used yet: `mp_raid_bosses_fetch`; nothing shows the pools on the map.

## Starting save (`world_save_distribution.rbx`)

A world's creator may start every new player from one of their own saves instead of the opening, or let each new player choose (*Player's choice*, the directory's `choose` flag). Both are chosen once, when the world is made, and never change.

- **Picking.** `Scene_MpStartSave` is the game's own `Scene_Load`, whose choice is handed back instead of loaded. `files_of` writes the system save first, then names the save, its thumbnail when it has one, and the newer of the game's two system saves (`SaveSystemData.load_filename`), under the names a new player gets them by: `Save01.rvdata2`, `Save01.png` and `SystemSave.rvdata2`. So the starting save is the world's first save, and the world's system save (Library, medals, affection) is the creator's.
- **The creator** gets the files copied into their folder of the new world (`place`) and enters it from them, with nothing fetched back.
- **A new player** fetches them (`fetch`, a directory action of kind `start`) when entering a world whose list entry, says `ready` and whose folder holds no save yet. `check` then loads every object of the save and the system save before the world opens, since the game quits when a system save fails to load. A class the game lacks, from a mod only the creator has, is named in the message, and the files are thrown away, so the next entry fetches them again.
- **Player's choice.** Entering a `choose` world whose folder holds no save yet (`ask_start?`) asks first: *From the creator's save* (only when it is `ready`) fetches as above, *At the beginning* starts a new game, and *From one of my saves* opens `Scene_MpStartSave` again and copies that save with `files_of` and `place`, as the creator's own copy is made. The copy waits for the world screen's next frame (`@own_start`), since entering loads the map, which must not happen while the scene starts. The creator is asked too when they made the world without their own save. Once the world holds a save, nobody is asked again.
- A world whose creator is still uploading (`pending`) cannot be entered.

## World mods (`world_mods.rbx`)

A world's required (`!`) mods must be the same in every game that enters it. The relay keeps a catalog of the admins' mods, which only they fill in the World Admin tool (see [Relay/README.md](../Relay/README.md), mod catalog): each mod's current version, the versions seen before, and a SHA-256 per file, `.rb` files without carriage returns (`ModHash`), so a checkout with Windows line ends and the release asset hash the same.

- **Kinds.** `link`: a script of a release on the admins' GitHub, which the game downloads from GitHub and installs where its copy is, else as `Patch/<file>`. `zip`: a link to a zip of a release, laid out as in `Patch`. `upload`: a mod of several files an admin uploaded, which the relay hands out as a zip. A zip's files go to their paths inside `Patch` (`ModInstaller`, which refuses any path that leaves it); the DLL tells the script `zip` for a link whose release file is one (`CatalogMod.ScriptKind`).
- **The check.** The catalog comes with the list (`mp_mods_list`). `differing` hashes this game's copy of each required mod (`mp_mod_hash`) and names the version the hashes are, "unknown" or "not installed"; a mod outside the catalog is compared with the creator's hash (`modHashes` of the world, sent with create and edit), and a copy that differs can only be fetched from its author. Without a catalog or a creator's hash, being installed is enough, as before. While the list is fetched again the DLL still hands out the catalog it had (state `loading`), which the script keeps using; a link the relay could not read yet (no version, no files) is listed for admins only and left out by the script, so it counts as a mod outside the catalog. The creator's hashes leave out names longer than 100 characters, as many as the relay takes.
- **Download and restart.** *Download and restart* installs every differing catalog mod (`mp_mods_install`, all files checked and staged before any is written, every replaced file put back when one cannot be written, and a zip mod's files that only an older version shipped deleted while they are still that version's), stores the world in Player.ini (`rejoin`), starts `Game.exe` again once this game has ended (`mp_restart_game`) and quits; the title screen then opens the world screen and enters that world again, checking anew. Under Wine or Proton `mp_restart_game` answers 2 and starts nothing: the game stays open, keeps `rejoin` and tells the player to restart it by hand, which then enters the world. An outdated game started again offers the update on the title screen instead (`MGQ_MpWorld.offer_update`), as a Discord invite into a world does. Updates thus reach a player only on their next entry.
- **Settings.** The world's `settings`, Mod Config values of every mod it names, required or listed (no key bindings, no `:personal` rows), are applied whenever a save of the world is loaded or started (`load_game_without_rescue`, which the newest translation's replaced `load_game` still calls), and Mod Config Remake shows them greyed out (`ModConfigRemake.world_keys`) until the player leaves the world. The creator's own stay unlocked: in their own world (`own_world`), the button *Use My Settings for This World* that `world_mods.rbx` adds to Mod Config Remake's rows (pressed through the handler of its key, set on every `Window_ModConfig`) sends their current values through `mp_dir_set_settings`, at most 2000 characters (options past them are left out, logged and named in the help line and the notice), and reports the answer as a notice. Creating and editing a world send no settings; the relay lets the creator and its admins replace them. A game applies only the settings of options a world may set (`world_option?`) in a mod's group of its own Mod Config, never the game's own options, key bindings or personal rows (`apply_values`). The relay's latest settings win: before the creator's game sends settings, and before it tells another player whose state names other settings than its own (unless it read them less than `CHECK_FRAMES` ago), it reads the world's settings on the relay through a fresh list (`check_relay`, `mp_dir_refresh`, started only while no list is being fetched and no request of its own runs). Settings someone else set there, such as an admin, become the world's, the creator's options and every player's (`take_relay`); settings the creator's game wants meanwhile keep only what the creator changed, joined to the relay's (`merged_text`), and only the creator's own switch turns sharing on or off. The DLL keeps one directory action's answer for the world screen and the world's settings alike, so each claims the action it starts (`Directory.claim`) and takes only its own answer (`Directory.mine?`); a request starts only once nobody waits for the last answer (`Directory.free?`), and settings whose answer gave way to another request are sent again. A world's settings are noted only as the world opens (`start_world`), so an entry refused for its data, a full world or a password leaves nothing behind, and the edit form starts from the settings the relay took from this game last while the list may be older (`settings_of`).
- **Options for the catalog.** Mods build their Mod Config rows as they load, often from constants and method calls, so only a running game knows them. Whenever the world screen reads the list and the player is an admin, `report_options` sends, once a session per mod, the options of each catalog mod this game has installed, whatever its version, unless the relay holds the current version's options already or those of the version this copy is (`opts` line of `mp_mods_list`): the version `row_for` found by the copy's hashes, or an empty one for a copy that matches no version the catalog knows, such as a build of the admin's own; the relay keeps any version's options until the current version's arrive. The options are the same rows a world may set (`world_entries`), each with its name without the `[Mod]` prefix, its type and default from `NWConst::Config::DEFAULT`, and its choices from its `:values` (an array or a proc) or else `DATA`, named by `DATA_TEXT`, as tab-separated lines through `mp_mods_options`. A mod that offers no such rows sends an empty list, so the relay knows it offers none. The DLL posts them on a thread of their own (`SendModOptions`), outside the actions, and only logs the answer. The World Admin tool lists them in its mod settings dialog.

## On the map

`overworld_sync.rbx` carries the world's messages; `overworld.rbx` shows what the player sees of them. While a world is open, the sync's `Graphics.update` hook runs every frame in every scene: it reads the world room's inbox (`mp_world_receive`, at most 64 entries a frame) and tells the others what changed about the player, so nothing piles up during a battle or in a menu.

- **What each game tells** (`Me`): one message of `key=value` lines with the player's id and name, the party leader's sprite and index (the vehicle's while in one), map, tile, facing, speed (`real_move_speed`, dashing included), whether the player is hidden, and what the player does (`Me.scene`): `battle`; `event` (a message or a running event on the map, or a novel scene, which requests and defeat scenes are); `away` while the game's window is not in front, unless in a battle or an event; a menu screen by its class name (`SCREENS`: `items`, `equip`, `shop`, `casino`, `library`, else `menu`); `sailing` or `flying` in a vehicle; or `map`; and the player's ping (`Ping.told`). It goes to everyone whenever any of it changed, and only then, so a player standing still sends nothing: every incoming message counts against the relay's free plan.
- **Newcomers** (`Inbox`): after every (re)connect (`kind=seat`) the game tells everyone everything, and keeps each of the others for 15 s (`REJOIN_FRAMES`, `Peers.wait_for_all`), in which they tell back; a game that went (`kind=out`) is kept as long (`Peers.wait_for`, its ghost hidden) and is the same player when its id tells again, on any seat, even while the relay still holds its old seat (`Peers.moved`, which forgets the old seat without a notice), so a party and a battle outlast the relay's limit per connection, and only who stays away has left (`Peers.tick`, `Peers.remove`; `Peers.present` lists those whose connection stands, `Peers.named` and `Peers.with_id` find one, `Peers.on_this_map?` tells one on the player's map); when another game comes in (`kind=in`), it tells that seat everything, and that game does the same, so both know each other at once. A message marked by a field a script registered (`route`: `chat`, `npcs`, `story`, `chest`, `pevent`, `coop` or `battle`, and through the map's gate of a Raid World `map_npcs`, `map_pevent`, `map_pscene` or `map_coop`) goes to that script, even when it names a map, as the leader's place does; any other message with a `map` is a state, which makes or updates the sender's `Peer` by seat; `kind=out` forgets it. The relay's push of a Raid World's story (`kind=story`) goes to the route `story_rev` (`STORY_FIELD`) without a sender, marked `:relay` as an admin's chat line is. Joining and leaving show as notices.
- **Ghosts** (`Game_MpGhost`, a `Game_Character` with `@through`): one per player on the current map, made where they stand. Every frame on the map (`Game_Map#update`) it takes their sprite, speed and visibility, and walks one tile toward where they stand, along the longer axis first, at their speed; more than `CATCH_UP_TILES` (3) away, or after a map change, it moves there at once. It triggers nothing, since only the player and events check triggers.
- **Sprites** (`Spriteset_Map#update`): a `Sprite_Character` and a `Sprite_MpGhostLabel` per ghost, made and freed as ghosts come and go. The label shows the name, and before it an icon of the game's icon set for what the player does (`STATE_ICONS`): battle 451 (crossed swords), event 4 (speech bubble), typing 4 (the same; `MGQ_MpActions.scene` says so while the chat box is open), menu 183 (open book), items 3059 (potion), equip 3905 (hammer), shop 3874 (coin), casino 220 (cards), library 3240 (red book), sailing 4069 (anchor), flying 3836 (wing), away 6 (Zzz); none while walking. `Sprite_MpWorldStatus` at the bottom left shows the last notices for 4 s each and, from `mp_world_status` every 30 frames, "Reconnecting . . .", "Connecting . . ." or why the connection failed.
- **Pings** (`Ping`): every 30 frames the status's `ping` becomes the player's own, shown right above their head (`Sprite_MpOwnPing`), and after the name on each ghost's label the ping its player told. The others are only told a ping that moved by 20 ms (`PING_STEP`) and a quarter (`PING_SHARE`) of the one they know, so jitter sends nothing. Colors: up to 100 ms green, up to 200 ms yellow, then red (`PING_COLORS`). `ui_actions.rbx` keeps `HEAD_ROOM` free above the head for it. Labels of characters on one tile stack upwards (`Sprite_MpGhostLabel#show` takes the room the labels before it took and returns its own), above the player's own ping on the player's tile, so two players standing together no longer draw their names over each other.
- **Registry**: the scripts that load after the sync join it at load time, each in a `begin` block before its hooks: `route(field)` for their messages, `state_fields` to add to the state message, `busy_scene` for a state of their own (the chat's `typing`), `on_tick` for every frame, `on_observe` and `on_leave` to hear of every state and every player leaving, and `label_line` for the line above a ghost's name. A failing block is logged once and left out; the others still run. Every state carries the marker field `state=1` (`STATE_FIELD`), which no route may be named like: a message with it is a state, any other goes to its route, so a state field may share a route's name. No message carries two marker fields, so the order of the routes decides nothing.

## The world never pauses (`core_async.rbx`)

In single player the map stops whenever another screen is in front: a menu, a shop, a battle or a story (novel) scene. In a world it goes on, so what others see of the player and what the player comes back to never waits for them.

- **Behind which screens** (`behind?`): every screen but the map itself, the title and the game over, while a world is open and a map waits on `SceneManager`'s stack. The map clears that stack whenever it starts, so a map on it is the one the player left and returns to; screens reached from the title never qualify.
- **What runs** (`tick`, from a `Scene_Base#update_basic` hook, which every screen's frame calls, battles and novel scenes included): `$game_map.update(false)`, so events move, background (parallel) events and common events run, ghosts walk (`overworld.rbx` hooks the same method), and the map's screen effects go on; and `$game_timer`, except in a battle, which runs it itself. The player does not move, and the map's main event, which drives whatever the player is in, never runs here.
- **What waits** (`hold?`, a `Game_Interpreter#execute_command` hook): while the tick runs, a command in `HELD_CODES` yields its interpreter's fiber until the map runs it again: messages, choices and inputs (101-105), party changes (129), transfers and vehicles (201, 206), music, sounds and movies (241-246, 249, 261), everything in 301-399 (battles, shops, name input, menu, save, game over, title, and actors' changes that would reach into a running battle), and scripts (355), which may do any of these. An event that starts by touching the player, or autoruns, only marks itself as starting; the main event picks it up once the player is back on the map. Events outside the tick, such as a battle's own, never wait.
- **Field music**: the game's map refresh plays the field's music when a switch changed it (`need_refresh_autoplay_field`), which would cut into a battle's, so the tick leaves that refresh to the map.
- **The live map** (`Spriteset_MpLiveMap`): a menu whose background is the picture the map took on leaving (`SceneManager.background_bitmap`) shows a `Spriteset_Map` instead, updated every frame, its viewports below everything the menu draws (z -300 to -200) and dimmed like the picture. Menus that make their background themselves, such as the casino and the warp screen, keep theirs.
- **No freeze between the map and menus** (`instant_switch?`, `leave`): leaving a screen freezes its picture (`Graphics.freeze` in `Scene_Base#terminate`), and the next screen fades in from it (`Graphics.transition` in `post_start`, 10 frames, the map 15). Nothing updates meanwhile, and even a transition of no frames takes about 117 ms (measured in game), so the world stood still for a moment at every menu. While a world is open, switching between the map and menus skips both: the screen keeps its last picture until the next screen draws its first. Battles, story scenes and the title keep their fades.

## Parties (`coop.rbx`)

**The party** (`Party`). Every state message also carries the player's party id (`party`) and whether they invite (`invite`), so a party needs no message of its own. Inviting lasts 15 s (`INVITE_FRAMES`, from the wheel in `ui_actions.rbx`), or a minute once it names a player from afar (`NAMED_INVITE_FRAMES`, from the World overview), who sees it in their notification box (`ui_notices.rbx`), and makes a party of one with a new id, which the invite line above the player's own head (`Sprite_MpOwnLine`) and above their ghost on the others' screens shows. Accepting takes the inviter's id. Anyone can read that id in a member's state, so naming it is not enough: the leader admits a player who names it only while the invite reaches them (`Party.admit`, `invite_reached?`, which still holds for 3 s, `LATE_FRAMES`, after a join ended the invite), tells whom it admitted in its state (`party_members`), and every member takes that list from the leader (`Party.adopt`). A member is who names the party and either made it or is on the list (`Party.member?`); a player who only names it is sent `kick=late`. A game sees another join its party when they become a member (`Party.update`), which also ends its invite. An invite nobody took forgets its party of one, and leaving the world leaves the party. Ghosts outside the party are see-through (`STRANGER_OPACITY`), party members' names green. `Party.members` and `Party.leader` are what the party scripts below build on.

**The party's messages** (`route`, `take`, `tell`). The party scripts (`coop_events.rbx`, `coop_npcs.rbx`, `coop_story.rbx` and `battles_coop.rbx`) register their fields with `MGQ_MpCoop.route`, which registers the same field with `overworld_sync.rbx`. A message is handed on only from a member of the party (`Party.member?`) and with the party's own id; the scripts keep only checks of their own, such as who the Map Owner or the leader is. `MGQ_MpCoop.tell(seat, field, value, fields)` adds the party's id to what they send.

A party holds at most four players (`Party::MAX_PLAYERS`), one per place of the Frontline; the wheel refuses to invite into a full party or to accept the invite of one (`Party.full?`), and so does `Party.join`. Two players may still accept before either sees the other join, so the leader sends `kick=full` to whoever joins one too many (`Party.admit`, `turn_away`). The invite's frames and targets live in `MGQ_MpCoop::Invite`, which duels share; `Invite.reaches_me?` is the near-or-named check of both. Only the leader invites more players (`Party.may_invite?`), and only the leader removes a member (`Party.remove`, from the World overview): it sends `kick=1` through the party's gate, and the member's game leaves the party when the message comes from its leader (`Party.removed_by`).

## Party or map (`coop_scope.rbx`)

`MGQ_MpCoop::Scope` tells `coop_npcs.rbx`, `coop_castle.rbx`, `coop_events.rbx`, `coop_gather.rbx` and `coop_scene.rbx` whom the player shares the map and the story with. Each question goes to `Scope::Classic` or `Scope::Raid`, by `MGQ_MpWorld.raid?` (`Scope.raid?`, false while `world.rbx` cannot tell, outside worlds and in Classic worlds), so Classic worlds behave as before.

| | Classic | Raid |
|---|---|---|
| `peers_here` | party members on the player's map | everyone on the player's map |
| `sync_host` (Map Owner of `coop_npcs.rbx`) | lowest `[since, id]` of the player and `peers_here`; the castle's maps: the party's leader (`MGQ_MpCoopCastle.owner`) | lowest `[since, id]` of the player and `peers_here`, the castle's maps too |
| `teller` | the party's leader | the player while telling; else of the players on the map (or the map the story takes the player to) whose state says `telling=1`, the lowest `[since, id]` |
| `viewers` | the synced members (`MGQ_MpCoopStory.synced_members`) | the players on the map, and those the story took along who have not arrived yet (`MGQ_MpCoopGather.taken_along`), whose `sm` equals the player's story progress as their telling started |
| `story_from?(peer)` | `peer` is the leader | `peer` is the teller, or nobody's state says `telling=1` yet (the teller's state and pages travel apart) |
| `watches?(peer)` | `MGQ_MpCoopEvents.following?` | the teller's `tsm` (or `sm` before it came) equals the player's own progress |
| `follows_teller?` / `leads_story?` | `follows_leader?` / `leading_synced?` of `coop_story.rbx` | another player is the teller / nobody else is |
| `sharing?` | `MGQ_MpCoop.in_party?` | a world is open |
| message gate | `route` (same party) | `route_map` (same map) |

- **The map's gate** (`MGQ_MpCoop.route_map`, `take_map`, `map_drop_reason`): a script registers its field, and the gate listens on `map_<field>`, so the party's gate and the map's never take each other's messages. A message is handed on (under its plain field) only from a known player who is on the player's map by their state, or whose message names the player's map, or the map the story takes the player to (`MGQ_MpCoopGather.story_map?`), in `mmap`. `npcs`, `pevent` and `pscene` are registered with both gates; the party chat, `kick`, invites, `chest`, `story`, co-op battles and duels keep the party's gate alone.
- **Sends** (`Scope.tell`, `MGQ_MpCoop.tell_map`): in a Raid World a message to everyone (`-1`) goes to each seat on the player's map instead of the whole world, since every message counts against the relay's free plan; it carries `map_<field>=<value>`, `mmap=<map id>` (the player's map unless the sender names another, as the story's `follow` does with the map it left) and no party id. Classic sends stay `MGQ_MpCoop.tell`.
- **The story in a Raid World** (`coop_events.rbx`): a story event starts only while no other player on the map tells the story (`hand_over`, notice "\<name> is telling the story here."); a talk turning into story ends the same way (`guard`). A player telling the story says `telling=1` in their state, alone on the map too, and `tsm`, their progress (`sm` values) as the telling started (`told_markers`), which decides who sees it: their pages (`say`, `done`) and scene changes (`pscene`) go to `viewers` alone, and only a player whose own progress matches takes them (`watches?`) and stands still while the scene plays on their map (`MGQ_MpCoopGather.blocked?`). A player whose story differs sees the NPCs move (the Map Owner's events on other pages stay their own) but not the scene. Two players who start telling at the same moment both say `telling=1` for a moment: the one with the lower `[since, id]` goes on (`Scope::Raid.first_teller_here`), and the other's event ends at its next command (`yield_story`, before every command of the map's interpreter). This tie holds only within 3 s of the telling's start (`TIE_FRAMES`) and on the map it started on (`note_telling_start`), since `since` starts anew with every transfer: a story that moves its teller onto a map where another player tells one goes on. While telling, `state_fields` also says `twb`, whether warping is banned where the player stands. Chests stay personal (`shares_chests?`): a Raid World's parties share no loot, and a `chest` message is ignored there. The pages a player follows are forgotten once another player tells (`forget_former_leader`, by `page_source_id`), and a page ends once its teller left or stopped telling 2 s ago (`page_teller`, `page_done?`).
- **Gathering in a Raid World** (`coop_gather.rbx`): nobody is gathered (`gathered?` is always true): whoever is on the map watches. A transfer of the teller's story takes everyone who was on the map along, and those an earlier transfer of the same telling took who have not arrived yet (`after_transfer`: `pevent=follow` with `mmap` the map it left; `take_raid` takes only `follow`). Until they show up on the teller's map, or the telling ends, they stay among the `viewers` (`taken_along`, forgotten when a telling starts), so the scene changes and pages told meanwhile reach them. *Teleport to the story* on the player's own row of the World overview (`MGQ_MpCoop::Offers.story_option`, in place of the teleport to the party's leader) goes to `MGQ_MpCoopGather.story_endpoint` once the player is free (`join_story`); it is closed to a player behind the world's story (`MGQ_MpWorldCatchup.holds_story?`), who could not play it there: the endpoint the relay keeps of the world's story (`MGQ_MpWorldStory.endpoint`, see [In the game](#in-the-game-world_storyrbx)), whose warp ban this game does not know, so the player keeps their own; while the relay keeps none, where this game last saw the story told (`note_story_place`, forgotten when the world closes), with the warp ban there (`story_warp_ban`): the player's own `warp_ban?` for their own telling, the teller's `twb` for another's; without `twb` the player keeps their own.
- **The party's story** (`coop_story.rbx`) is off in a Raid World: `MGQ_MpCoopStory.leader` is nil, `follows_leader?` false and `synced_members` empty, so no member borrows a leader's story and no leader tells one; a member who borrowed one gets their own back. The world's story takes its place (`world_story.rbx`, see [In the game](#in-the-game-world_storyrbx)), built on the same state model: `mix` (which takes the chests to keep), `story_lists`, `pack`, `unpack`, `decode_full`, `raw_state` and `set_raw`.

## Squads (`coop_squad.rbx`)

A party shares one single-player team: each player keeps a **squad** of their first characters, and the rest are cut. `share(position, count, max)` splits the Frontline's 4 places and the Backline's `max - 4` (`max` is the player's own `party_member_max`, 8 plus variable 56) between the players, one more each for the first ones while some are left over; the players are ordered the same way on every game (`ranked`): the leader first, then by player id. Outside a party, or alone in one, nothing is cut. Nothing here changes the game's party: a battle the player fights alone brings their whole team, and `party_member_max` and `max_battle_members` stay the game's, except in a Raid World (below). Variable 56 is the player's own in `coop_story.rbx`, since the game cuts its party list down to `party_member_max` on every change, so a leader's smaller value would drop a member's characters.

- **Followers** (`Game_Follower#visible?`, `follower_shown?`): in a party only the player's share of the Frontline (a follower's `@member_index` below the share; the trail sent to the others lists only those shown), or nobody in a party whose leader chose *Leaders Only* (`mode`, the option *Party Followers* in `$game_system.conf[:mp_party_followers]`, registered in the Mod Config Remake's `MOD_CONTENTS` or the game's `CONTENTS`; members read the leader's from their state's `follow` and may not change it). `tick` keeps the share and the mode each frame, which `follower_shown?` reads, and refreshes `$game_player` once either changed.
- **Ghosts' followers**: every state carries `trail`, the looks of the followers the player shows (`name*index|...`); `Game_MpGhost` in `overworld.rbx` keeps a `Game_MpGhostFollower` per look while the player is a party member, each stepping onto where the one before it stood, before the ghost steps, as the game's followers do, and gathered when the ghost jumps.
- **The formation screens** (`place_of`, `place_at`): both hooks wrap the game's own `draw_item`, so the game's and the translation's layouts stay, and only change how a row draws by its place in the squad. The menu's formation list (`Window_MenuStatus`) draws the squad's Frontline faces opaque and its Backline's translucent, as the game draws the Backline (`draw_actor_face`), and the cut characters monochrome: faces and icons through `monochrome` (a grey copy per face and icon, made once per session, since `get_pixel`/`set_pixel` over every pixel is slow) and texts and gauges through `text_color` and `grey`. The party edit screen (`Foo::PTEdit::Window_PartyMember`) colors rows through `change_color`: Frontline normal, Backline the system color, cut grey. Both draw a line above the first cut row.
- **In a Raid World** (`raid?`, from `MGQ_MpCoop::Scope.raid?`) every player has a squad, in a party or not (`squads?`): `own_share` is `RAID_SHARE`, one on the Frontline and two on the Backline, and the 4th place is cut, so the formation screens draw the line after the 3rd place and the 4th monochrome. Co-op battles take the same through `battle_share` (`own_build` sends the first 3, `arrange` gives every player 1 and 2); `share` stays as it is for Classic worlds and team duels, though a team duel takes only the squad (`team_build`, `raid_team`). Nobody follows on the map (`follower_shown?` is false for every follower, so the `trail` is empty).
  - **The team of four** (`fit_team`, `party_member_max`, `RAID_PARTY_MAX`): the game cuts its party list (a `Game_Party::BattleMember`) down to `party_member_max` on every change; a cut companion stays in `include_actors` and so waits on standby (the Pocket Castle). `party_member_max` is capped at 4 only for the `$game_party` that `tick` fitted first: on entering a Raid World, and for every new game or loaded save there (a new `Game_Party`), the companions past the 4th go to standby (`add_stand_actor`, then `move_stand_actor`, Luka always kept, `past_cap`, and swapped into the 3rd place when he stood past it, `luka_into_squad`) while the cap does not hold yet, so nothing depends on the order of the game's own cut. A team in a battle waits. A story's temporary party (`temp_actors_use?`) is its own standby list, so the cap never holds for it (a cut character would leave the story) and is lifted while it plays (`lift_cap`); the team is fitted again once it ends. Outside a Raid World the cap is lifted. A companion joining the full team, a recruit or `$game_party.add_actor`, lands on standby by the game's own cut (a recruit after the game's "The party is full" choice); items raising variable 56 change nothing below the cap.
  - **Battles of the player's own and duels** (`raid_battle?`: in battle, no co-op party formed, no team duel): `max_battle_members` is 1 and `bench_members` the next 2, both kept to the team's first 3 places (`in_squad`, since the game skips hidden members such as an eaten one), so the 4th never fights, not even as a reserve, and a skill reaching the Backline too (`item_target_members`) reaches only those 3. The game's Backline window and swap count from `max_battle_members`, which is why the Frontline is narrowed there. This covers a player left alone in a co-op battle (`go_solo`, `take_over`), who fights on with 1 and 2. A duel's team (`MGQ_MpBattlesPvp::Team.build`) is the squad, `raid_team`, and its Frontline is 1 (`pvp_front`), so without the Backline only that one fights. Outside a battle `max_battle_members` stays 4.

## NPCs in a party (`coop_npcs.rbx`)

Players outside a party share no NPCs: each game moves its own, as in single player. Between party members on the same map, one game moves the map's events and the others follow it.

- **The Map Owner** (`owner`): of the party members on a map, the one who entered it first. Every state message carries `since`, when the player entered their map (`Me.map_since`, milliseconds by that computer's clock), so every member's game finds the same Map Owner without asking: the earliest `since`, the lower player id among equals. A member whose connection is down counts no longer (`party_here`), so they never hold the events still. It changes as members come and go. It has nothing to do with who created the world.
- **The Map Owner's game** (`lead`) moves events as the game does and sends, at most every 15 frames (`SEND_FRAMES`) and only when something changed, each changed event's x, y, facing and page index (`-1` for none, as when erased): `npcs=<map id>`, `party=<party id>`, `full=0`, `events=<id>:<x>,<y>,<d>,<page>;...` to everyone. A member who comes onto the map gets every event (`full=1`) to their seat. Other members block events walking on their own there (`Game_Event#collide_with_characters?`), never a forced route nor any event while the leader's story plays, since a story waits for the routes it moves its events on and a member in the way would hold it up for good, and events that approach the player go for the nearest member (`near_the_player?`, `move_toward_player`). Touching a member's ghost starts nothing, since only the player starts touch events.
- **The other members' games** (`follow`) take only the Map Owner's messages for their party and map, stop events moving on their own (`update_self_movement`), and walk each event toward its place, one step at a time within 3 tiles (`MGQ_MpOverworld::CATCH_UP_TILES`), at once farther away or after 60 frames stuck (`STUCK_FRAMES`); a full picture places every event at once. An event talking to the player, moved by the player's own events, or on another page than the Map Owner's, which means another story state, stays where it is. An event walking into the player there starts its touch event there.
- It runs from a `Game_Map#update` hook, so behind menus and battles too (see [The world never pauses](#the-world-never-pauses-core_asyncrbx)).

## The party's story (`coop_story.rbx`)

Outside a party every player plays their own story in their own world save. In a party, the members synced with the leader play the leader's: the player who made the party (`Party.leader`: the member whose id starts the party's id, else the lowest id while they are gone).

- **Who follows the leader's story** (`sync_state`, `check_sync`, `follows_leader?`, `synced_members`): every player tells how far their own story is in their state (`sm`: variables 1001, 1141, 1142, 1143; a member who borrows the story of a leader they are ahead of tells their own). Before the Great Decision (1001 below 40, `GREAT_DECISION`) two players are synced while at most 2 apart in 1001 (`SYNC_STEPS`); past it, while both are at 40 on the same route (the first of 1141-1143 above 0; the Great Decision itself sets 1143 to 1) at most 5 apart on it (`ROUTE_SYNC_STEPS`). Anything else is not synced: too far apart, one on each side of the Great Decision (as a player reset to it against one on a route), or different routes. The member decides after every map update, again whenever either side's progress changes, and tells the leader whose story they follow in their state (`ssync`: the leader's id, empty for none); a member who keeps the leader's story stays synced, as their story moves with the leader's. A member not synced plays their own story completely: no borrowing, catch-up or gifts (the leader's story messages are ignored, nothing waits), their own story events run (`MGQ_MpCoopEvents.following?`), and the leader's pages, scene changes (sent to `synced_members` alone) and gathering never reach them. Chests, the map, co-op battles, chat, trading, duels and the castle are shared all the same. Notices: "You and \<leader> are too far apart in the story; each of you plays your own.", "... are on different sides of the Great Decision; each of you plays your own story.", "... are on different routes; each of you plays your own story." for the member and the same with the member's name for the leader, who also reads "\<member> follows your story while in the party."; a member who starts following reads the borrowing notice "You follow \<leader>'s story while in the party."

- **What is borrowed**: the story as the game keeps it, `$game_switches`, `$game_variables` and `$game_self_switches`, read and written as raw data (`data_of`, `MGQ_MpGame.get` and `set` of `:data`). The game's own `[]=` would run its side effects: a switch in 1001-2000 adds or removes that companion, an awakening switch refreshes an actor, an affection variable writes through to `$game_global_system`.
- **What stays the player's own** (`personal_switch?`, `personal_variable?`): the side they chose (switches 4 Alice Chosen and 5 Ilias Chosen, `SIDE_SWITCHES`) until the Great Decision, which sets the side anew with the route, so after it they follow the leader's (`personal_switch?` takes the story's variables), configuration mirrored in switches (95, 445-447, 502), party membership (switches 1001-2000), awakening (switches 6000-6999, `AWAKENING_SWITCHES` to `AWAKENING_LAST`; the game's switches from 7000 tell which story bosses were defeated and belong to the story), where a game over returns them (variable 1002), monsters' friendliness (variables 2000-2999) and affection (variables from 3000, one per companion). Every join of a story with the player's own values (`mix`) keeps these.
- **Borrowing**: a member asks the leader (`story=ask`, every 2 s until answered, again whenever the leader changes), who answers with the whole story (`story=full`: `s` and `sf` the switches on and off, `v` the variables set, zero included, `ss` and `ssf` the self switches on and off; what the story never set stays out). The lists travel packed in one field `z` (`pack`: deflated and Base64), and a story still above `MAX_FULL_BYTES` (200 KB, the DLL's frame is 256 KB) leaves out what it turned off or set to zero and says so (`part=1`), so a member who catches up keeps none of their own values in its gaps. The member keeps their own story aside (`@own`) the first time and plays the leader's with their own values. The leader then sends what changed, at most every 15 frames (`story=delta`, found by comparing with the story last sent), to the whole party. Variables carry only numbers, strings and true or false (`encode_value`), so no message can make objects in the other game.
- **Getting it back** (`restore`): leaving the party, the leader leaving or changing, or becoming the leader gives the member their own story back, with their own values as they are by then.
- **Playing along** (`same_story?`, `behind?`, `@keeps`, `@recorded`, `own_story`): a member whose main story and route progress (`STORY_MARKERS`: variables 1001, 1141-1143) are no further than the leader's when they first borrow keeps what they play together. One as far along has every change of the leader's story they take recorded and laid over their own story when they get it back and in every save; one behind keeps the leader's story as they played it (`caught_up_story`), with their own value of every switch, variable and self switch the leader's story never set, such as a side quest only they played, and their own chests on every map (`MGQ_MpCoopStoryRewards::CHESTS`), so a chest only the leader looted stays shut for them. A member ahead gets their own story back unchanged. A companion who joins the leader's roster (`Game_Party#add_stand_actor`) while the leader's main event plays story on the map (`MGQ_MpCoopEvents.telling?`, `telling_party?`) is told to the party (`story=recruit`, `actor`), one the leader has already too, and joins the roster of every member who keeps the story and lacks them, unless only the other side gets them; one recruited outside the story, as after a battle, stays the leader's. What changes in a shop, a synthesis or a menu the story opens is never told, since those scenes are not the map.
- **Catching up** (`holdings`, `catch_up`, `coop_story_rewards.rbx`): the leader tells what of the story's rewards they hold with their story (`story=full`) and whenever it changes (`story=hold`, rebuilt and compared every 15 frames): `sk` the story skills Luka knows, his abilities included (`knows?`), `ac` the story companions in the roster, `it` the story items and key items with their counts, `side` "a" or "i". On first following the story, a member who was behind gets what the leader holds and they lack: the skills and companions, and the items, as many as the leader holds and one list of the story's events gives at most, summed over the lists (key items as many as the leader holds; equipment worn at the castle counts, `story_count`). After that only the story's own messages bring more: companions (`story=recruit`), items (`story=gain`) and skills (`story=learn`, which the leader sends when Luka learns a story skill while `telling_party?`, hooked on `Game_Actor#learn_skill`), so what the leader gets outside the story stays the leader's. The past catch-up covers the companions and skills the leader got from optional side events too, by design: the member takes over the leader's flags, so those events count as done for them. What waited before the whole story came (`drop_covered`) is forgotten where the story covers it: older holdings always, and for a member who just caught up the story's gifts, companions and skills, which they would get twice. Companions are read from the player's own roster (`roster_ids`, the party's `@include_actors`), past a story's temporary party, by their main persona (`main_id`, as the game's roster keeps every persona), and the game's roster never holds a companion twice; the game's switches 1001-2000 already read whether a companion is there.
- **Sides** (`MGQ_MpCoopStoryRewards::SIDED`, `GROUPS`, `due_groups`): a skill or companion only the events where the sides differ give before the Great Decision (`sided?`) never comes as it is, unless the Final Chapter gives it too (`ROUTE`, such as the companions the Great Decision brings with the route), which comes as the leader holds it once the story is past the decision; one the story gives while the sides still differ waits until then (`@route_waiting`, `take_route_rewards`), since the Great Decision brings its companions before the route's progress is set. A reward some event gives without a side, such as Morrigan at the Strategy Conference, comes as it is. Each such event the leader's story got past (`played?`) gives the member their own side's rewards once (`@granted_groups`), such as Angel Dance in place of Demon Decapitation at the first camp, or Eden at the Snow Shrine for Ilias's side where Alice's side fights her. An event counts as got past when everything one of its pages leaves in the story holds (`marked?`: the story variables it sets, else the switches and self switches it turns on), or when the leader holds a reward only that event gives, to either side (`only_from?`), as for the camps, which leave nothing; either side counts, since the Great Decision sets the leader's side anew. The member's side here is the one they chose before the Great Decision (`story_side`, `@own_side`), past it the leader's for one who never chose, so a member holds one side's rewards whenever they joined. A member as far along leaves out the events the story had got past when they joined (`@baseline_groups`). After the Great Decision the side switches follow the leader's route (`follow_route_side`, also when the route's progress arrives alone in a delta, which `apply` takes before the switches), and route companions come as the leader's story gives them. Run `ruby GameScript/Tools/story_rewards.rb "<game folder>\Data"` to write the table again; it leaves out the Final Chapter's events (the Great Decision, common events from 9000, lists that read a route's progress, every map from 1000 on) but for `ROUTE`, counts gold-only chests as chests, and companions who join by their switch (1001-2000) or a party set by `set_actors(...)` as joining. It reads the maps from 1000 on where the game keeps them (`map_folders`, as `DataManager.map_file_name` finds them: `Data/Map/Data` for 1000-1999, `Data/Map2/Data` for 2000-2999, each with its own `MapInfos.rvdata2`), such as the Chaos route's snow shrine where Puruel and Inuel join.
- **Choosing a side** (`ask_side`, `choose_side`): only the leader plays the Iliasville scene where the player takes Alice or Ilias along, so a member without a side gets the same choice in their own game once the leader chose and the member is free on the map outside the leader's story scene; the answer sets their own switch 4 or 5, brings in the companion that choice brings (`:choice` events: Alice or Ilias), and catches them up with their side's rewards.
- **The Pocket Castle's way out** (`PERSONAL_VARIABLES` 21-23, `MGQ_MpCoopCastle.arriving`): the castle's item notes where it was used in variables 21-23, and its way out ("Leaving the Pocket Castle") transfers there. They are each player's own, so the leader's never send a member elsewhere, and a member the party brings into the castle (its front gate, map 126, or a resident's map) from outside, by a story's call, its follow or a teleport to the leader, has them set to where they stood, as the item would. Before, such a member left the castle for a place of an old save, such as Iliasville.
- **Lent key items** (`lend_keys`, `return_lent`, `without_lent`): a member ahead of the leader gets none of the items and gold the leader's story gives (`story=gain`), but borrows the leader's key items (`RPG::Item#key_item?`) they lack, such as the one that opens the basement of Lily's mansion, so they can play the story along. The leader tells the key items they hold (`key_items`, `k=<id>:<count>,...`) with their story (`story=full`) and whenever they change (`story=keys`, checked every 15 frames); the member's game lends the difference to what they hold themselves (`@lent`) and takes back what the leader no longer holds, in one notice ("<Leader> lent you <item> for the story.", `key_list`). Once they get their own story back (`restore`), the lent items go back too, and a save made meanwhile, the autosave and a duel's snapshot included, leaves them out of its party (a copy of `Game_Party`). Since no save holds them, a member who crashed, loaded a save or came back from a duel borrows them again with the leader's story. A member who keeps the story gets key items to keep instead (see Catching up).
- **Held back** (`held_back?`, `hold_back`, `take_held`): what the leader's story gives or takes (`gain`, `recruit`, `depart`, `hold`) waits while a PvP battle runs, whose end puts the game back as it was before it, and until the member plays the leader's story again, as after a load or a duel; it is taken once they do (after the map's update), only from the leader who sent it, since another leader's story differs, and forgotten once the party is over. Chests other members open during a PvP battle wait the same way (`MGQ_MpCoopEvents.take_held_chests`). Gifts never count as what a chest the player opens at that moment gives (`MGQ_MpCoopEvents.granting`).
- **Saving** (`DataManager.make_save_contents`, `own_with_values`): while a member plays the leader's story, every save, the autosave included, holds their own story with their own values as they are. Loading a save or starting a new game (`extract_save_contents`, `create_game_objects`) brings its own story, so the member asks the leader again.

## The story's choices (`coop_choices.rbx`)

A member makes the story's choices for themselves, whatever the leader chose. The choices (`BRANCHES`, by the main story's progress 1001 from which each can be made): Alice or Ilias (7, switches 4/5), Amira in Iliasburg (9: ask her name, switch 2127 and Amira 540 joins, or kill her, switch 2108, after which she comes back), Magistea Village (17: defeat Lily, switches 2096/7017/2095, Lucia 167 joins, or defeat Lucia, 2097/7016/2094, Lily 163 joins; 2137/2138 and 1029 = 6), Plansect (24: the Priestess's side, Queen Bee defeated 7003, 1061 = 1, the Priestess 241 joins, or the Queen Bee's side, 2154/7002, 1061 = 2, Miria 245 joins; 1056 = 6), Succubus Village (27: Natasha's side, 7007, Natasha 288 joins with Lily, 2210, else 2211; or the mayor's side, 7008, the mayor 287 joins with Lucia, 2212, else 2213; 1065 = 3), the Spider Princess (30: 2280 and she, 334, joins, or the Queen Ants, 2281), the Sphinx (31: challenge her, 2090, or invite her, 153 joins) and the Great Decision (40).

- **What is asked** (`passed`, `made?`): every choice whose progress a catch-up or the shared story carries the member past, unless their own story made it (Amira only once she joined, so she is asked of every member who never had her join). The third way of the Great Decision only when the member's own save cleared both endings (`ssw(:ed1) && ssw(:ed2)`, as common event 380 asks).
- **Kept the member's own** (`personal?`, `MGQ_MpCoopStory.choice_key?`): the switches and variables of every choice the member's own story made are personal while they play the leader's story, like the side switches, so the leader's full story and deltas never overwrite them. The choices' companions (`CHOICE_COMPANIONS`) never come with the catch-up or a `story=recruit`, only with the member's own outcome (`skip_reason`).
- **The leader's offer** (`offer`, `Offers`): the leader's World overview menu of a member who is behind (no progress beyond the leader's) and does not follow the leader's story offers *Sync story*. The offer stands in the leader's state (`ssoffer`: member id and number) for a minute, until the member follows or leaves; the member answers it in the notification box. Declining tells the leader (`choices=declined`). Accepting opens the screen of choices; *Bring me there* lays the outcomes over the member's own story first (`apply`), then the member follows the leader by the offer (`offer_with?`, before the rule of `check_sync`), catches up as a member behind, and `borrowed` ends the offer.
- **The Great Decision**: the same route as the leader's catches up as usual. Another route (`start_route`): the member keeps the leader's story up to the decision (1001 = 39, 1140-1143 = 0, `MGQ_MpCoopStory.keep_and_leave`), catches up with nothing only the leader's route gives (`MGQ_MpCoopStoryRewards::FINAL`), and once free plays `decision_commands`: common event 154 (the game's own reset of the Final Chapter), the outcome's part of common event 380 (from 1002 = 111 or 112 to the transfer, with its party changes when 912 = 0), switches 4/5 and the route's variable = 1, and the transfer to map 430 or 431 (25, 19, facing up), whose event plays the route's start. The third way sets 7091, 7092, 92, 1001 = 40 and 1143 = 1 and goes to map 437.
- **Synced play** (`story_passed`): a delta that carries the shared story past a choice, or resolves one, which the member has not made asks their own outcome on the same screen with one row once they are free on the map.
- **The screen** (`Scene_MpStoryChoices`, `Window_MpStoryChoices`): a `Window_MpWorldForm` with a switch per choice (`MGQ_MpWorld::Form::Field` of kind `:switch`, `Form#turn`) and the line of what the picked outcome brings below it (Succubus Village follows the Magistea answer), then *Bring me there* and *Cancel* (a prompt: *Confirm*). Left/Right or Enter turn a switch, a click turns it or presses a button; the lines at the top name the choice and the keys. Every turn and the final choices are logged.
- **In a Raid World** (`raid?`) every choice's outcome is each player's own (`personal?`, `raid_keys`), and nobody offers a story sync (`Offers.peer_option` is nil). A choice the world's story carries the player past (`story_passed`, called by `world_story.rbx`) asks their own outcome, the side included; the screen stays while no leader is followed. The Great Decision's labels are `decision_routes` (the world's route after `raid_decision`, else `MGQ_MpWorldStory.decision_routes`), the third way by the world's clears (`both_endings?` reads 7096 and 7097), and its note says the whole world plays the route (`raid_decision_note`). Confirmed on the screen titled "The world's route", only the player's own half plays (`take_raid_decision`, `raid_decision_commands`, see [In the game](#in-the-game-world_storyrbx)).

## Events in a party (`coop_events.rbx`)

**What an event page is** (`kind`; `kind_of` for a list of commands): read from its commands when it starts, following called common events up to 5 deep. Only the commands that can run now count (`runnable`): a conditional branch on a switch or a variable (111) counts only when it holds now (`holds?`), its else only when it does not, and a branch on anything else counts whole. Called common events count the same way (`common_marks`, kept once per common event and depth for the frame, since the game's state decides what runs), so a shop calling a side quest's common event, as Vanilla's supply quest in Magistea and the other towns (common events 274-288), is a talk while that quest's step cannot run. What a choice's branch (402, 403) would make story counts as `:choice_story` instead: the page stays a talk that may turn into story (`may_tell?`), such as a blacksmith whose "Talk" moves a side quest on; a choice that gives items and sets the event's own switch stays a chest. While such a talk runs on the map, each command is watched before it runs (`guard`, a `Game_Interpreter#execute_command` hook): at the first that moves the story on (`story_command?`), a member's game ends the event there (on the list's closing empty command) with "Only <leader> can move the story on.", and the leader's game tells the party the story from there (`@telling`), without gathering. Exits hold the story's warnings in such branches (Iliasville's: "I need to be on time for my baptism", the village chief, the crying slime), which would make them story long after the warnings passed. Since the answer depends on the game's state, a page is sorted anew each time it starts.

- **The Pocket Castle** first (`MGQ_MpCoopCastle.resident?` in coop_castle.rbx, maps 227-230 and 268-278, not the side stories' copies of it): a companion's page (`companion_talk?`: its first speaker's name shows their affection variable, `\V[3000+n]`) and a page that calls one of the castle's services (`SERVICES`: Vanilla's shop, Papi's smithy, the maids' party saves, the item storage, Teeny's inn) or the coin shop (`@goods`) is a talk, whatever it sets: each player talks to them in their own game. The companions' scripts (`actor_label_jump`, presents, novel scenes) appear in the castle's story events too, so only the speaker tells them apart. This makes 728 of the castle's 745 story pages talks; the 17 left are its story events, such as the Sphinx's orb, the Elf Princess's room and Papi joining.
- **The leader's residents** (coop_castle.rbx): on the castle's maps the party's leader is the Map Owner of `coop_npcs.rbx` while there (`MGQ_MpCoopCastle.owner`), so the castle shows the leader's residents. A resident the member's own game shows nothing of (its event shows no page there, or one without a look) while the leader's page shows it, such as a companion only the leader recruited, stands as a see-through ghost (`Game_MpResident`, as see-through as players outside the party, `MGQ_MpOverworld::STRANGER_OPACITY`) with the look of the leader's page, walks where the leader's walks and starts nothing, since it is no event of the member's map (`update`, `ghost_of?`, drawn by a `Spriteset_Map` hook). Residents the member has stay their own to talk to; a resident whose page differs only (both show it) stays where the member's game puts it. Decided by the user on 2026-10-03.
- **Exits** next (`exit?`): a page the player starts (trigger 0-2) that transfers them without dialogue, battle, items, its own self switch or a story script is `:travel`, even when it sets switches or variables on the way. These are bookkeeping: the warp and library flags of a town's entrance, "Warp OFF", "Encounter OFF", or a flag such as Iliasville's north exit noting Sonya. The leader's game sets the same when it passes, so a member takes the exit in their own game instead of handing it to the leader. This turns 370 map pages from story into travel, 128 of them the world map's entrances.
- `:battle`: the page starts a battle (301) and shows no dialogue itself (101, 102, 105). The wandering monsters call common events before and after their battle that set variables, so the page alone decides.
- `:story`: it sets a switch or variable that is neither scratch (named like "General", "temp", "System Only") nor the player's own (see `MGQ_MpCoopStory.personal_switch?`); party membership switches 1001-2000 always count. Or it sets its own self switch without giving items, fights with dialogue, changes the party (129), uses vehicles (206), asks for a name (303), ends the game (353, 354), or runs a script that is not a talk's or travel's.
- `:chest`: it gives items or gold (125-128) and sets its own self switch.
- `:travel`: it transfers the player (201, or the scripts in `TRAVEL_SCRIPTS`).
- `:talk`: everything else: conversations, choices, shops, and the scripts in `TALK_SCRIPTS` (companions' own lines, choices, presents and affection, medals, the job change, synthesis, casino and party menus, and shops that list their goods in a script, `goods` or `@goods`, as the Casino's coin sellers).

Over the game's 28,500 event pages with commands this gives about 12,800 story, 6,100 talk, 5,100 travel, 2,600 battle and 1,800 chest pages. Most story pages among the conversations call a story common event; the largest group is the Chaos Labyrinth's.

**Chests** are the player's own. While the map's main event runs a chest page in a party (`started`), the items and gold it gives are kept, only the outermost of the game's nested `gain_item` calls for enchanted items (`enter_gain`). When the event ends (`Game_Interpreter#run`), the party is told `chest=<map>.<event>.<letter>` and `gains=<kind><id>x<amount>,...` (kinds `i`, `w`, `a`, and `g0` for gold). Every member who has not looted that chest in their own story gets the same items and has it marked looted (`MGQ_MpCoopStory.keep_own_self_switch`). The message also carries the first sound the chest played (`se=<name>,<volume>,<pitch>`, noted after `RPG::SE#play` while it runs, "Chest" by default, `played_sound`); a member who gets the items hears it and reads the notice with the first item's icon (`tell_chest_news`, `first_icon`, `MGQ_MpOverworldSync.notice` with an icon), once on the map: in a battle the items come at once and the sound and notice wait. A sound named like a path plays the chest's own. A member playing the leader's story sees their own chests: the chests' self switches of the map they are on are the player's own in every join of stories (`MGQ_MpCoopStory.personal_self_switch?`), and again whenever a map is set up (`map_entered`).

**Story scenes together** (coop_gather.rbx, `MGQ_MpCoopGather`, to which `MGQ_MpCoopEvents.take_party` hands `gather`, `come` and `where`). Party event messages carry `pevent=<kind>`, the party's id, and the leader's place: `map`, `x`, `y`, `d`. Only the leader's are taken.

- Members do not follow the leader to other maps; only story scenes bring them over.
- `where` and `come`: a member teleports to the leader on their own (`join_leader`, offered by `MGQ_MpCoop::Offers.teleport_option` on the wheel in place of the invite and on the leader's row of the World overview). The member asks `where`, the leader answers that member `come` with its place and warp ban (`answer_where`, `place_fields`), and the member comes as a called member does, without the five seconds (`answered`); an answer nobody asked for within `CALL_LAPSE_FRAMES` is dropped.
- `gather`: when the leader's main event starts a story scene (`scene?`: story with its own dialogue, or a novel scene) and a member stands away (`gathered?`: on the leader's map within `GATHER_TILES`, 3), the scene waits at its first command (`holding?`, a `Game_Interpreter#execute_command` hook that yields the interpreter's fiber), so the leader can neither move nor open the menu, and calls the members, again every 3 s (`CALL_FRAMES`). A member called (`called`) gets 5 s (`GATHER_FRAMES`, measured with `Graphics.frame_count`, a countdown above their head) to finish what they do, then is brought to the leader once free (`come?`, `update`): on the map, after a battle, menu, event or transfer of their own. The call carries whether warping is banned where the leader stands (`warp_ban`, the game's switch 100, `MGQ_MpCoopStory::WARP_BAN`), and the member takes it over on arrival (`take_warp_ban`): the game sets the ban in the events a player walks through to enter or leave a cave, which a member brought over never touches, so a Harpy Feather would otherwise stay unusable. The switch is each player's own (`PERSONAL_SWITCHES`), since it tells of the place a player stands in, not of the story. While called (`coming?`) the member meets no random encounter (`Game_Player#encounter` starts none and draws new steps once they ran out) and turns co-op battle invites down, so no new battle holds them up. Once everyone stands near, or after 30 s (`HOLD_FRAMES`) without those still away (`missing`), the scene plays and the leader's state tells `telling=1` (`story_playing?`); meanwhile every member on the leader's map stands still and cannot open the menu (`blocked?`, through `Game_Player#movable?` and `Scene_Map#update_call_menu`). A member's call lapses once no call came for 6 s (`CALL_LAPSE_FRAMES`, `pending_call`), so one the scene started without is never brought over later. A loaded save sets `Graphics.frame_count` back, so a moment before it counts as long past (`within?`), and a loaded save or the world closing forgets the calls, the question where the leader stands and the hold (`forget`).
- `follow`: when the leader's story moves the leader elsewhere (a transfer while `MGQ_MpCoopEvents.telling?`, noted around `Game_Player#perform_transfer`: `before_transfer`, `after_transfer`), such as a theater show's stage and the "Stage End" common event's way back to the Grand Theater (map 624), or a story's own teleport, the members who stood near the leader's old place are told the new one and come at once, without the five seconds (`followed`). Until they arrive, the leader's pages of that map reach them (`story_map?`), so none is missed. A follow that lapses tells "<Leader>'s story went on without you." (`lapse_notice`). The leader's other transfers take nobody along.
- A PvP battle keeps calls out (`pvp_running?`), and when a duel puts its snapshot of the game back (`MGQ_MpBattlesPvp::Battle.restore`) a call that waited through it is dropped (`drop_call`), so the member answers the leader's next call; a member is only moved on a settled map (`settled?`: no PvP battle, no Library battle, `Graphics.brightness` 255). A call that waited through a duel and moved the player as the map started again left a lasting black screen in the field test of 2026-10-04.
- Gathering, calls, arrivals, follows and calls that lapsed each write a line to the in-game log (`co-op gather:`).
- A member is moved once they are free (`free?`: on the map, with no event, message or transfer of their own in the way), checked after every map update, so a member in a menu or battle follows when they are back. Another map means a transfer, the same map a plain `moveto`.

**Story in the leader's game.** A member's game never plays story itself:

- A story event the member starts (`Game_Map#setup_starting_map_event`, which looks at every starting event, so one left to the leader never keeps the member's other events from starting) does not start, in the member's game or the leader's: only the leader starts story, in their own game (`hand_over`). The member hears "Only <Leader> can move the story on.", once per event in 3 s (`refuse_story`, `REFUSE_FRAMES`), since an event the player stands on starts again with every step, with "Bring them here to go on." while the leader is elsewhere.
- Story events and story common events that run by themselves (autorun) are left to the leader's game (`leave_to_leader?` in `setup_autorun_common_event`), which runs them on its own map.
- While the leader's main event plays story (`@telling`, which ends with the event, `finished`, since a loaded save or the game put back after a PvP battle runs the map's last event's list once more), every message page and its choices (`show`, caught in `Game_Interpreter#wait_for_message`, since the Yanfly plugin writes its own `command_101` after the Patch folder loads) go to the party (`pevent=say`: face, index, background, position, and the lines and choices in Base64). Each page carries an id (`page_id`, a session tag and a count, so a page of an earlier session is never taken for one done), and once the leader moved past it the leader's game says so (`shown`, after `wait_for_message`: `pevent=done`). Members on the leader's map show the page in their own message window once free (`show_heard`, at most 30 kept), the choices as its last line ("<Leader> chooses: Yes / No"), and leave out the pages the leader moved past meanwhile (`done?`), so a member back from a menu or battle joins at the leader's page. Only the leader moves it on: `Window_Message#input_pause` waits on such a page (`mirroring?`) for its `done` instead of the player's buttons or the game's skip key (`page_done?`), and ends it anyway once the leader is gone or stopped telling the story for 2 s (`STALE_FRAMES`, since the leader's state and their pages travel apart). A page too long for the window shows its rest after 2.5 s (`OVERFLOW_FRAMES`); `process_input` marks the pause at a page's end, after which the player's own messages wait for their buttons again (`page_ended`). Escape codes such as `\V[n]` are read in the member's game, which plays the leader's story. Novel scenes are not shown to members yet.

**The story's scene** (coop_scene.rbx, `MGQ_MpCoopScene`). While the leader's story plays for the party (`MGQ_MpCoopEvents.story_playing?`), each change the story makes besides its dialogue goes to the party as `pscene=<kind>` with the map and the arguments as one `MGQ_MpBattlesSync::Wire` line: a picture of the map's screen (`picture.show`, `move`, `rotate`, `start_tone_change`, `erase`), such as a story's CG, the map's screen (`screen.start_fadeout`, `start_fadein`, `start_tone_change`, `start_flash`, `start_shake`, and the game's `od_fadein`/`od_fadeout`), and the leader's character hidden or shown (`player.transparent`), as on a theater show's stage. Only the story's own changes count (`story_change?`): those made inside the update of the map's main interpreter, which a common event it calls runs inside too, noted around every `Game_Interpreter#update` (`updating`, `updated`); a parallel event, such as the map's own display, changes pictures every frame and stays the leader's own. The update tells interpreters apart rather than the command, since a command may wait frames before it runs, as while the party gathers. A member on the leader's map, or on the way there (`MGQ_MpCoopGather.story_map?`, since the screen keeps its pictures and tint through a transfer), makes the same change (`apply`), a picture only by a number of 1-100 and a file name that may hold dots but no path, and notes what to put back, with the screen's tint before the story's first screen change. Once the member no longer sees the story (`watching?`: the leader stopped telling it, or either left the map) and no change came for 2 s (`STATE_GRACE_FRAMES`, since the leader's state that says the story plays travels apart from the changes), the story's pictures are erased, flash and shake cleared, the member's own tint comes back over 30 frames (`RESTORE_FRAMES`) on the map they watched from (on a map the story brought them to, the story's last tint stays), the brightness comes back and the member's own character shows as before (`restore`); a loaded save forgets it (`forget`).

Its key (`MGQ_MpHotkeys`, B by default, read with `GetAsyncKeyState`, since neither the game's `Input` nor its gamepad plugin reads it) opens it on the map while no event or message runs, and closes it again. The game's confirm button takes it, and cancel closes the wheel. A choice without `run` is grey, and taking it shows its `refusal` as a notice. While the wheel is open it holds the buttons (`MGQ_Multiplayer::Capture`, which has the guarded `Input` report none to the game, while the wheel reads them past it), so the player stands still and the game's menu and map keys stay shut. - Middle: the World overview (`MGQ_MpWorldOverview.open`).

## Chat (`ui_chat.rbx`)

**The chat box.** T (`CHAT_KEY`, 0x54) or the wheel's chat choice opens the chat box, which takes the keyboard through `mp_typing`/`mp_take_typed` like the world screen's text box, and holds the buttons (`Capture`), so keys that type move nobody. It opens while the map is quiet, or while the player only waits for the party's story (`map_open?`, `MGQ_MpCoopGather.waiting?`: gathering, called, held or reading the leader's pages), and a box already open stays when an event starts, whose messages then wait for it. The character of the key that opened it arrives after it opened, since the key is read from Windows before the game's window gets the character, and is left out (`without_echo`, within `KEY_ECHO_FRAMES`). Enter sends, Escape or the numpad's 0 closes, as the numpad's 0 closes the game's windows (`MGQ_MpUi.numpad_cancel?`, see below, read from Windows; its 0 arrives as the number row's, so what came in its frame is dropped, and a later one finds the typing off), and a line has at most 120 characters (`MAX_LENGTH`). The box has a cursor that blinks every half second (`BLINK_FRAMES`) and shows at once after a change. Typing and Backspace work at the cursor. Left and right move it (`Capture.repeat?`, so a held arrow repeats), Home and End jump to either end, and Delete removes the character after it. None of these keys types a character, so they are read as the game's buttons or from Windows (`Key`). The text moves left as far as the cursor needs to stay in sight. A line goes to the chosen chat (see below) as its own message: the global chat's `chat=<line>` and `name=<sender>` without a `map` to everyone, so `overworld.rbx` hands it to the chat's route rather than taking it for a state, the say chat's with `ch=say` to each player whose state names the player's map (`tell_map`, `on_this_map?`), and a receiver drops a say line from a player on another map too; the name covers a line that arrives before its sender's first state. Every line, the player's own included:

- joins the chat log (`Sprite_MpChatLog`, font 16) at the bottom left, above the status line, for 10 s (`LOG_FRAMES`); the open chat box shows the kept lines (`KEPT`), wrapped, with the box on the row below, and scrolls them: up and down a row, Page Up and Page Down a page (`PAGE_ROWS`, the page keys read from Windows, since the game's L and R are Q and W too). `MGQ_MpChat.scroll` counts the rows below the last one shown; the sprite breaks the lines into rows (`rows_of`, once per text), keeps the scroll above the oldest row (`limit_scroll`), scrolls on by the rows of lines that come in meanwhile so the rows shown stay put (`keep_place`), and draws an arrow at the right while older rows lie above or newer ones below. Closing the box shows the newest rows again. The log lies on a viewport of its own, which rises above everything while the box is open (`MGQ_MpUi::Z[:typing]`) and otherwise rests just under the map's topmost viewport (`@viewport3.z - 1`), whose wheels and World overview lie above it, or in a battle above its windows (`BATTLE_ROOM`, `Z[:wheels]`); and T and typing work through `Scene_Battle#update_basic` (`on_battle`), which runs in the battle's waits too;
- shows for 6 s (`BUBBLE_FRAMES`) in a bubble (`Sprite_MpChatBubble`) above the sender, while their ghost is on the player's map, placed from the character's `screen_x`/`screen_y`, so it needs no sprite of `overworld.rbx`.

**Chats, tabs and colors.** A line goes to the global chat (everyone in the world), the party chat, the say chat (the players on the same map) or the whisper chat (one player). `/g`, `/p` or `/s` (also `/global`, `/party`, `/say`, `COMMANDS`) at a line's start chooses the chat for it and every line after it (`take_command`; with a space after it the command is taken out of the box as it is typed, and the box names the chosen chat before the text); the say chat holds until the player chooses another. `/w <name>` or `/whisper <name>` chooses the whisper chat and whom it goes to: while the box holds the command and the start of a name, a list above the box offers the names of the world's players that fit (`suggestions`, at most `SUGGESTIONS`), Up and Down move the pick, and Enter or Tab (a typed `\t`, or the Tab key read from Windows) takes it and empties the box (`take_suggestion`); a line sent with the command finds the longest name that starts it (`named_in`). A whisper is `whisper=<line>` and `name=<sender>` to that player's seat alone (`tell_whisper`, routed to `receive_whisper`); the sender's log shows `[To <name>] `, the receiver's `[Whisper] `, and Multiplayer InGame.log leaves its text out. `/help` opens a help tab at the far right of the tabs (`open_help`), which shows `HELP` and nothing else, takes no typing but Escape, and closes once another tab is picked or the box closes (`leave_help`). The empty box names scrolling, Alt and `/help` (`BOX_HINT`), and the tab and resize controls while Alt is held (`ALT_HINT`). A click on another player's name in the open box's log (each line keeps its sender's id, the sprite where their name lies, `@name_spots`) opens their menu above the name (`open_menu`, drawn by `draw_menu` on a sprite of its own): `MGQ_MpActions.peer_options`, which the World overview shows too, and Whisper. Pointing or Up and Down pick a choice, a click or Enter takes it through `MGQ_MpActions.choose` (one that leaves, such as accepting a duel, closes the box too), and Escape, the numpad's 0 or a click outside closes the menu alone; it closes once the player leaves the world. The party chat sends `pchat=<line>` through `MGQ_MpCoop.tell`, so it carries the party's id and the party's gate (`coop.rbx` routes `pchat` to `receive_party`, since `ui_chat.rbx` loads before the gate) drops it for everyone else; outside a party it is refused with a notice. The open box shows tabs above the log (`TABS`: All, Global, Party, Say, Whisper), picked with a click or the left Alt with left or right (`switch_tabs`, the arrows read from Windows every frame, the editor's keys left alone while Alt is held; the right Alt is AltGr, which types). What arrives while the left Alt is held and for `ALT_CODE_FRAMES` after is dropped (`without_alt_code`): Alt with the numpad's arrows, which are its digits, types an Alt code once Alt is let go, a symbol the game's font lacks; a chat's tab also chooses that chat, a command chosen on a chat's tab moves to its tab, and All keeps the chat. A tab shows its chat's lines and the game's own (`Line#shown_in?`). Alt held while the left mouse button goes down on the log resizes it as the mouse is dragged, its bottom left staying put, within the screen and at least `MIN_WIDTH` and `MIN_ROWS`; letting go keeps the size in Player.ini (`chat_size`, `width`x`rows`), and the open chat and each tab have a thin grey outline (`OUTLINE`, `draw_frame`), the chat's white while Alt is held (`RESIZE_OUTLINE`). The picked tab is filled with its chat's color under dark text (`TAB_INK`). A line of the global, party or say chat that comes while neither its tab nor All is picked lets that tab glow yellow at its top right corner, fading toward its middle and opaque at the corner (`UNREAD_GLOW`, `draw_unread_glow`), until its tab or All is picked (`see_tab`, every frame). While a text screen takes the keyboard, `GameWindow` drops `SC_KEYMENU`, so letting Alt go never opens the window's menu, in which the game would wait. The log keeps each line as a `Line` (name, text, `who`, channel, frames left) and draws its head in color (`draw_row`): the tag (`[Global] ` orange, `[Party] ` violet, `CHANNEL_COLORS`), then the sender's name by `who` (`NAME_COLORS`: the player's own yellow, a member of the player's party green as their label on the map, anyone else white, an admin's gold as the featured worlds, the game's own lines grey), then the text, in the chat's color for the global chat and the whispers (`COLORED_TEXT`, pale pink) and white otherwise. A bubble is filled with its chat's color, white for the say chat, at 85 % opacity (`Sprite_MpChatBubble::OPACITY`). `log_lines` writes the lines as text, as the tests read them.

**The admins' chat.** Every line of the global chat is also mirrored to the relay (`MGQ_MpOverworldSync.say`, `mp_world_say`), which keeps a world's last lines for its admins; the say and the party chat are not. A line an admin says in the World Admin tool arrives as a `chat` inbox entry with the admin's `name`, which `overworld_sync.rbx` hands to the chat's route as `chat=<line>`, `name=<admin>` and the Symbol key `:relay`, which no player's message can carry, since those are parsed into strings; the log shows it as `[Admin] <name>: <line>` in gold, without a bubble, since no seat said it.

## PvP battles (`battles_pvp.rbx`)

Two games swap their teams' builds, then fight the same battle live (see [Live battles](#live-battles-battles_syncrbx)), each player commanding their own team; on the host, the friend's characters are rebuilt as real characters and take the friend's commands. A **mirror match** fights the player's own team the same way, played by the computer, without any network.

**Flow.** The World overview's key on the map (`MGQ_MpHotkeys`, F11 by default, read with `GetAsyncKeyState` while the game window is in front (`MGQ_Multiplayer::Background.in_front?`), since the game's `Input` knows only F5 to F9 and all are taken, F8 by the game's message hiding) opens `Scene_PvpLobby` (named without "Battle", which `GameState.scene` reads as a fight). *Host* calls `mp_host` with the team, *Join with the copied code* `mp_join_clipboard`. An invite the player accepted in Discord joins by itself (`MGQ_MpBattlesPvp.join_invite`, `mp_join_invite`) as soon as the map or the screen sees it, and the map opens the screen to show the join; Discord starts a closed game for it, and the title screen then loads the newest save, the one *Continue* picks first (`DataManager.latest_savefile_index`), finished by the game's own `Scene_Load#on_load_success` (`MGQ_MpBattlesPvp.on_title`). Its `Scene_Title#update` hook must wrap the Discord mod's, which skips the methods it wraps while its invite box is open; `battles_pvp.rbx` loads after `Discord_RPC.rb`, so it does. The map and the screen poll `mp_status` every 20 frames; once it says `received`, the map reads the team through `mp_state` and starts the battle. *Fight your own team* returns to the map, which starts a mirror match: the player's own `Team.build`, read back through `Team.parse`, so it meets exactly what a friend would.

**Exchange (DLL, `Network/Pvp/`).** `Session.Current` holds the state; threads of an earlier start (a generation) change nothing.
- The host makes a **join code** (`JoinCode`): `mgqmp2;<token>;<relay>`. The token is 16 characters (about 79 bits); the relay is an id of `Relays`, the one this version hosts on (`Relays.Current`). The games never connect to each other directly, so the code holds no address. The host enters its **relay room** (`Serve`) and only then offers the code: on the clipboard (`Clipboard`) and, while hosting, in the activity as party and join secret (through the Discord bridge, see below); until then the PvP battle screen says it is reaching the relay. When the relay cannot be reached at first, hosting fails (`RelayUnreachable`). Once the code is out, the host keeps the connection open with `ping`. When the relay turns it away or was lost, the host tries again, since a friend may hold the code already: after 10 s the first time (`RelayFirstRetry`), since the relay may still hold its last connection, then every 30 s (`RelayRetry`). Hosting stops with a message (`NobodyJoined`) once nobody joined for 30 minutes (`HostWaitLimit`) or the relay closes the lone host for waiting too long (close code 4004, `RelayFrameChannel.WaitedTooLong`). The first guest swaps teams, which cuts the wait (`StopWaiting`). A team too large for a frame fails hosting and joining at once (`TeamTooLarge`). `mp_cancel` turns a waiting Discord invite down, except once a team arrived: ending a battle's link keeps an invite the player accepted during the battle.
- The guest (`Reach`) enters the room the code's token leads to and waits there at most 10 s for the host (`RelayPairTimeout`). The game says whether the relay found no host in the room (`NotHosting`), could not be reached (`RelayUnreachable`) or is unknown to this version (`UnknownRelay`). A code that starts like one of any mod version (`mgqmp`, `JoinCode.IsOfAnyVersion`) but does not read is from another version (`OtherModVersion`), which the game tells apart from no code at all; an invite with such a code waits like any other, so joining it can say so. Each side sends one **frame** of at most 256 KB (`IFrameChannel.MaxFrameBytes`; four late-game builds take about 35 KB) over the **frame channel** (`IFrameChannel`; `RelayFrameChannel` carries each frame as one binary WebSocket message through the relay). Every body is **encrypted** (`FrameCipher`): AES-GCM with a key derived from the join code's token and two salts of 16 random bytes each, in the clear (HKDF-SHA256): the guest sends its own first and the host answers with its own, so every connection has a key of its own even when a guest tries the same code again or a relay replays an earlier guest; a counter per direction ahead of each frame and in its nonce, so a frame of another token, or changed, repeated, left out or sent back, fails the check. Inside is a `Message`: `key=value` headers (`game`, `player`, or `refused`), an empty line, the team, in UTF-8. The token itself never travels: a guest's first frame that decrypts proves its join code, and the host turns any other guest away without a message and goes on hosting. The host then checks the `game` fingerprint and answers with its team. The connection then stays open as the **link** (`Link`) that a live battle will need: `kind=game` frames carry the game script's own text both ways (`mp_send`, and `mp_receive`, which the game script polls), `kind=ping` goes out after 2 s without another frame, and `kind=bye` says goodbye; the link goes on with the exchange's cipher. A reader and a writer thread of its own keep the game from ever waiting on the network; only the writer encrypts, pings included, so frames go out in the order of their counters. The link counts as `closed` after a goodbye and as `dropped` when the connection breaks or stays silent for 10 s, which the pings of a game still running never let happen; `mp_state` reports it as `link`. Cancelling or starting anew closes it, so the PvP battle without a live battle still ends it at once.
- **The relay** passes frames between the two games, which only connect out to it, so it works where a home connection cannot be reached from outside (DS-Lite, CGNAT, no IPv6, no forwarded port). The room is named after the token by HKDF with a label of its own (`Relays.RoomOf`), so the relay learns neither the token nor the frames' key and only ever sees encrypted frames. A join code names its relay by id, and `Relays` maps each id to an address; moving to another relay is a new id beside the old one, never a new address for an old id, since a guest always takes the relay the host's code names. The server, its protocol and the move to a rented machine: [Relay/README.md](../Relay/README.md).
- Discord invites and the profile: see [Discord](#discord-optional).

**Team (`Team`, on `MGQ_MpActors::Builds` and `MGQ_MpActors::Items` in `core_actors.rbx`).** `Team` writes and reads the whole team through `Builds`, the Frontline first, then the Backline, at most `MOST_MEMBERS`, below a first line `backline=1` or `backline=0`, the sender's *PvP Backline* option. The host's line holds for the battle (`Team.sent_backline?` on the host, `Team.backline?` of the host's team on the guest); without the Backline, `Battle.start` takes the first 4 members only. A line per member, the **build** rather than its results: `member=` then, split by `;`, the actor id; personal level; job; race; every job and race level (`id:level`); the eight stat growths from items; the skills learned; the abilities learned and the abilities set (`skill type:id.id`); the equipment per slot; the eight stats plus hit, evasion and critical in per mille as the sender sees them, for the self-check; then what of the sender's *save* the character reads: the counters `Builds::COUNTERS` (battles fought, the character's Library counts, affection) and the switches its battle start states wait for that are on. Equipment (`Items`): `w<id>`/`a<id>` for a database item, `s…` for a socket item with its gems, `e…` for an enchanted item with its rolls (rarity, upgrade, sockets, variance, enchantments, stat rolls, trait rolls, gems), which the receiver turns into its own copy and lets the game remake the traits from (`reset_data`, as on loading a save). Only numbers leave the game, never the save format, since loading someone else's Marshal data can run code. The receiver takes only ids its own data has, and logs a line or item it cannot read. `Builds.game` is the build format (`Builds::FORMAT`) plus the sizes of the databases, which must match, since ids and fields differ between versions. The format was checked by writing and reading back real Part 1 and late-game parties (socket and enchanted equipment, 1,136 skills, 182 job and race levels) outside the game.

**Rebuilt characters (`Game_MpActor` in `core_actors.rbx`, `Opponent`).** Each friend's character is a `Game_MpActor`, a `Game_Actor` subclass made for its actor id and given the build (`rebuild`), with its owner's affection, save counters and battle start switches, the extra accessory slot and enchanted equipment its owner's game allowed, and items from its owner's bag; `Opponent` builds on it for the enemy side. The build: job, race, levels (and the matching EXP), stat growth, skills, abilities, equipment, then the game's own `refresh` and `recover_all`. As a real character it has every trait of its equipment, gems, abilities, job and race: pre-battle spells and the other automatic skills, passives, and the stat boosts only a battle applies. It answers for the enemy side where the game assumes the player's party (audited: the battle scripts' references to `$game_party`, `$game_actors`, `actor?`/`enemy?` and Luka):
- allies `$game_troop`, enemies `$game_party`, its index in the troop, always a battle member;
- drawn as a sprite (`use_sprite?`), picture by `Pictures`, placed side by side at the screen's bottom;
- `luca?` false, so Luka's binding, giving up and ero offers stay with the player's Luka;
- `booster_actor_exist_param` counts its own side, where the game counts `$game_party.members`;
- the hit effect of a monster (blink) instead of shaking the screen, and on defeat a monster's flash and sound (`:whiten`) instead of its collapse: it stays on the battlefield and turns grey and see-through once that flash ends (`Sprite_Battler#update`: the game marks it `dead?` when the hit lands, before the battle log tells of the defeat, so a `:whiten` effect while dead starts the silhouette; the opacity is set every frame, since every sprite effect makes it opaque again when it starts), since its team can revive it. It stays dead to the game, so every target choice (`Game_Unit#random_target`, the enemy window, all-enemy scopes) skips it as it skips dead monsters;
- the monster data the battle's code reads of the enemy side (`enemy`, `enemy_id`, `friend`, `lose_event_id`, `escape_level`, `escape_not_count?`, `steal_list`, `boss?`, `hide_name`, `lefx`), with no rewards or recruiting; any other method only monsters have is answered by the monster stand-in (`method_missing`) and logged once, so a call the audit missed does not end the game mid-battle;
- the extra accessory slot when the sender had it (6 slots sent), where the game reads a switch of the receiver's save;
- enchanted equipment even while the receiver's save has enchanting off (`NWConst::Sw::ENCHANT_OFF`, which `equippable?` reads), since the game's `refresh` would take it off: `equippable?` turns the switch off for the check in the switches' own entries (`MGQ_MpGame` `:data`), since the game's setter takes every enchanted item off the player's party when it turns on;
- the sender's save where the game reads the receiver's for a character (fields 12 and 13): the damage boosts of `booster_ex_count` (battles fought in the save, the character's Library counts of carries, defeated enemies, times down, orgasms and steals, its affection), `love` itself, which a won battle never raises in the receiver's save (`love=` does nothing), and the battle start states that wait for a switch (`auto_state_with_switch`), which `on_battle_start` adds or removes to match the switches that were on in the sender's save. A mirror match cannot show any of these, since both sides read the same save;
- actions from the game's own actor auto-battle (`make_auto_battle_actions`), which targets its `opponents_unit` and checks what is usable;
- no action without a target: skills aimed at one sex only, or at Luka only while they bind (`ext_scope`), find none in a team without one, which the game never had to handle since only monsters use them on the party, and the battle log then names a target that is not there (`replace_ext_character` fails on `nil`). A `Scene_Battle#use_item` hook shows the game's own "is watching the situation" line instead (`Battle.targetless?`), for both teams;
- the conditions of its automatic skills (pre-battle spells, counters, turn start and end) from its own side (`firing_auto_skills` through a `BattleManager._auto_skill_per` hook): the game checks `$game_party` for "an ally of these ids" and "an ally has this state". A mirror match cannot show this, since both teams are the same. Which automatic skill fires is random (`rand < per`, and a `sample` among skills of the same priority), so a mirror match's pre-battle states, and the element rates they change, differ between the two sides.

What stays as the player's side is harmless in a PvP battle or undone by the snapshot: gold and items spent on skills, Library counters, the local actor of the same id that `Game_Actor#refresh` touches. `Battle.check` logs where a rebuilt character's stats or rates differ from the sender's; both measure outside of battle. A mirror match also writes `Patch/Multiplayer/Mirror Match.log` (`MirrorReport`): each character next to its rebuild, once outside of battle and once when the first turn starts (a `BattleManager.turn_start` hook), after pre-battle spells and battle-only boosts: the 8 stats, 10 extra and 10 special rates, max SP, levels, job and race, element rates and states that differ from normal, states resisted, states on the character, skills, set abilities and equipment with gems, every differing value marked.

**Battle (`Opponents`, `Battle`).** An empty troop is appended to `$data_troops` for the battle only; after `BattleManager.setup`, the rebuilt characters are put into `$game_troop`'s `@enemies` and the escape ratio is made again. Picture: the full picture the Library shows (`NWConst::Library::ACTOR_IMAGE`, 640 × 480 in Graphics/Pictures), at full size, cut to the box around its visible pixels (sampled every 4th pixel, reading them all is too slow) down to the picture's bottom edge, which stands at the screen's bottom like the game's own full-size monsters; the face, enlarged, when there is none. The Library's pictures are the same files as the monsters' battle pictures and the largest the game has; shrunk, they turn jagged, since RGSS scales without smoothing. Drawn by `Pictures.stand_in_for` through `Sprite_Battler#update_bitmap`; their HP bars through `Sprite_Battler#update`, since the HP bar plugin only draws for `Game_Enemy`. The battle runs in the game's own battle replay mode (`$game_temp.in_memory_battle`: no EXP, gold, drops, recruiting or autosave) with *can lose* (defeat revives and returns to the map); `Game_Troop`'s EXP, gold and drop totals are 0 for other mods such as a victory screen. It also turns on the rules every multiplayer battle shares (`MGQ_MpBattles.begin(:pvp)`): the switch that removes the battle's *Party* command (`NWConst::Sw::FORBID_BATTLE_SHIFT_CHANGE`, 27) unless the battle has the Backline (`MGQ_MpBattles.begin(:pvp, backline)`), and the switch *No Seduction* (86), which ends common event 6 before it runs a monster's **ero offer** (the low-HP offer of an H-scene for giving up, common event 2000 + enemy id) or conversation. Before it, `Battle.start` Marshals the save contents plus `$game_library`, `$game_system_switches` and `$game_global_system`; the `Scene_Map#start` hook extracts them again and removes the troop, the way the game's own Retry restores a battle. This also undoes whatever rebuilding the characters touched.

**Nothing reaches the disk.** The game writes the system save (Library, system switches, affection) at every scene change (`Scene_Base#pre_terminate` → `SaveSystemData.auto_save`) and when it closes, so the battle scene's end would write the battle's changes before the map puts the snapshot back. While a PvP battle runs, hooks on `DataManager.save_system` (`Battle.as_before_for_system`) and on `save_game_without_rescue`, `auto_save_game_without_rescue` and `save_game_backup_without_rescue` (`Battle.as_before_for_save`) swap in the snapshot for the write and swap back after it. A reset (F12) during a battle goes to the title screen, which makes the save's objects anew but keeps the shared ones; `Battle.forget` puts those back and calls `MGQ_MpBattlesSync.finish`, which closes a live battle's link, so the friend's game wins instead of waiting. The restore also drops the notices of medals earned in the battle (`$game_temp`'s `@gain_medals`, the medals themselves are in the Library) and the game's Retry data of the battle (`BattleManager`'s `@retry_data`). The feature caches (`CacheActorFeatures`, `CacheUniq`) are keyed by object, not by actor id, so a rebuilt character never shares an entry with the player's character of the same id.

## Backline (`battles_pvp_backline.rbx`)

A PvP battle between two players has the Backline when its host's *PvP Backline* option says so (`Backline.wanted?`, `$game_system.conf[:mp_pvp_backline]`, on by default); a duel's challenger hosts, and tells the option in their state (`challenge_backline`), which the challenge's lines show. Team duels never have it. `Battle.start` then rebuilds every member of the other team: the first 4 stand in the troop, the others wait in `Backline.reserve`, and the balance fills the HP of both Backlines too.

- **The player's own swap** is the game's own shift change (`Scene_Battle#bench_member_ok`, `Game_Party#swap_order`), so it stands at once on the player's screen. `Backline.round_front` reads the Frontline once per round, keyed by the troop's turn count, which only changes as a turn starts; a character standing in a place another held then was swapped in (`swapped_in?`), gives no commands (`Game_Actor#inputable?`) and has no actions (`Game_Actor#make_actions`, which the game runs anew after a shift change). Swapped back within the same command phase, it costs nothing.
- **Telling the other game** (`Backline::Mode`): a guest's commands carry its Frontline's actor ids (`own_order`), which the host puts in its troop before the commands (`take_order`, `take_front`). Once the commands came, the host takes away any actions of the characters swapped in and posts its own Frontline as `pvp_front` after a flush, before the turn's events (`share_order`, `settle_round`); the guest takes it in the stream's order (`stream_kinds`, `take`). So both games reorder between the same two sends, and the stream's places (`a0`, `e0`) mean the same characters on both. `take_front` leaves out a Frontline that names a character the team lacks, names one twice or has another size, and draws the troop's sprites anew (`Spriteset_Battle#dispose_enemies`, `create_enemies`). A sprite made for a dead character starts as the silhouette (`Sprite_Battler#update` in `battles_pvp.rbx`).
- **Targets** are places: the game finds a single target by its index when the action runs, so an attack hits whoever stands there by then.
- **Outside both Frontlines**: the stream names the host's own Backline `b<actor id>` and the other side's `r<actor id>` (`Mode.reserve_ref`, `Mode.reserve`), and records their values and names with the battlers' (`MGQ_MpBattlesSync.party_side`, `troop_side`), since skills that reach the Backline change them. `Game_Troop#item_target_members` gives such skills the other side's reserve, as `Game_Party`'s gives the player's.
- **Defeat** is the game's: a side loses once its whole Frontline is down, whoever waits behind it.

## Duels (`battles_duel.rbx`)

A duel is `MGQ_MpBattlesPvp`'s PvP battle between two players of a world, carried over the world's room instead of the PvP link.

- **Challenge** (`invite`, `stop`): like a party invite, for 15 s (`INVITE_FRAMES`), to the players nearby, and to a player anywhere named by the World overview. The state tells `challenge=1` and `challenge_to` (ids); never a field `duel`, which marks the duel's messages (`MGQ_MpOverworldSync.route("duel")`) and would turn every state into one. Anyone may duel, in a party or not. The line above the challenger's ghost says "Challenges you to a duel (B)" to the players it reaches (`challenged_by?`), and the challenger's own line "Challenging to a duel . . .".
- **Accept** (`accept`): only while free on the map (`free?`: no event, message, transfer, menu or other multiplayer battle). It sends `duel=accept` to the challenger with the game's fingerprint and team (`Team.game`, `Team.build`) and waits 6 s (`ANSWER_FRAMES`) for the answer.
- **Start** (`take_accept`, `take_start`, `on_map`): the challenger, still challenging and free, answers `duel=start` with a battle id and its own team, and hosts; both games then call `MGQ_MpBattlesSync.join_world(role, id, [seat], name, :pvp)` and `MGQ_MpBattlesPvp::Battle.start` on the map's next frame. Whichever side cannot start any more (busy, a `start` it no longer expects, an unreadable team, or an event that came first on the map) calls the duel off (`call_off`, `give_up`): `duel=cancel` with the id drops the other side's duel still waiting to start (`take_cancel`), and `battle=broken` ends a battle already waiting.
- **Decline** (`decline`, `take_decline`): `duel=decline` with a reason (`REASONS`: busy, stopped challenging, another version of the game, an unreadable team), shown as a notice.
- **Over the world's room**: `MGQ_MpBattlesSync` already speaks it for co-op battles; in PvP mode the seats are the other player's, a player who leaves the world ends the battle (`world_gone?`), and `finish` leaves the PvP link alone. Discord and the ghosts need nothing new: `Battle.running?` feeds `pvp_battle_with`, and the state's scene is `battle`.

## Team duels (`battles_team.rbx`)

A duel becomes a team duel when either player leads a party of two or more, unless both play in the same party (`MGQ_MpBattlesDuel.team_duel?`). Each side is that party, or the single player; party members who do not lead still duel one against one.

- **Gathering** (in `battles_duel.rbx`): on the accept, the challenger sends `duel=team` to its own party and to the player who accepted (`gather`). A call counts only from the challenger the player accepted or from the leader of the player's party (`take_call`). The player who accepted, leading a party, passes the call on through the party's gate (`duel_call`, `call_party`, `take_passed_call`) and tells the challenger whom (`duel=side`, `take_side`), who then count on the other side. Each answers `duel=ready` with their game's fingerprint, their Frontline (`MGQ_MpBattlesCoop.team_build`, the places the duel counts) and their `party_member_max` once free on the map (`tick_called`). After everyone answered, or 10 s (`READY_FRAMES`), the challenger arranges both sides as a co-op battle's party (`MGQ_MpBattlesCoop.arrange`: the leader first, each player's share of the Frontline, a single player's whole Frontline) and sends `duel=start` with `team=1` and both sides to those ready, `duel=cancel` (`late`) to the others; without anyone of the other side ready the duel is off. A player busy by then sends `battle=leave`, which counts them as having left.
- **The battle**: `MGQ_MpBattlesSync.join_world(..., :pvp, true)` (`team?`). Every game has its own side as its party, through `MGQ_MpBattlesCoop.form` (`MGQ_MpBattlesTeam.form`), and the other side as its troop, rebuilt as `MGQ_MpBattlesPvp::Opponent`s that carry their owner's seat (`opponents`, through `Battle.start`'s block). The challenger hosts. A guest on the host's side has the host's party and troop (`same_side?`, like a co-op guest); one on the other side has them swapped (like a one-against-one guest). The host takes commands from every guest (`several?`), each for their own characters (`Commands.commanded_by?`): a guest of its side in its party, a guest of the other side in its troop, by the same places. The Backline stays out of a team duel, whatever the players' options say.
- **Leaving**: a guest who escapes leaves the duel (`leave`) and returns to the map; their characters stay. At the next command phase the host hands them to the first player of their side still in it (`settle`, `heir_of`), told as `team_heirs`, so that player commands them (`Game_MpAlly#inputable?`). The host wins once the other side is empty; a host who leaves or gives up ends the duel: lost for its side, won for the other (`guest_end`, `end_early`).

## Trades (`trade.rbx`)

A trade moves items and gold between two players on the same map. Key items stay out (`Items.tradeable?`: `key_item?`, enchant stones excepted); only the bag counts, not equipment or the storehouse.

- **Offer and accept**: like a duel challenge (`MGQ_MpCoop::Invite`), told as `trading=1` and `trading_to`, never a field `trade`, which marks the trade's messages. It reaches only players on the same map (`same_map?`). The player who accepts sends `trade=accept`; the one who offered, still offering and free (`free?`), answers `trade=open` with a 24-character id, and both games open `Scene_MpTrade` from the map (`on_map`).
- **Offers**: each change sends `trade=offer` with the offer's revision and the offer as text (`Items.write_offer`: `g<gold>` and `<token>*<amount>` separated by semicolons). A token is `i`, `w` or `a` and the id, or `u`, an enchanted or socketed copy as `MGQ_MpActors::Items` writes it, and its name prefix in hexadecimal after `~`. Every change takes both confirmations back.
- **Confirm**: `trade=confirm` names the revisions of both offers (`mine`, `yours`). A game whose own confirmation and the other's name the offers as they stand (`Session#agreed?`) hands both offers to the relay (`commit`): `mp_trade_commit` with an id of the trade's id and both revisions ordered by player id (`relay_id`), so both games name it alike and a later confirmation is a trade of its own, and the text `<id>=<offer>|<id>=<offer>` ordered by player id (`agreed_text`). The relay commits once both games sent the same text.
- **Commit**: while the relay decides (`:committing`) nothing changes. `committed` applies the trade (`Items.apply`, inside `MGQ_MpCoopEvents.granting`, so a leader's story does not pass it on), notes the relay's id in the save (`$game_system`'s `@mgq_mp_trades`, the last 50), saves (`Saving`: the slot last loaded or saved in the world, else the first free one) and sends `mp_trade_done`. `cancelled` opens the trade again unconfirmed; an offer or unconfirm from the other player cancels a commit the relay has not decided.
- **Recovery** (`Recovery`): once per save loaded in a world, on the map, `mp_trade_pending` lists the committed trades the player has not marked done. One the save lacks is applied from its text and saved; each is then marked done.

## World overview (`world_overview.rbx`)

A box over the map (`Sprite_MpWorldOverview`), not a scene, so the world runs on behind it; it holds the buttons (`MGQ_Multiplayer::Capture`) while open. Its key (`MGQ_MpHotkeys`, F11 by default, which opens the PvP battle screen outside a world) or the wheel's middle opens it; its key, cancel, the wheel's key, a click outside the box, leaving the map, an event, a message or the chat box close it.

- **What every state tells** (`state_fields`): `place` (the map's shown name, else its name in the editor), `lv` (the highest base level of the companions in the party and waiting, `stand_members`, Luka left out) and `progress` (`part`, `part:side` or `part:route`, such as `2:alice` or `3:destroyer`). Level and story are read every 3 s (`READ_FRAMES`). The story is read by name in `$data_system`, the translation's or the untranslated game's (`PROGRESS`, `SIDES`, `ROUTES`): Part 2 from progress 20, Part 3 from 40; the route only in Part 3, else the side. In a party the members borrow the leader's story, so they show the leader's. In a Raid World it also tells `flv`, the highest base level of the player's share of the Frontline, Luka included (`front_level`: `battle_members` cut to `MGQ_MpCoopSquad.own_share`'s Frontline share, else the first character); a Classic world never sends it.
- **The list** (`rows`, `lines`, `own_row`, `row_of`): every player online and the player, grouped by place (the player's first, then by name), each group by name with the player first. A row shows what they do (the ghost's icon), a crown for a party's leader, the name (green for members, and for the player while in a party), the party's size, "Lv n", the place in the story ("Part 2: Alice side") and the ping. A player whose party invite or duel challenge reaches the player shows it in place of their story (`call_of`). The title shows the world's name and the player's party ("Party 2 / 4").
- **The menu** (`menu_options`): for another player, accept their party invite (also one that names the player from afar, `Party.invited_by?`), invite them wherever they are (`Party.invite(id)`, told as `invite_to`), or remove them from the party as its leader (`Party.remove`), and accept their challenge or challenge them (`MGQ_MpBattlesDuel`); on the player's own row, leave the party and stop inviting or challenging. The arrows and confirm, or the mouse, pick and take; choices that cannot be taken are grey and say why.
- **The mouse** (`MGQ_Multiplayer::Mouse` in `Multiplayer.rb`): `GetCursorPos`, `ScreenToClient` on the window in front and `GetClientRect` scale the pointer to the game's screen while the game is in front; the left button is read like F11. Pointing picks a row or a choice once the mouse moved, a click opens or takes it.
- **The party box** (`Sprite_MpPartyBox`, `party_rows`): while the player is in a party of two or more and the overview is closed, a box in the top right corner of the map lists the party: the leader first with a crown, then by name, each with "Lv n" and the ping, and their place on a smaller line below (`draw_place`). `fit_place` shortens a place to the box: the Pocket Castle's short name (`SHORT_PLACES`), then without its part in brackets, then cut with "..." before a floor, layer or area (`PLACE_FLOOR`) it keeps; the game's names run up to 45 letters. It builds rows for the party only, since it redraws every frame it changed. Its key (`MGQ_MpHotkeys` `:party_box`, Tab by default, which the game does not read) makes it small and full again on the map, in a party, with no screen of the mod over the map (`MGQ_MpPartyBox.on_map`, `toggle`); the choice is kept in Player.ini (`party_box_small`), so it holds after a restart and in every world. Small, it lists a row per player with the crown, the name and the ping, without title, level or place, 150 pixels wide (`draw_small`, `SMALL_WIDTH`).
- **The map box** (`draw_map`, `map_rows`): in a Raid World (`MGQ_MpPartyBox.map_box?`, `MGQ_MpCoop::Scope.raid?`) the party box lists everyone on the player's map (`Scope.peers_here`) while someone else is on it: the party's members first and green, its leader first with the only crown, then the other players by name in white, each with "Lv n" from their `flv` and the ping, and no place line. The title says "Map n", the number of players on the map. The box grows with its players up to `MAP_LINES` (10) lines; past them it lists 9 and a line "+n more" (`capped`), small too. Its key works while someone else is on the map.

## Party size and leader

`MGQ_MpCoop.size_of(id)` counts a party's players from the states, `leader_of(id)` finds its leader (the player the party's id names, else the lowest id, as `Party.leader`; a player who just joined counts only once the leader's list names them, `Party.admitted_me?`, so the leader turning them away reaches them) and `leads?` tells whether a player leads their party of two or more. Every party script asks `MGQ_MpCoop.party_leader` and `party_leading?` for the leader of the player's own party of two or more. Any party can be shown, not only the player's own: a ghost's label shows "2 / 4" after the name and a crown (`MGQ_MpOverworld::CROWN_ICON`, 226, the game's King's Proof) before it; the player's own line above their head (`Sprite_MpOwnPing`) shows the same next to their ping. A party holds at most four players (`Party::MAX_PLAYERS`).

## Co-op battles (`battles_coop.rbx`)

When a party member's game sets up a battle (`BattleManager.setup`, which random encounters, event battles and story bosses all go through), the party members on the same map who are walking it, reading an event's messages, or on it with their window in the background, which keeps running (their state's `scene` is `map`, `event` or `away`), are invited to it. When nobody is, the in-game log says what each party member does. The party's leader is the **host** and computes the battle, so the leader's game and mods decide it; the others are **guests** and play it back through `battles_sync.rbx`, now over the world's room. When the leader is not among the members invited, the game that set the battle up hosts it.

- **Leader leads** (`offer`, `ask_leader`, `await_leader`; `serve_request`, `lead`, `refuse_lead`): a member whose game sets up a battle while the leader is invited sends the leader `coop=lead` with a battle id it chose, the troop, escape, lose and the map, and becomes a guest of that battle (`join_world(:guest, ...)`). Its battle start (`Live` in `battles_sync.rbx`) waits up to 6 s (`LEADER_FRAMES`, "Asking <leader> to lead the battle...") for the leader's `coop=invite` with that id. The leader, on the member's map, no other battle running and free within 3 s (`ACCEPT_FRAMES`), sets up the same troop and hosts it with the member's id, inviting the member though their state says `battle`; otherwise it answers `coop=no_lead`. A refusal, a leader gone or a silent one leaves the battle to the member, who hosts it (`host`) and drops a late invite for the id it asked with (`@dropped_bid`). A leader whose member did not join calls the battle off for everyone (`call_off`, `broken`), since the encounter was the member's.
- **Held encounters** (`encounter`, `hold`, `tick_hold`, `take_soon`): a random encounter (`Game_Player#encounter`) whose battle the game just set up waits up to 3 s (`HOLD_FRAMES`) while party members on the map are busy (`busy_members`: any scene but `map`, `event`, `away` and `battle`, such as a menu, typing or a vehicle). `offer` holds it instead of inviting, `encounter` then returns false, the player stands still (`Game_Player#movable?`) and opens no menu (`Scene_Map#update_call_menu`), and each busy member is told `coop=soon`, which shows for a moment as a message in their notification box (`MGQ_MpNotices.message`). Once every one of them is back on the map, or the time ran out, `tick_hold` offers the battle as usual and calls the battle scene; an event that started meanwhile drops it, and so does the title screen (`drop_hold`).
- **The party stands still** (`freeze_party`, `take_freeze`, `frozen?`): whenever a member's encounter is held, hosted or asked of the leader, every party member is told `coop=freeze` with the map. A member on that map stands still and opens no menu (through `hold_player`) until they join that battle (`accept`), turn it down (`decline`), set up a battle of their own (`offer`) or 10 s pass (`FREEZE_SECONDS`, by the clock, since a member in a menu counts no map frames), and reads "Enemies! <Member> is in a battle." in the notification box. Before, only the member who met the enemies and the leader stood still while the others could walk off before their invite came.
- **Invite** (`host`): the host makes the battle a live co-op battle (`MGQ_MpBattlesSync.join_world(:host, ...)`), turns on the multiplayer rules (`MGQ_MpBattles.begin(:coop)`) and tells the party `coop=invite` with the battle's id, the troop, escape and lose, the invited seats and the map. Not while another multiplayer battle, a Library replay or no party is there.
- **Accept** (`take`, `on_map`): an invited member on the host's map joins once free on the map (no event or transfer of their own), within 3 s (`ACCEPT_FRAMES`, counted by the clock in `expired?`, since an invite that came outside the map waits for it), else turns it down (`battle=decline`). A member in a battle of their own turns it down at once. Joining sets up the same troop (without inviting anyone itself), becomes a guest (`join_world(:guest, ...)`) and calls the battle scene from the map, which plays the game's own battle music and transition. The leader's story dialogue on screen is cleared.
- **Gather** (`gather`, at the host's battle start): the host waits up to 6 s (`JOIN_FRAMES`) for each invited member's `join` (`own_build`: the builds and HP and MP of as many characters as their squad holds with two players, the most any battle needs, and their `party_member_max`) or decline. Without anyone, the battle is the host's own (`stand_down`). Otherwise it sends `roster`: the troop (`troop_entries`: each enemy's id, screen x and y, and whether hidden) and every player (`arrange`): seat, name, builds, HP and MP, `party_member_max`, the order of their places, and their shares of the Frontline and the Backline (`MGQ_MpCoopSquad.share`), the party's leader first, then by player id. A guest (`join`) sends its `join` at its battle start and waits for the `roster`. A guest whose own troop differs, as through a mod of either game, fights the host's instead (`take_troop`): it rebuilds the enemies as `Game_Troop#setup` does, names them apart again (`make_unique_names` with `@names_count` emptied) and draws them anew (`Spriteset_Battle#dispose_enemies`, `create_enemies`), since the host names every enemy by its place. It pays out its own rewards for them. Only a host's enemy missing from this game's database keeps the guest's own troop.
- **The party** (`form`): every game builds the same party in the roster's order, each player's share of the Frontline (`Player#lines`; a player is a `MGQ_MpBattlesCoop::Player` record, which the messages carry as its fields in order). A player's own characters are their real ones; everyone else's are `Game_MpAlly`, a `Game_MpActor` on the party side with its owner's seat (`mp_seat`), HP and MP, which this game's player never commands (`inputable?`) and for which the host's computer chooses nothing while it waits for its owner's commands (`make_actions`, `awaits_commands?`). The party is named after the player's own characters (`Game_Party#name`, `party_name`), as when it runs away or is defeated, since its first character may be another player's. `Game_Party#battle_members` returns this party while the battle runs (hooked once the first scene starts, since plugins may define it anew), and `bench_members` the player's own share of the Backline (`own_bench`); `all_members` stays the player's own, so EXP goes to the player's own characters. Others' characters are rebuilt once per battle (`ally`), so one swapped out and back keeps what the battle did to it.
- **Swaps** (`swap`, `take_order`, `share_order`): the battle's *Party* command works, since `MGQ_MpBattles` forbids it only in PvP. In its shift change a player may pick only their own characters (`Window_BattleStatus#current_item_enabled?`), and `Scene_Battle#bench_member_ok` swaps within their squad's order, in their own party too, as the game's shift change does. A guest's commands carry their order, which the host takes before the commands (`Commands.apply`); once every guest's commands came, the host sends `coop_party` when any order changed, before the turn's events. A swap only changes who stands in a player's own places, so the others' commands still mean the places they chose.
- **Leaving** (`settle`, `reform`, `go_solo`, `take_over`): whoever gets away leaves the battle. At the next command phase, before it is recorded, the host takes the players who left out: the others fight on with the shares of the smaller party (`arrange` again), the roster carrying everyone's squad for two players for that; the host sends what it recorded so far, then `coop_party` with the players who stay, which a guest's playback takes between two sends (`Channel.take_first`, `Playback.next_event`), so every battler reference after it means the new party. Characters who stay keep what the battle did to them (`mp_seat`, `mp_place`). A host left alone, and a guest whose host got away or is gone, fight on as a battle of their own (`stand_alone`): their own full team, the game's own settings, no live battle; a guest starts a new command phase from the host's last values. Every player still in the battle hears of it at once (`MGQ_MpBattlesSync::Departures`): a `leave` goes to the whole room, so each game tells "<name> left the battle." in the chat log (`MGQ_MpChat.system`), which shows in battle, and in the status line as it arrives, mid-turn or during command input; a battle player who leaves the world is told too (`on_leave`), each once per battle.
- **End** (`ended`, after `Scene_Battle#terminate`): the player's own party again, the game's own settings back (`MGQ_MpBattles.finish`) and the live battle over, the world's room left open.
- **In a Raid World** (`raid?`, from `MGQ_MpCoop::Scope.raid?`) a battle takes the players on the map, party or not; Classic worlds keep everything above.
  - **Who joins** (`raid_candidates`): the other players on the battle's map (`Scope.peers_on`) whose state's `scene` is `map` (`RAID_FREE_SCENES`, not `event` or `away`) and who are not busy (`raid_free?`: their state's `busy`, 1 while they trade or are about to teleport, `state_fields`, sent only in a Raid World), the party's members first, then by the steps (diagonals counted as one) from the party leader's tile when the leader is on the map, else from the player's own (`raid_center`, `distance`; positions from the states, not the ghosts), at most 3 with the player (`RAID_PLAYERS`). Outside a party too (`host_possible?`).
  - **The player who starts it hosts it** (`offer`): no `ask_leader`, a request to lead is refused at once (`take_request`), and the host comes first in the battle's order (`arrange`). The invite and the hold (`freeze_party`) go to the players taken alone, through the map's gate (`tell_map`, `map_coop=<kind>`), which only a Raid World takes (`take_map`; a Classic world keeps the party's gate); a busy party member is still waited for (`hold`, `coop=soon`), and the players the hold froze whom the battle then leaves out get `coop=off` (`release`). Of two invites waiting for a player, the one whose battle hosts first (`hosts_first?`: an event's battle, else the host who entered the map first) stays and the other is turned down (`keeps_waiting_invite?`). The invite tells `enc`, 1 for a random encounter, else 0. A battle that begins while another player's invite waits for its player also invites that player, whose own battle gathers and so is no candidate (`with_waiting_host`), so of two battles one yields. The host waits 10 s for them to join (`RAID_JOIN_FRAMES`, `join_frames`), a guest 4 s more for the roster (`roster_frames`). A guest who trades turns the invite down (`on_map`). No level sync (`MGQ_MpCoopLevelSync.level_for` is nil).
  - **Two battles started at the same moment** (`rival?`, `keep_rival`, `yield_to_rival`): a player whose random encounter (`offer`'s `encounter`, also a held one) still gathers its players and who is invited to another battle on the same map, of at most 4 players, that is an event's (`enc=0`) or whose host entered the map first (`Scope.key_of`, the lower `[since, id]`), keeps that invite instead of turning it down (`yields_to?`). Its gathering ends, it tells the players it invited `coop=off` (`take_off`: a waiting invite is forgotten, a guest waiting for the roster follows or breaks off, and nobody stands still for it any more unless another host froze them or their invite waits, `unfreeze_for`), takes the rival's troop (`adopt_troop`: `Game_Troop#setup`, the escape ratio, escape and lose, no first strike, its enemies drawn anew) and becomes the rival's guest: `Mode.host_start` returns `:guest`, and `Live.host_start` starts the battle as a guest. A rival's invite that waited as the player's own battle began counts too (`answer_waiting_invite`; the player then hosts even with nobody to invite, `waiting_rival?`), any other waiting invite is turned down then; of two rivals the one that hosts second is turned down (`keep_rival`), and a rival whose `coop=off` comes is forgotten. The rival turns the other's invite down as usual. An event's battle never yields, since its event goes on by the battle's result. A guest waiting for the roster of a random encounter's battle (`@awaited`) keeps an invite to a battle it would yield to instead of turning it down (`follows?`); when its host's `coop=off` comes it takes that battle's troop and joins it (`follow`, `join` sends its join anew), and when its own roster comes it turns that invite down.
  - **Hotjoining** (`battles_coop_hotjoin.rbx`, `MGQ_MpBattlesHotjoin`): every game tells the battle it fights in its state, `rb` (the battle's id) and `rbh` (its host's seat), also a battle of its own (`fight_alone`: nobody to invite, nobody joined, or left alone), both empty outside a battle (`state_fields`, sent only in a Raid World). A random encounter on a map where another player's state tells such a battle (`target_battle`: the one whose host entered the map first, whose own state tells the same battle) asks its host instead of hosting (`ask`, from `offer`, only while no invite waits): `coop=hot` through the map's gate with the battle's id, the troop, its enemies (`id:x:y:hidden`, `;` between them) and the seats of the free players it would have taken (`raid_candidates`, who stand still), and waits as that battle's guest up to 3 s (`ANSWER_FRAMES`, `await` from `Mode.before_start`). The host takes it in (`take_request`, `refusal`) when it hosts that battle or fights it alone, its battle no longer gathers, nobody left it to the computer, neither troop is a boss battle (`MGQ_MpRaidBosses.battle?` for its own, or the `boss=1` its host's invite carried for a battle it took over, `boss?` for the encounter's), its players, those taken in before and the new ones stay at most 4, this game has the enemies, and they find places (`place`: at most 8 standing or hidden, `TROOP_LIMIT`; on the screen where at most half of the narrower of two pictures, measured through `Cache.battler`, hides behind another, `MAX_OVERLAP`, the place nearest the middle among equals; pictures as wide as the screen stand in its middle and count for no overlap, as the game's own troops stack them there). It answers `coop=hot_ok` with its escape and lose, invites the players who come along with `hot=1`, lets in their battle messages (`MGQ_MpBattlesSync.expect`), and, fighting alone, hosts its battle without turning it live yet; otherwise `coop=hot_no`. Taken in, the player joins as a late guest (`join_late`: the host's escape and lose, no first strike or surprise); refused or without an answer it hosts its encounter as usual, telling a silent host `coop=off`. A late guest (`late?`, also one invited with `hot=1`) waits up to 75 s for the roster (`ROSTER_FRAMES`), "Joining <host>'s battle at its next turn...". The host takes them in as a command phase opens, before the live battle opens it (`settle`, first in `Mode.settle`): a host fighting alone turns its battle live first (`before_phase`, `go_live`, its hook wrapping `battles_sync_live.rbx`'s): the multiplayer rules, its squad as the party's first player, the stream. The new players' characters join the party (`arrange`, `form`), and the encounter's enemies the troop once its player joined (`add_enemies`: at their places, started as the game starts a battle's, named apart, the escape ratio anew, drawn anew); the guests in the battle get `coop_party` and `coop_troop` (the troop and the names, which a guest adds after its own enemies or takes whole, `take_troop`, between two sends), the new players `roster` (the troop with the fallen enemies marked `2`, `late_entries`, which a guest rebuilds dead and unseen, `lay_down`, its escape ratio anew, the players, no level and the turn) and `ready` with the names, and then the command phase's stream. Players who turned the invite down or stopped waiting (`give_up`: any end of a late guest's wait without the roster sends `decline` and puts its encounter's own escape and lose back), left the battle or the world, or did not join within 60 s (`WAIT_SECONDS`, told `coop=off`) are forgotten (`expire`); a host fighting alone whom nobody joins keeps its battle its own (`stay_alone`), its Retry too should the battle end first. A host whose co-op battle goes on alone (`stand_alone`) calls off those taken in who did not join. The host's `coop=off` lets a late guest's encounter start on its own (`call_off_own`, `fight_own`, through `take_over`: its own escape and lose, from its start), and so does a roster that never comes; an invited late guest breaks off as any guest. The battle's end tells those taken in who did not join `coop=off` (`ended`). Every game pays out the whole troop it fought, as in any co-op battle. An event's battle never asks, since its event goes on by its own troop's result and pages.

Each game ends the battle as the host's ended: a victory with its own EXP, gold and item drops (the guest's enemies carry the host's death states, which `exp_total`, `gold_total` and `make_drop_items` count), a defeat with its own defeat, an escape as an escape.

## Live battles (`battles_sync.rbx`)

**First version.** Both players command their own team. The host's game computes the battle and streams what it shows; the guest's game plays that back and sends its commands. Each game sees its own team as the party, so the two would draw their random numbers in a different order if both computed. When the teams arrive over an open link, `battles_pvp.rbx` calls `MGQ_MpBattlesSync.join`, which takes the role the DLL reports (`role=host` or `guest`), and keeps the link instead of cancelling it; `Battle.start` calls `MGQ_MpBattlesSync.battle_started` as it calls the battle scene, and `Battle.restore` calls `MGQ_MpBattlesSync.finish`, which closes the link. A mirror match calls `MGQ_MpBattlesSync.record_to_file` instead of joining.
- **Co-op** (`mode` `:coop`, `join_world`): the same system with several guests over the world's room instead of the link. A message is `battle=<kind>`, `bid=<battle id>`, then the body (`MGQ_MpBattlesSync.tell`), sent to each of the battle's other players (`player_seats`) and taken only for the running battle (`MGQ_MpBattlesSync.take` through overworld_sync.rbx's routes); a guest takes only its host's, the host only its guests' (`Channel.receive`, `take_from`). The sides stay as they are, since every game has the same party and troop (`Playback.battler`, `Names.setup`). A guest's commands cover only its own characters, and the host gives them to that guest's allies (`Commands.apply` by `mp_seat`). The host waits for every guest still in the battle (`all_ready?`, which starts each wait with nobody ready, and `host_guests_commands`); a guest who left (gone from the room, or `leave` once their escape succeeded, `Live.escaped`) does nothing more, their characters' actions taken away at once on the host (`guest_left`, `Mode#left`, `MGQ_MpBattlesCoop.idle`; commands they sent before are left out), and taken out of the party at the next command phase (`MGQ_MpBattlesCoop.settle`). Every player's Escape is the game's own escape attempt (`escape_leaves?` is false in a co-op battle); a failed one spends that player's turn, since its empty commands take its characters' actions away. When the host gets away (its stream ends with `process_abort`) or is gone, each guest takes the battle over as its own (`MGQ_MpBattlesCoop.take_over`). Each game ends it as the host's ended (`guest_end`), never swapped. The world's room stays open afterwards (`finish`).
- **Messages** (`Channel`) are the game script's own: a kind on the first line (`ready`, `commands`, `events`, `forfeit`, `broken`), the rest after it. Values travel as `Wire` lines, tab-separated typed tokens (`i5`, `sText` with `\t`, `\n` and `\` escaped, `@a0` for a battler, `k12` a skill, `t3` an item, `z2` a state, `w5`/`a7` a weapon or armor, `g` in front of one of these for an equipped or stolen item, `xcount` an action's kind, `[` … `]` an array, `{` … `}` an action result as field names and values), never as Ruby code or Marshal data. The guest only calls the methods its lists name, takes picture names without a path and waits of at most 10 s.
- **Start:** both battle scenes send `ready` and wait for the other's (`Waiting`, "Waiting for <Player>..."). The host's `ready` carries its party's and troop's names, which the guest swaps for its own in every text that still arrives as text (`Names`: the host's characters are the guest's enemies, named with their owner), but not in a speaker's name box (`\n<Name>`) or the untranslated game's speaker line (`【Name】`). An untranslated guest has no name box, so it shows a translated host's as a speaker line (`Names.readable`). The host turns its skip settings off for the battle (`SKIP_SETTINGS`), since the guest sees only what the host's battle shows; `finish` puts them back.
- **Host:** `Recorder` streams every event every 10 frames, with each battler's HP, MP, SP, states with the turns they have left, buffs and barriers when they changed: before and after every action, after every hit (`apply_item_effects`, which counters and reflections go through too) and before every sprite effect, so the guest has a hit's HP and a defeat's death before it shows them; at every command phase every battler's, which corrects whatever the guest missed. Sprite effects are recorded at the setter and after `perform_damage_effect` and `perform_collapse_effect` of `Game_Actor` and `Game_Enemy`, which write the field directly (`Recorder.sprite_effect`). When recording fails, the host breaks the battle off (`MGQ_MpBattlesSync.break_off`, which sends `broken`), since the guest sees nothing but the stream. In a PvP battle, a host's character that falls with an actor's collapse is the guest's enemy, so its collapse becomes the defeat flash its silhouette starts from (`Playback.sprite_effect`). The stream also carries a `commands` marker where the host's command phase starts, sent at once as `start_party_command_selection` begins (`Recorder.command_phase`, once per phase), since with none of the host's characters able to act (stunned, bound, frozen by time stop) the game goes straight on to `turn_start` and the host waits for the guest's commands within that call; and an `end` marker in `process_victory`, `process_defeat` or `process_abort`. At each turn's start the host waits for the guest's `commands` (`Live.host_commands`) and gives them to the friend's characters (`Commands.apply`: skill or item, id, target index; a troop is the other game's party in the same order, so an index means the same member). A character the guest names no commands for (`nil`) keeps the computer's choice, an empty list takes its actions away, and a list counts only as many commands as the host's game gave the character actions, since the host rolls the extra ones. The friend's characters use items from the friend's bag, so `Opponent` checks no item count and uses none up; the host records an `item_used` event for a consumable one, which the guest's own game uses up (`Playback.use_up`).
- **Guest:** never runs battle logic. `battle_start` and `turn_start` send its `ready` or its `commands` (`Commands.build`) and play the stream (`Playback.run`) until the next `commands` marker or the end, and `judge_win_loss` never ends the battle on its own. Animations are only started on the guest's battlers, unless the guest holds its skip key, since the host's recorded waits that follow keep the pace and the game's own animation methods would wait a second time. When four or more sends of the stream wait (`BEHIND_SENDS`), the guest skips waits and animations until it caught up. A message goes into a box as soon as its last line arrived. Values are set directly (`@hp`, `@states`, …), with no side effects of adding a state; once a character's states or buffs changed, the game's cache of its features (`CacheActorFeatures`, which only `Game_Actor#refresh` clears) is cleared (`features_changed`), or a state's extra actions, such as Division's (states 208-210, 663), and its counters would never count on the guest. A recorded call the guest does not make (`callable?` false) is logged once per method ("left out the host's log call ..."), since a call left out shows nothing, such as a hit's damage numbers; the host logs where a co-op guest's rebuilt character differs from what the guest's game showed (`MGQ_MpBattlesCoop.check`, `Game_MpActor#differences`), whose rates now include magic reflection and counter (`MGQ_MpActors::Builds::RATES`, xparams 0, 1, 2, 5 and 6). The host's end is turned around (`Live.guest_end`). After a played turn the guest ends its turn (`BattleManager.turn_end`) before the next command phase, since `BattleManager.input_start` makes new actions and starts at the first member only when the phase is not `:input` already. While it plays a turn, the guest keeps its party's status windows up (`@battle_actor_status_windows_show`), which the game shows only during its own turn logic. Time stop (the game's *over drive*, `Game_Party#od_turn` and `od_user`, which decide who may act) travels as a `time_stop` event whenever it changes, and its darkening and music fade as `Game_Screen#od_fadein`/`od_fadeout` and `Audio.start_over_drive`/`end_over_drive`.
- **Each game's language:** a translated and an untranslated game play together, so the host sends what happened rather than its texts wherever the game builds a line from data, and the guest writes the line with its own game's code and texts (`Recorder.call`, `Playback.call`). These are every `display_*` method of `Window_BattleLog` (the battle log's lines, built from the target's `Game_ActionResult`, the database and `Vocab`), `Scene_Battle#process_skill_word` (the line a character says with a skill, and its cut-in) and `#display_skill_name`. The host records the method, its arguments, the action results of the battlers among them and a seed; it draws its own random numbers from that seed during the call (`Recorder.seeded`), and so does the guest, so the guest's `.sample` picks the same one of a skill's lines. Everything the call does itself is left out of the recording (`Recorder.muted`), since the guest's call does it too: its log primitives, popups, messages, sounds, pictures, sprite effects (on the guest's own battlers, so a hit on the host's character is a hit on an enemy) and waits, which the guest skips while it catches up (`Playback.skip_wait?`). The battlers' values are recorded right before the call. The guest calls only the `display_*` methods its own hooks wrapped (`Hooks.log_calls`) and the battle's `SCENE_CALLS`, compared as text, never making a symbol of the host's. "X appears!" comes from `BattleManager.battle_start`, which the guest never runs, so the host records an `emerge` event instead of those lines, with whether its party struck first or was surprised, and the guest names its own troop, says who struck first and gives its first command phase the same start (`Playback.emerge`, `take_encounter`). A call with an argument `Wire` cannot carry is recorded as what it does, in the host's language, like every line built outside these methods.
- **Rules:** Escape ends the battle at once as a forfeit (`Live.forfeit`), which also sends `forfeit`; Give Up is off, as in every multiplayer battle (`MGQ_MpBattles`, `BattleManager.can_giveup?`). Both sides watch for the friend's `forfeit`, a `broken` and the link ending (`Channel.ending`) every frame of `Scene_Battle#update` (`Live.watch`) and while they wait (`Waiting.wait_for`, `Playback.run`), so a forfeit or a friend who leaves ends the battle while a player chooses commands too; `Live.end_early` ends it. No message holds either player up: the Battle Dialogue mod, when installed, shows them in boxes (see below), and one the message window shows moves on by itself after 90 frames (`Window_Message#input_pause`). When the link ends, the remaining player wins; `DROPOUT = :computer` lets the computer play the friend's team on the host instead. A battle broken off has no winner (`process_abort`, "broke off" on the map). There is no turn timer: once a wait lasted 10 s (`Waiting::LEAVE_FRAMES`), the box offers to leave the battle with Cancel, which counts as a forfeit, so a friend whose game hangs with the link still open never holds the other player for good.
- **Mirror matches** record into `Logs/Battle Recording.log` instead, one `Wire` line per event after its frame.

`Hooks.install` puts the hooks in once the first scene starts (a `SceneManager.run` hook), since the game's plugins load after the Patch folder and `Promestein2` defines `Scene_Battle#battle_start`, `Scene_Battle#turn_start` and `Window_BattleLog#add_text` anew, which drops a hook installed before it. `Hooks.wrap` keeps each wrapped method under a name of its own, since `turn_start` is wrapped twice. What the stream carries: the calls the guest makes itself (see *Each game's language*), and outside them the battle log's primitives (`add_text`, `replace_text`, `back_one`, `back_to`, `clear`, `clear_popup`), `PopupResults#push`, messages with their face and speaker (`process_skill_word` and `process_down_word` set it, since a line names its speaker only by name, which both teams can share), pictures of the troop screen (cut-ins; erases only of pictures that were shown), its shakes, flashes and tone changes, every `Audio` call (the log plays some sounds directly), animations as `show_animation` is asked for them, before it checks the skip key, sprite effects, the skill name, turns, actions and the scene's waits.

**Not yet in the live battle:** effects outside the battle log's calls turned around for the other side, a confirmation before Escape, and the computer taking over the host's team when the host leaves.

**Not covered yet:** the Backline in team duels and levelling the two teams.
